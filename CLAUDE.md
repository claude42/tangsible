# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Tangsible is a TUI wrapper for `ansible-playbook`, aimed at interactive use (e.g. during development). `design-docs/Purpose.md` documents the "why" — read that before making design choices; this file covers the "how" of the live run/TUI machinery. `README.md` is the user-facing feature tour (all verbs, keyboard shortcuts, install); `design-docs/Codemap.md` is a brief per-package/per-file map of the source tree for orientation, kept in sync separately from this file — check it (and re-verify against a quick `grep`, since it can itself drift) before assuming a file lives where a past version of this doc said it did.

Tangsible is a single Go binary with nine verbs: `run`, `rerun`, `role`, `template`, `host`, `hosts`, `revisit`, `vault`, `version` (`internal/config/resolve.go`'s `ParseVerb`). Most of this file covers the shared live-run/TUI machinery behind `run`/`rerun`/`role`/`revisit`; the other verbs (`template`, `host`/`hosts`, `vault`, `version`) are standalone programs that share supporting packages but never construct the live tree at all. See each verb's own section below.

**Package layout.** The codebase used to be one flat `package main`; `design-docs/Restructuring.md` documents the full move to `internal/`, phase by phase, including several "checked directly, not assumed" corrections worth reading if you're ever tempted to guess a dependency instead of grepping it. Current shape: `internal/playbook` (core event/aggregation data model, depended on by nearly everything, itself dependency-free), `internal/uikit` (generic tree/row/tab rendering toolkit — knows how to render a `PlaybookState`, nothing about verbs or subprocesses), `internal/config` (settings/history/passthrough-arg parsing, the hub every verb reads), `internal/runner` (spawn/stream/track-progress/record-outcome for one `ansible-playbook` generation), `internal/source` (task YAML source lookup), `internal/ansibledoc` (`ansible-doc` shellout), `internal/inventory` (shared `ansible-inventory --list` client), `internal/role`/`internal/host`/`internal/template`/`internal/revisit`/`internal/diff` (one package per standalone-ish verb), and `internal/session` ("the live tangsible session": verb orchestration for run/rerun/role plus the live TUI itself). `NewLiveTUI` (`tui.go`) used to be one ~3400-line function built from ~40 closures over shared state — `design-docs/Restructuring.md`'s own postponed "Phase 3," done as of this writing: `tui.go` is now an 879-line constructor, and everything it used to contain directly lives on a `liveSession` struct across a dozen `internal/session/livesession*.go` files (see Package layout's own Codemap.md pointer, and the TUI section below). Root `main.go` is a ~30-line wrapper: `func main() { session.Main(...) }`.

The TUI (`tview`) comes up immediately and updates incrementally as jsonl events arrive while `ansible-playbook` runs. Navigation: arrow/j-k (no wraparound), Space/`b` page down/up, Enter expands/collapses a task's host rows, Right/Left expand/collapse a task directly, `E`/`C` expand/collapse everything, `n`/`N` hop to next/prev task (preserving selected host where possible), Home/End/`G`/Ctrl-A/Ctrl-E jump to first/last row, `q`/Ctrl-C quit (or interrupt the running process — see Exit codes below). The view auto-follows the newest row until the user scrolls (including via End/`G`/Ctrl-E, deliberately plain navigation); only `F` re-engages follow. Full shortcut reference: `design-docs/Keyboard-shortcuts.md`.

Play rows: white/bold. Task rows: plain gray, with every host discovered so far shown on the collapsed row, each colored by its outcome for *that* task (green/yellow/teal/red/maroon for OK/Changed/Skipped/Failed/Unreachable) or grey if not yet reported — not aggregate counts. The selected row renders distinctly (black bold text, light gray title background, per-host outcome colors as backgrounds with blended transitions) rather than a flat highlight. Expanding a host row shows outcome + a short detail (OK: single output line or line count; Skipped: `skip_reason`/`false_condition`). Enter on a host row opens a full-screen (or split-pane) drill-down (MSG/STDOUT + STDERR + full JSON, plus Resolved/Docs/File/Diff tabs — see below); Left/Right there switch host, `n`/`N` switch task. Top/bottom bars are white-on-navy (purple when revisiting a past run, fuchsia in diff mode, olive with a `[CHECK MODE]` note under `--check` — see their own sections below); the top bar ticks a spinner + elapsed time + a progress fill, freezing once the run finishes. Requires a real TTY.

## Commands

```
go build ./...                                          # build
go vet ./...                                             # lint
go run . <verb> [args...]                                # run any verb
go run . run [<playbook.yml>] [ansible-playbook args...] # the common case
```

The leading verb is mandatory (`internal/config/resolve.go`'s `ParseVerb`): `run`, `rerun`, `role`, `template`, `host`, `hosts`, `revisit`, `vault`, or `version`. Each verb's own arg shape is documented in its section below and in `README.md`.

Try it against the bundled fixtures:
```
go run . run testdata/outcomes.yml -i localhost,
go run . run testdata/multihost.yml -i testdata/multihost-inventory.ini
```

`go test ./...` runs the unit suite (`go test -run <Name> ./...` for one test) — see `design-docs/TESTING.md` for the testing philosophy (its own file/function references predate the `internal/` split and need translating through `Codemap.md`, but the phased "pure functions before UI code, weighted by this codebase's own bug history" approach still holds). `go test -tags e2e ./...` adds tmux-driven e2e smoke tests (`e2e_rerun_test.go`, root-level — the one file that deliberately stays outside `internal/` regardless of what moves underneath it, since it only ever drives the compiled binary externally), needing `tmux`/`ansible-playbook`, excluded by default.

`completions/` (bash and fish) is hand-maintained, not generated — it needs a manual update whenever the CLI surface (verbs/flags) changes; nothing enforces that it stays in sync.

The playbook argument is optional for `run`/`rerun`/`host` (`internal/config/resolve.go`): if omitted, resolved in order from `$TANGSIBLE_PLAYBOOK`, `./.tangsible/config.toml`, `$XDG_CONFIG_HOME/tangsible/config.toml` (or `~/.config/...`), `/etc/tangsible/config.toml` (`SystemConfigPath`, an admin-set system-wide default — deliberately not `$XDG_CONFIG_DIRS`/`/etc/xdg`, which in practice is a desktop-session convention, not one CLI/server tools follow for `/etc`), then `./site.yml`; usage error otherwise. All three config files share a `[general]` table — beyond `default_playbook` (the only key that cascades beyond the project-local file, in that same project → user → system order; every other key below is project-local only):

```toml
[general]
default_playbook = "myplaybook.yml"
default_tree_state = "collapsed"    # or "expanded"
two_pane_layout = true              # nil (absent) also means true
color = true                        # nil (absent) also means true
run_dialog = "default"              # "default" | "never" | "always" — see Rerun dialog below
notify_playbook_finished = "off"    # "off" | "osc9" | "osc777" | "osc99" | "bell" — see Notifications
notify_task_failed = "off"
notify_task_failed_max = 5
template_hosts_max = 10             # see Template below
```

All unrecognized/absent values silently fall back to these documented defaults — no warnings, consistent with `resolvePlaybook`'s existing "swallow and fall back" convention.

Requires `ansible-playbook`. Tangsible ships its own bundled ansible callback plugin (see Data source below) - no separate collection install needed.

## Architecture

**Verb dispatch / playbook resolution (`internal/config/resolve.go`, `internal/session/main.go`).** `os.Args[1]` must be one of the nine `Verb` constants; `session.Main()` funnels each verb into its own machinery, with `run`/`rerun`/`role` sharing the same live-TUI/generation path (see Rerun below). `SplitPlaybookArgs` decides by *shape* whether a playbook was given positionally: empty or starting with `-` means no playbook (whole slice becomes passthrough), anything else is the playbook — this is `run`'s own resolution; `rerun` has a separate, history-aware one (`internal/config/rerunresolve.go`'s `ResolveRerun`). A missing config file is silent; an existing-but-unparseable one warns to stderr and falls through. The resolved playbook string is passed through with no path-joining of Tangsible's own — `ansible-playbook`/`BuildTaskSourceIndex` resolve relative paths against the cwd themselves.

**Data source (`internal/runner/`, `callback/tangsible_jsonl.py`, design-docs/OwnCallbackPlugin.md).** Shells out to `ansible-playbook` using tangsible's own bundled `aggregate`-type callback plugin — a GPL-3.0-or-later fork of `ansible.posix.jsonl`, deliberately schema-compatible with it (`internal/playbook/events.go`'s `RawEvent` decodes either), shipped as a sibling file to the `tangsible` binary rather than `//go:embed`-ed into it (keeps the Apache-2.0 binary GPL-free; `ResolveCallbackPluginDir` finds it via a dev-only env var, `<prefix>/share/tangsible` derived structurally from the executable's own path (data, not an executable itself, so `.../share` not `.../bin` — install.sh's own `CALLBACK_DIR`, `internal/config.DataHome`), or `$XDG_DATA_HOME/tangsible` directly, in that order — see that function's own doc comment). Being `aggregate` rather than `stdout`-type is what lets it run *alongside* the user's own configured stdout callback instead of replacing it: `CallbackPluginEnv`/`ResolveCallbacksEnabled`/`PrependCallbackPluginsPath` union our plugin into `ANSIBLE_CALLBACK_PLUGINS`/`ANSIBLE_CALLBACKS_ENABLED` rather than overwriting whatever the user already configured (`ansible-config dump --only-changed` is how the "already configured" part is even known). The live TUI run (`SpawnGeneration`) gets events over a dedicated inherited fd (`TANGSIBLE_EVENT_FD`, `cmd.ExtraFiles`) so the child's real stdout stays free for the user's own callback; three one-shot scrapes (`internal/host/host.go`/`internal/template/template.go`/`internal/session/resolved.go`) skip the fd and just tolerate the mixed stdout `cmd.Output()` already scans (they only ever look for one specific event+host, discarding everything else, JSON or not). `ANSIBLE_JSON_INDENT=0` is still pinned everywhere, guarding the one-event-per-line scanner against a user's `ansible.cfg` overriding it to pretty-print.

**Concurrency (`internal/runner/process.go`, `internal/session/main.go`).** TUI and event stream run concurrently, coordinated by two `atomic.Bool`s: `processDone` (set on `cmd.Wait()`; per-*generation*, reset by `requestRerun` before each new spawn) and `quitting` (set once the user quits; checked before every event so a closed UI is never queued into — tview's update queue is a fixed 100-slot buffer nothing drains once stopped). `StreamStderr` collects the child's stderr into a slice printed only after `app.Run()` returns (printing to the terminal while the alternate screen is active would corrupt it); `cmd.Wait()`'s error is likewise deferred.

**Pre-flight gate (`internal/session/main.go`).** A bad playbook path/parse error/missing inventory is caught by `ansible-playbook`'s own CLI layer before any callback event fires, writing zero bytes to stdout — so showing the TUI unconditionally used to open a blank, ticking screen. `ScanEvents` (`internal/runner/process.go`) sends one `StreamItem` per stdout line on its own goroutine, closing the channel at EOF; `Main` peeks one item before constructing `PlaybookState`/`NewLiveTUI`. If the channel closes with nothing (`!ok`), the TUI is never built — stderr + exit error print directly. `v2_playbook_on_play_start` fires unconditionally as the first event of any real run (even a zero-task play), so "at least one line arrived" is a reliable gate. Not handled by this gate: `--list-tasks`/`--list-hosts`/`--syntax-check` bypass Ansible's callback system and print listing text straight to stdout, so they still open the same empty ticking TUI.

**Exit codes (`internal/runner/process.go`, `internal/uikit/tui_rows.go`).** `ansible-playbook`'s exit codes are overloaded:
- **99** (`runner.AnsibleUserInterruptedExitCode`) = "user interrupted execution." Unambiguous here because `tcell`'s raw mode disables OS Ctrl-C→SIGINT delivery, so the child only ever receives SIGINT via Tangsible's own forwarding.
- **4** = both `HOST_UNREACHABLE` and `PARSER_ERROR` (ansible-core has its own `FIXME: conflicts` comment about this). Disambiguated via `state.HadUnreachable` (`internal/playbook/aggregate.go`, set only by a real `v2_runner_on_unreachable` event, structurally impossible for a parse-time failure): `benignHostUnreachable := exitCode == 4 && state.HadUnreachable`. Exit 6 (failure + unreachable) still reports as an error.

Both benign cases return normally (exit 0) instead of `os.Exit(1)`; only 99 additionally suppresses stderr noise. `uikit.StatusRowText(code, hadUnreachable, userInterruptedCode)` renders the closing status line: green for genuine success, yellow for benign-unreachable, red for user-stopped or genuine failure — every terminal case gets an explicit line so a real failure never reads as "did this even finish?". `uikit.GenuineFailure(code, hadUnreachable, userInterruptedCode)` is the shared predicate behind that and behind auto-jumping the cursor to the last failed task/host on the running→frozen transition (skipped if that task doesn't match the active filter — see Filtering). Both took a third `userInterruptedCode` parameter when they moved into `internal/uikit`, specifically to avoid reading `runner.AnsibleUserInterruptedExitCode` across a package boundary for a value that isn't really a rendering concern — every caller passes the constant (or a literal `99` from a test with no access to it by name) at the call site.

**Error output (`internal/session/errorrows.go`, `design-docs/ErrorOutput.md`).** A genuine failure's collected stderr (`runner.StreamStderr`) used to only ever be printed after the whole session ends — corrupting the alternate screen was the risk that kept it out of the live TUI at all, so the one thing that explains *why* a run failed was invisible until `q`. Now shown inline: a `lastStderr *atomic.Pointer[[]string]`, stored by `RunOneGeneration` the exact same way (and at the exact same point, right before `processDone`) as `exitCode` already is, so `rebuild()` can read it with no separate lock once it observes `processDone`. `errorOutputRows(width)` appends a blank divider, a plain "Error output:" heading (styled like the recap section's own "Summary" heading), then the stderr — filtered through `runner.FilterRedundantWarnings` (drops `[WARNING]:` lines already visible via the tree's own per-host marker) and `uikit.WrapText` (`TreeList` rows are single-line and don't wrap on their own — an already-short line is left completely untouched, whitespace included, since `ansible-playbook` prints short, alignment-significant context lines — a source snippet, a `^` column pointer — right alongside a long `[ERROR]:` sentence, and only the latter needs reflowing). Gated on `GenuineFailure`, same as the auto-jump-to-failure feature; ordinary rows, no modal, so the terminal's own native mouse-selection/copy already works on it.

`state.HadUnreachable` is read with no atomic, deliberately: every write happens inside `state.Apply`, which always runs on the single `app.Run()` event-loop goroutine.

**Event shape (`internal/playbook/events.go`).** `RawEvent` decodes the subset of the jsonl schema needed. Empirically confirmed, not formally documented upstream — re-verify against real output before depending on new fields: `v2_playbook_on_play_start`/`v2_playbook_on_task_start` carry `play.name`/`task.name` but no host list (no event reveals a task's hosts before its first per-host result); `v2_runner_on_{ok,skipped,failed,unreachable}` share `task` + `hosts: {<hostname>: {...}}`, with `changed` distinguishing OK/Changed within `_on_ok`. `RawEvent.Hosts` is `map[string]json.RawMessage` (module result shapes vary too much to model as one struct) — `DecodeHostResult` extracts classification fields; the raw bytes are kept for display (`TaskNode.Raw`). `TimestampText` is a plain string with fallible parsing done separately by `Timestamp()`, so a malformed timestamp can't fail `json.Unmarshal` for the whole event.

**Aggregation (`internal/playbook/aggregate.go`).** `PlaybookState.Apply` builds `Plays []*PlayNode` → `Tasks []*TaskNode` → `Hosts map[string]Outcome`, lazily (a play only appears once its first task starts). Every event resolves its own task via `findOrCreateTask(ev, host)`, keyed by `ev.Task.ID` (`tasksByID`) — present on every task-start/terminal/`v2_runner_on_start` event alike, under stock `ansible.posix.jsonl` as much as this app's own bundled fork (confirmed directly against `jsonl.py`'s own `_new_task`) — rather than a single shared `currentTask` pointer updated on task-start, the design this replaced (`design-docs/StrategyFree.md`): that assumed Ansible's linear strategy (never more than one task in flight at a time), and simply broke under `strategy: free`, where hosts progress independently and several tasks can be genuinely simultaneous — see `strategy: free` below. `id` alone isn't always trustworthy, though: a dynamically-included task (`include_tasks`/`include_role`) gets its own freshly-constructed Task object — and so its own distinct `id` — independently per host under `strategy: free` (confirmed live, a real bug report), since `free`'s per-host independence means Ansible never merges hosts into one shared batch the way `linear` does for an identical include. `findOrCreateTask` falls back to matching by source `path` (`PlayNode.tasksByPath`, scoped per play) when `id` misses — safe because no two distinct tasks share a path — but only claims the earliest same-path node this host hasn't already touched (`TaskNode.hasHost`), since a `loop:` around an include produces one genuinely separate node per iteration at that same shared path, and those must stay separate rows. `v2_playbook_on_task_start` and `v2_playbook_on_handler_task_start` (handlers) are handled identically in the same case — treating them separately used to silently attribute a handler's result onto whichever regular task last started. `TaskNode.inFlight` (per host, set by `v2_runner_on_start`, cleared once that host reports a terminal outcome) backs `PlaybookState.IncompleteTasks()` — every task currently in flight, in first-seen order; under `strategy: linear` this is never more than one task, exactly what `CurrentTask()` used to track before it was retired. Counts are computed on demand from `TaskNode.Hosts` via `Counts()`, not tracked separately. Three nil-checked hooks (`OnPlayAdded`/`OnTaskAdded`/`OnHostRecorded`), UI-agnostic, let `internal/session/livesession_events.go`'s `onPlayAdded`/`onTaskAdded`/`onHostRecorded` grow the tree incrementally instead of rebuilding from scratch. Safe with no mutex only because `Apply` always runs on tview's single event-loop goroutine (via `QueueUpdateDraw`) — not a general concurrent structure.

`AllHosts` is the run-wide sorted set of hosts seen so far (only grows); the TUI uses it to grey out hosts that haven't reported for a given task yet, and (live, sorted/deduplicated) as one of Rerun dialog autocomplete's candidate sources. `OutcomeUnreachable` is its own outcome, not folded into Failed. `TaskNode.Raw` mirrors `Hosts` with each host's full raw JSON, read but never interpreted here. Deliberate simplification: `ignore_errors: true` failures still render as Fail (Ansible itself counts them toward `ok` + a separate `ignored` tally, and `ansible.posix.jsonl` never even includes the `ignore_errors` field in its emitted events — confirmed by reading its source directly) — this app's rollup won't numerically match Ansible's own recap for such playbooks, and neither does the recap view below.

**Plain-text rendering (`internal/session/render.go`).** `Render` dumps the whole tree in one shot. No longer used by the normal flow; kept as a dependency-free debug/non-interactive-mode option.

**TUI (`internal/session/livesession*.go`, `internal/uikit/`).** Built on `tview`/`tcell`. `NewLiveTUI` (`tui.go`) constructs every widget and populates a `liveSession` struct (`livesession.go`) — every piece of state or widget more than one method touches lives there as a field, set up once at construction and never re-declared. `design-docs/Restructuring.md`'s own Phase 3 turned what used to be ~40 closures sharing that state into named `*liveSession` methods (and, for the two genuinely self-contained pieces, their own dedicated types — see below), spread across a dozen files by concern:
- `livesession_rebuild.go` — `rebuild()` (the ~380-line method nearly everything else calls to trigger a redraw) plus the small chrome/style helpers that exist only to serve it.
- `livesession_tabsearch.go` (+ `_test.go`) — `tabSearchPanel`, the in-tab search subsystem (see In-tab search below) as its own type, genuinely independent of the rest of `liveSession`'s state.
- `livesession_rerundialog.go` (+ `_test.go`) — `rerunFieldSync`, the re-run dialog's field/checkbox sync logic (see Rerun below) as its own type, the other genuinely self-contained piece — plus `openRerunDialog`/`submitRerun` as plain `liveSession` methods in the same file, since those two *do* reach into the rest of the shared state pool.
- `livesession_output.go` — the output drill-down (`showOutputWithOrigin` and friends).
- `livesession_filter.go` — the tree-level filter/search dialogs.
- `livesession_nav.go` — expand/collapse/navigation.
- `livesession_events.go` — `PlaybookState`'s event hooks and `applyLive`.
- `livesession_heartbeat.go` — the heartbeat and resize-watcher tickers.
- `livesession_input.go` / `livesession_mouse.go` — the keyboard/mouse dispatchers (see Keyboard shortcuts/Mouse below).

These two dedicated types (`tabSearchPanel`, `rerunFieldSync`) are the only pieces of the former `NewLiveTUI` that are genuinely unit-tested in isolation — everything else reaches too far into `liveSession`'s shared state to test without a live `*tview.Application` or tmux, and this refactor never tried to change that; see `design-docs/TESTING.md`'s own long-standing stance and `Restructuring.md`'s Phase 3 write-up for the honest accounting of what did and didn't become more testable.

The generic rendering/filtering/tab-building machinery `liveSession` and the standalone verbs (`diff`, `host`, `template`) all reuse lives in `internal/uikit`: `treelist.go` (a hand-rolled `tview.Primitive` replacing `tview.List` — see Mouse below for why), `tabs.go` (`TabbedPane`, shared by the drill-down and the template page), `tui_style.go` (palette/style constants), `tui_layout.go` (row-text rendering: `TaskLabel`/`HostLabel`/`PlayRowText`/`ColorTag`/host-column layout), `tui_rows.go` (`Row`, `FlattenRows`, status-row text), `tui_filter.go` (`FilterQuery`/`TaskVisible` and the All/Changed/Failed/search filters), `tui_dialogs.go` (`CenteredModal`/`FilterDialogText`/`InRect`), `tui_drilldown.go` (`BuildOutputTabs` and the whole per-tab builder family). Row text still goes through `tview.Print`'s same tag-parsing entry point (`[color]text[-]`).

`liveSession` owns:
- **Expand state** (`s.expanded map[*playbook.TaskNode]bool`) — a new task inherits the *previous* task's current entry, except the very first task of a generation, which falls back to `startExpanded` (`.tangsible/config.toml`'s `general.default_tree_state`). This is what makes `E` "sticky" for a still-running playbook.
- **Flattening** — `uikit.FlattenRows(state, s.expanded, width, ...)` walks `Plays → Tasks → (if expanded) Hosts` into an ordered row list, rebuilt fresh on every event (cheap at ~10-host scale).
- **Selection preservation** — `s.rebuild()` tracks the selected row's *identity* (`*playbook.PlayNode`/`*playbook.TaskNode`/`hostRowID`, not an index, since row order shifts). Computes `selectedIndex` *before* `Clear()`+`AddItem()`, since the cursor row's styling is baked into its own text. A `s.rebuilding bool` guard is needed because `Clear()`+first-`AddItem()` fires a spurious "changed" event that would otherwise stomp the tracked selection mid-rebuild.
- **Autoscroll** — `s.following bool` (default true) makes `rebuild()` resolve `selectedIndex` to the newest row. Any genuine navigation disengages it; only `F` re-engages (with its own `s.jumpingToEnd` guard against immediately un-following itself). End/`G`/Ctrl-E are deliberately plain navigation, not follow-resuming.
- **Navigation triggers a full `s.rebuild()`** so the cursor's baked-in styling actually moves — otherwise, once frozen (heartbeat ticker stopped), the highlight would never move again.
- **`s.revealExpandedTask`** — expanding a task via Enter/Right leaves the cursor on the task row itself, so nothing auto-scrolls to reveal newly-added host rows below the fold; this nudges the scroll offset down (never up) just enough to reveal the block's tail.

`NewLiveTUI` returns the `*tview.Application` plus `s.applyLive` (a `func(playbook.RawEvent)` method value); `internal/session/main.go` never imports `tview` — only `tui.go`/`livesession*.go`/`internal/uikit` touch `tview`/`tcell`.

**Heartbeat (`internal/session/livesession_heartbeat.go`).** A 200ms ticker (`spinnerInterval`) calls `app.QueueUpdateDraw(s.rebuild)`, refreshing the top bar (spinner + elapsed + progress fill, see Progress indicator below) and every currently-active task's own spinner prefix (`state.IncompleteTasks()`, empty once `processDone`). Stops permanently once `processDone` is observed, after pushing one final frozen frame — elapsed time is latched (`haveFrozenElapsed`/`frozenElapsed`) the first time `s.rebuild()` sees `frozen == true`, so later rebuilds (from navigation or mouse panning) don't keep recomputing a climbing elapsed time after the run has actually finished. Started only after `app` itself is assigned, for Go memory-model happens-before reasons.

**Resize watcher (`internal/session/livesession_heartbeat.go`).** A second permanent ticker, needed because the heartbeat ticker stops once frozen and nothing else would notice a bare terminal resize then. Skips its body while the run is live (heartbeat already covers resize). Once frozen, compares `list.GetInnerRect()`'s width against `lastRebuildWidth` each tick and calls `s.rebuild()` + `app.ForceDraw()` only on an actual change. Must use `ForceDraw()`, not `Draw()`/`QueueUpdate` — calling `Draw()` from inside a `QueueUpdate` closure (already on the event-loop goroutine) is a self-deadlock.

**Task source lookup (`internal/source/source.go`).** `BuildTaskSourceIndex(playbookPath)` backs the drill-down's "Task definition" section. Every event's `task.path` is an absolute `file:line`, resolved by Ansible itself even for a Jinja-built `include_tasks:` path — so no include/role resolution needs reimplementing; `BuildTaskSourceIndex` just walks every `.yml`/`.yaml` under the playbook's directory tree and indexes each task by `(path, start line)`. A miss (unusual layout, a runtime-generated task) just means no source section, never an error. Uses `gopkg.in/yaml.v3`'s line-tracked `*yaml.Node` tree (not a typed struct) to compute each task's end line as the start of the next sibling at whichever ancestor level has one — this is what correctly stops a `block:`'s last task right before a sibling `rescue:` key with no special-casing of `block`/`rescue`/`always`, and handles multi-line scalars for free (the boundary comes from the next task's line, not from measuring the scalar). Source text is sliced verbatim, never reformatted; `{{ ... }}` expressions render as literal text (no Jinja evaluation). This same walk-the-directory-tree approach is why `role`'s and `template`'s own throwaway stub playbooks are always written to the current working directory rather than a system temp dir — see their sections below.

**Output drill-down (`internal/session/livesession_output.go`, `internal/uikit/tui_drilldown.go`).** Root is a `tview.Pages` with `"main"` and `"output"` (a single reused `TextView`). Host rows' `selected` callback calls `s.showOutput(task, host)` (a struct-field closure calling `s.showOutputWithOrigin`, kept as a field rather than a plain method since `uikit.FlattenRows`/`flattenRecapRows` need its exact 2-arg callback shape) → `uikit.BuildOutputTabs` → switch pages; `SetDoneFunc` (Escape/Enter/Tab/Backtab) switches back. Tabs, in order: Output, Task definition, Resolved, Docs, File, Diff, Details — built lazily per tab-open except Resolved/Docs/File, which are fetched async on their own goroutines the moment the drill-down opens (see Resolved values and Show file contents below) and populated via `app.QueueUpdateDraw` once done, so switching tabs never blocks. Three gotchas: `TextView.SetText` doesn't reset scroll position, so `showOutputWithOrigin` must call `ScrollToBeginning()` every time; Left/Right and `n`/`N` mean different things per page, so `handleKey` (`livesession_input.go`) needs `s.viewingOutput bool` to dispatch correctly; and closing the drill-down (`closeOutput`) must call `s.outputTabs.Clear()` (`internal/uikit/tabs.go`, `design-docs/RerunDialogFocusBug.md`) — a real, reported bug otherwise: `tview.Pages.InputHandler` (unlike `MouseHandler`, which dispatches by `Visible`) dispatches a keystroke to the *first* registered page whose own `Item.HasFocus()` is true, regardless of `Visible` — and `s.outputTabs`' own internal `tview.Pages` is left with a stuck `hasFocus` once ever focused, surviving even `Application.SetFocus` elsewhere and even removing its tabs; only an explicit `.Blur()` on it (what `Clear()` does) clears it. Left unfixed, "output"/"split" (registered before every dialog page) silently hijacked every real keystroke meant for whatever dialog opened next — confirmed live: the re-run dialog's own fields accepted mouse clicks fine but not typing/Tab.

`uikit.BuildOutputTab` decodes `task.Raw[host]` into a generic map (module shapes vary too much for a fixed struct), leads with a colored status line, then `PrimaryOutputField`'s text, then `stderr` if present, then the full result as pretty JSON as a universal fallback. `PrimaryOutputField` picks `stdout` if non-empty else `msg` — shared with the collapsed-row OK-line summary so both agree on what "the output" means.

**Color in the output view.** `SetDynamicColors(true)` means every piece of dynamic content must be `tview.Escape()`'d first (a literal `[` from YAML/JSON would otherwise be misread as a color tag). Section headings use colors deliberately outside the outcome palette (orange/aqua/red/gray for Task/Output/Errors/Details) so they're never mistaken for an outcome color. `colorizeYAML` gives the Task section light `key:` highlighting via a regexp, not a real YAML parser — good enough, not chased to 100%.

**Diff tab (single-run, `internal/uikit/tui_drilldown.go`).** `--diff` is unconditionally appended to every generation's invocation. The drill-down's own Diff tab (`BuildDiffTab`) is a direct port of ansible-core's own `CallbackBase._get_diff` display logic, using `github.com/pmezard/go-difflib`'s `UnifiedDiff` (the same algorithm real `--diff` output uses) — so hunk headers/context grouping match real `ansible-playbook --diff` output. Handles the `diff` field being a single dict or list of dicts, binary/oversize skip notices, and non-string before/after (serialized as JSON, matching Ansible's own default). **Don't confuse this with "diff mode"** (the `d` key, `internal/diff` — comparing two whole *runs* against each other), covered in its own section below; they share the word "diff" but are otherwise unrelated features with unrelated implementations.

**Docs tab (`internal/ansibledoc`, `internal/session/livesession_output.go`).** Shows a task's module documentation by shelling out to `ansible-doc <action>` (the task's own `action` field — `ansible-doc` resolves both bare and FQCN names itself). Strips the ANSI SGR codes `ansible-doc` always emits (rather than translating them to tview tags, which would need re-escaping literal `[` in the docs text without also escaping the tags just inserted). Cached by module name, not cleared on rerun since module docs don't depend on the run. A "Play definition" tab existed briefly and was removed outright after live use showed it was never consulted — its whole plumbing came out with it.

**File tab (`internal/session/fetchfile.go`).** See Show file contents below.

**Resolved tab (`internal/session/resolved.go`).** See Resolved values below.

**Two-paned drill-down (`internal/session/livesession_rebuild.go`, `design-docs/TwoPanedLayout.md`).** On a wide enough terminal, the drill-down opens beside the tree instead of taking over the screen. Governed by `general.two_pane_layout` (`*bool`, absent = enabled). A third `Pages` entry, `"split"`, reuses the exact same `flex`/`outputFlex` primitives the other two pages use (not parallel copies) plus a `splitDivider` box. `s.rebuild()` re-decides `s.splitMode` live on every call (`SplitMinTreeWidth`/`SplitMaxTreeWidth`, ~110 total cols) — not decided once at open — using `pages.GetInnerRect()`'s width, since `list`'s own width isn't a reliable proxy once split-mode has pinned it independently of the terminal.

Live-sync: `s.showOutputWithOrigin` unconditionally sets `s.expanded[task]=true; s.currentID = hostRowID{task,host}; s.following=false` and calls `s.rebuild()` on every call (not just first open), so `Left`/`Right`/`n`/`N` inside the drill-down keep the tree pane's cursor in sync in real time. Hostnames are omitted from collapsed tree rows while split (the currently-relevant host is already shown via live-sync) — implemented via the same `allHosts == nil` fallback path `computeHostColumnLayout`/`taskLabel` already had for "no hosts reported yet." The tree pane stays keyboard-inert while split (no focus-switching — `handleKey`'s dispatch is gated on whether the drill-down is open, not on tview's own focus); its bottom-bar hint text swaps to reflect that.

**Tree pane mouse interaction while split (`internal/session/livesession_mouse.go`'s `handleOutputViewMouse`).** Wheel-scroll pans the tree; a left click on a row expands/collapses a task or switches which host's output is shown (a host row's click calls `s.showOutput`, the same live-sync entry point `Left`/`Right`/`n`/`N` already use) — reported live as a real gap otherwise, since the tree pane is fully visible and already scrollable but couldn't be clicked. Implemented by calling `s.list.MouseHandler()` directly with a **no-op** `setFocus` callback, deliberately not tview's real one — `TreeList.MouseHandler` unconditionally calls `setFocus(t)` on a normal click, which would silently steal keyboard focus onto the tree with no way back short of Escape; swallowing that call is what keeps the drill-down's own keyboard shortcuts working unchanged regardless of what was last clicked.

A real bug found live while building this: `MouseMove`/`MouseLeftDown`/`MouseLeftUp` landing on `s.list` must be let through **unchanged**, never swallowed with a nil event, even though only `MouseLeftClick` itself does anything here. `Application.fireMouseActions` synthesizes one physical click from several calls against the same `SetMouseCapture` callback (move, then down, then up, then click) and threads each call's own returned event into the *next* call in that batch — so swallowing the `MouseMove` that precedes every click (this code's first cut did, via a blanket catch-all `return nil, action`) poisons the rest of the batch with a nil event and `MouseLeftClick` never gets synthesized at all. Confirmed live: with the naive swallow, clicking a row did nothing whatsoever. `handleFilterDialogMouse` had already hit and fixed this exact class of bug for its own dialog (see its own doc comment) — same fix here: only `MouseLeftClick` swallows (after handling it), everything else lands on `s.list` passes through untouched (harmless, since none of `TreeList.MouseHandler`'s other cases act on those action types anyway). A click landing on `s.bottomBar` instead of `s.list` still gets swallowed unconditionally, same "don't let TextView's own default click handling silently steal focus onto a status bar" reasoning as `s.outputTopBar`/`s.outputBottomBar` elsewhere in the same function.

**Row text / host column layout (`internal/uikit/tui_layout.go`).** `ColorTag` maps outcomes to `green`/`yellow`/`teal`/`red`/`maroon` — `teal` for ANSI cyan, `maroon` (not `brown`/`darkred`) because it's in the same base-16 ANSI palette family as the others rather than an RGB-approximated extended name. Hosts are left-aligned starting at a shared column across all task rows (computed once per `s.rebuild()`, not per-row) — the widest *natural* task title across the whole run, monotonically non-decreasing since `state.Plays` only grows within a generation. If the widest title + full host list + a breathing-room floor don't fit, the column shrinks first (down to `minTaskTitleName`=30), then hostnames shrink one rune at a time (no ellipsis, floor of 1 rune, overflow accepted beyond that) — run once against the shared column, not per row, so truncated host text lines up column-by-column.

**Collapsed-row summary mode (`internal/uikit/tui_layout.go`, `design-docs/Morehosts.md`).** When color isn't usable (`NO_COLOR`, non-color terminal, or `general.color = false`) or hosts don't fit even after full shrinking, a task's host list is replaced by a fixed `OK:x/Chgd:x/Skip:x/Fail:x/Unrch:x` count summary instead, colored per-field if color is usable, plain text otherwise. `useColor` is computed once via a throwaway `tcell.NewScreen()` (since `Application.Screen()` isn't available before `Run()` starts) — `SetScreen` must run before `EnableMouse(true)`, since `EnableMouse` only touches a non-nil screen. Live-reevaluated every rebuild, same as `splitMode`.

**Selected-row rendering.** Can't be one uniform `tcell.Style` since different runs within a row need different fg/bg — `PlayRowText`/`TaskLabel`/`HostLabel` each take a `selected bool` that switches their tag construction. `halfBlock` (▌) blends adjacent hostnames' colors at their boundary (selected rows only — tried unselected too, reverted, looked wrong without the "two solid color blocks" context). Uses `pureBlack = "#1a1a1a"`, not `tcell.ColorBlack`/`"#000000"` — a value that exactly matches a base-16 slot's nominal RGB always gets mapped back to that (potentially theme-remapped) slot on reduced-palette terminals; nudging off pure black forces the fixed extended-256 grayscale ramp instead.

**Ctrl-C/`q` (`internal/session/livesession_input.go`'s `handleKey`).** Behavior depends on `processDone`: while running, both forward SIGINT to the child and leave the TUI open; once finished, both close the TUI. This restores "Ctrl-C behaves like running ansible-playbook directly" (`design-docs/Purpose.md`), which `tcell` raw mode would otherwise silently break.

**Keyboard shortcuts (`internal/session/livesession_input.go`).** `design-docs/Keyboard-shortcuts.md` is the source-of-truth reference. `s.app.SetInputCapture(s.handleKey)` wires a small dispatcher that calls out to 12 named sub-methods in a fixed, behavior-critical order (`handleKey`'s own body is the authoritative list — don't rely on this paragraph's grouping over reading it directly), conceptually three tiers: (1) Quit — `handleCtrlC` (Ctrl-C, unconditional, closes an open dialog first if any but always still aborts/quits — see Ctrl-C/`q` above) and `handleGlobalQuit`/`handleOutputViewQuit` (`q`, meaning differs by `processDone`/`viewingOutput`); (2) dialog guards (`handleSearchDialogKey`/`handleTabSearchComposingKey`/`handleRerunDialogKey`/`handleFilterDialogKey`) and universal key aliases (`translateKeyAlias`: `j`/`k`→Down/Up, Ctrl-F/Ctrl-B and Space/`b`→PgDn/PgUp, Ctrl-A/Ctrl-E→Home/End, `G`→End — implemented by returning a *different* synthesized `*tcell.EventKey`, which `Application` forwards to the focused primitive exactly as if typed, so no logic is duplicated per-widget), checked before anything page-specific so a literal typed space/letter still lands normally in a focused text field; (3) page-specific bindings, gated on `s.viewingOutput` (`handleOutputViewKey`/`handleTreeKey`): output view gets Left/Right (`navigateOutputHost`) and `n`/`N` (`navigateOutputTask`, both no wraparound), plus `/` (in-tab search) and `y` (copy active tab); main tree gets `F` (jump-to-bottom + resume follow), `E`/`C` (expand/collapse all), Right/Left (`handleRight`/`handleLeft`), `n`/`N` (`navigateMainTask`), `r` (rerun dialog, once finished), `d` (diff mode, once finished).

`s.handleRight`/`s.handleLeft` act on whichever row is under the cursor (not `s.currentID`) — Right is a one-way collapsed→expanded trip (no-op otherwise); Left always means "close/go up" (collapses an expanded task, or on a host row collapses its parent task and moves the cursor there; no-op on a play row). `navigateMainTask(delta)` hops via `allTasks(state)`, bounds-checked, no wraparound, carrying the selected host to the destination task only if that task actually recorded a result for it. Closing the output view syncs the tree's cursor to whatever (task, host) was last shown there, even if that moved via in-view navigation since it was opened.

**Mouse (`internal/session/livesession_mouse.go`, `internal/uikit/treelist.go`).** `tview.List`'s wheel handling only pans an internal `itemOffset`, but `List.Draw()` unconditionally re-clamps that offset to keep `currentItem` visible on every redraw — so panning could never move the viewport further than the cursor's own distance from the edge. `TreeList` (a minimal purpose-built `tview.Primitive`, single-line rows only, no shortcuts/horizontal-scroll/wraparound) fully decouples `itemOffset` from `currentItem`: `Draw()` has no clamp at all; keeping the cursor visible after genuine navigation is handled instead by `ensureVisible()`, called only from `SetCurrentItem` on an actual index change (guarded by the same `s.rebuilding` flag so `s.rebuild()`'s own housekeeping calls don't trigger it) — this is what makes unbounded wheel panning possible. Click handling ports `tview.List`'s ordering: a row's `selected` callback fires before `SetCurrentItem` moves the cursor there.

**Filtering (`internal/uikit/tui_filter.go`, `design-docs/Filters.md`).** `FilterQuery{Mode, Search}` bundles the filter kind (All/Interesting/Changed/Failed/Search) with a search term. `TaskVisible(t, q, sourceIndex, isActive)` is the single predicate: a task matches Changed/Failed if *any* host has that specific outcome (Unreachable counts toward Failed, not Changed); Interesting matches Changed, Failed, Unreachable, a non-empty stderr, or a warning, on any host — the broader "worth a second look" filter, backed by `TaskNode.Warnings`/`HasStderr` (`internal/playbook/aggregate.go`), precomputed per host at ingestion time rather than decoded from raw JSON on every redraw (a measured cost — profiling a frozen recap once showed most of its CPU time was exactly that). `isActive` (the run's current in-progress task) always matches regardless of filter, so an in-progress task can't flicker in and out before it has any recorded outcome. The search filter (`TaskMatchesSearch`) does case-insensitive substring matching against the task's title, its source text, or any host's output — an empty term matches everything. `FlattenRows` skips non-matching tasks entirely, but shows *all* hosts of a task that does match. `VisibleTasks`/`VisibleTasksForHost` mirror `allTasks`/`tasksForHost` for `n`/`N` navigation so filtered-out tasks are never a navigation target. On a filter switch, if the cursor's task disappears, `nearestVisibleTask` walks forward then backward from its old position to land on the nearest surviving task (only relevant when `following == false`).

Two dialogs, not one (split after live use showed a combined menu+search-box was too easy to fumble): `f` opens a discrete-key `a`/`i`/`c`/`f` menu (`s.filterDialogOpen`) where every other key is swallowed and `q` closes without quitting (a menu reflex, unlike everywhere else in the app); `/` opens a real `tview.InputField` (`s.searchDialogOpen`) where every key except Ctrl-C passes through untouched to the field's own native editing, since a real search term can legitimately contain any shortcut letter. Ctrl-C always closes whichever dialog is open *and* still performs its normal abort — the one key that's never ambiguous.

## Rerun (`design-docs/Rerun.md`)

Re-run a finished playbook (whole thing or starting from a chosen play, with editable tags/skip-tags/hosts) without leaving Tangsible, or via a `rerun` CLI verb.

**Invocation history (`internal/config/rerunargs.go`, `internal/config/history.go`, `internal/config/resolve.go`).** Settings and history are deliberately two separate files/types — combining them meant every invocation's history append rewrote (and could corrupt/strip comments from) the user-authored settings file too:
- `.tangsible/config.toml` — `SettingsConfig`, user-authored, read-only from Tangsible's point of view.
- `.tangsible/state.toml` — `StateConfig` (`General.Last`, `History []PlaybookHistory`), fully app-owned, read+written via full-rewrite each time.

`AppendInvocation` is the single funnel every verb invocation goes through: caps history at 20 entries per playbook (oldest dropped, its saved run log deleted too — see Run logs below), and sets `General.Last` to the target just run — a separate field from `History` because `History` preserves first-seen order, not recency. `LastTarget` falls back to a lone `History` entry if `Last` is unset (covers a state file from a build predating that field); two-or-more entries with no `Last` can't be disambiguated. Only `.tangsible/state.toml` is gitignored, not the whole directory — `config.toml` is meant to be shared/tracked. A role-originated history entry carries a `role` field instead of `playbook` (mutually exclusive shape), so `rerun`'s `General.Last` resolves to either kind uninterpreted.

Each history entry is one generation's passthrough-arg list as a single string (`ArgsToHistoryString`/`HistoryStringToArgs`, a minimal POSIX-ish tokenizer — quoting/escaping only, no expansion). `ParsePassthroughArgs` pulls `--tags`/`-t`, `--skip-tags`, and `--limit`/`-l` out of a tokenized arg list (both `--flag value` and `--flag=value`, multiple occurrences comma-joined), leaving the rest in `Rest` untouched. An attached short form like `-tfoo` isn't recognized (falls through to `Rest`) — a documented gap.

**Process-restart mechanics (`internal/runner/process.go`, `internal/runner/generation.go`, `internal/session/main.go`).** `tview.Application.Run()` is still called exactly once for the whole process; a rerun spawns a new child and streams into the *same* running `app`. `ProcHandle` (an `atomic.Pointer[os.Process]`) is what Ctrl-C/`q` forwarding always reads fresh, so it targets whichever generation is current. `SpawnGeneration` is the shared "start one invocation" step; `RunOneGeneration` drains one generation's stdout, waits, and records a `GenerationOutcome`. `session.Main` accumulates one outcome *per generation* (a rerun's tree/screen state is gone by the time Tangsible exits, so its stderr would otherwise be lost) and prints all of them in order after `app.Run()` returns; only the last one decides Tangsible's own process exit code. `runner.NewRequestRerun(startAtPlay, tags, skipTags, hosts)` resets `state` (`PlaybookState.Reset()`, keeping the `On*Added` hooks wired), reassembles the arg list (tags/skip-tags/hosts from the dialog, a trimmed playbook copy if a start play was chosen — see Start with a play below; everything else carried forward unedited from the *original* invocation's `Rest`), records it, and spawns.

**The re-run dialog (`internal/session/livesession_rerundialog.go`'s `rerunFieldSync`, `design-docs/Rerun.md`'s "Extend rerun dialog").** A real `tview.Form` — `playField`/`tagsField`/`skipTagsField`/`hostsField` as plain `InputField`s (all but `playField` with autocomplete, see Autocomplete below), plus three checkboxes: `resumeCheckbox` ("Resume where failed"), `onlyFailedCheckbox`, `onlyUnreachableCheckbox`. There used to be a "Start at task" field/checkbox pairing (`--start-at-task`); it was removed outright, not just left unwired — task names aren't unique across a playbook (most plays' first task just names the role they call, which repeats every play), so it "cannot be used sensibly at all" per the design doc, and `--start-at-play` (below) replaced it as the thing that actually makes sense. A raw `--start-at-task` can still be passed by hand as an ordinary passthrough arg; there's just no dedicated field for it.

The checkboxes deliberately never call `SetDisabled` on themselves or on `r.playField`/`r.hostsField` (`rerunFieldSync`'s own fields, `internal/session/livesession_rerundialog.go`) — confirmed live during that original "Start at task" checkbox's development: `InputField.SetDisabled`/`Checkbox.SetDisabled` both unconditionally call their own `finished(-1)`, which `Form`'s shared handler replays as a stray navigation key once any real Tab/Enter has happened anywhere in the form's lifetime — so toggling a checkbox this way silently advances focus by one, landing text one field over from where it was typed. Instead: checking "Resume where failed" writes the computed resume play into `r.playField` and auto-checks "Only failed" (one-way coupling — unchecking "Only failed" afterward by itself doesn't uncheck "Resume where failed"); editing `r.playField` by hand unchecks "Resume where failed" and clears it back out if unchecked via the checkbox itself. Checking "Only failed"/"Only unreachable" (either or both) recomputes `r.hostsField` from scratch from whichever failed/unreachable hosts the just-finished generation recorded, rather than incrementally appending — unchecking one when both were checked recomputes down to just the other; editing `r.hostsField` by hand unchecks both. A checkbox is omitted from the form entirely (`rerunFieldSync.rebuild`, not to be confused with `liveSession.rebuild` — same name, different type, both legitimately "recompute and redraw this thing"), not shown disabled, when there's nothing for it to do (no failed/unreachable hosts, or no jsonl data available at all for the `rerun` verb's very first dialog). This focus-skip quirk is exactly the class of bug `e2e_rerun_test.go`'s tmux-driven smoke tests exist to catch — see `design-docs/TESTING.md`'s "hard-to-test tier."

**CLI flags for the same options:** `--only-failed`, `--only-unreachable`, `--resume-where-failed` (`internal/config/rerunargs.go`'s `ExtractRerunFlags`) pre-fill the corresponding checkboxes the same way `-l`/`--tags` pre-fill the text fields — the dialog still always opens and still has to be confirmed with Enter before anything runs. `--resume-where-failed` combined with an explicit `--start-at-play` is a usage error, reported immediately rather than silently picking one. Asking for data that doesn't exist (`--only-failed` when nothing failed, or no jsonl available for the target run at all) likewise fails with an explanatory error rather than silently ignoring the flag.

## Start with a play (`design-docs/StartWithPlay.md`)

`ansible-playbook --start-at-task` is unreliable for the reason above (non-unique task names); there's no equivalent `--start-at-play` in real Ansible at all. Rather than mutating the user's tracked playbook (inserting marker tasks was considered and rejected — pollutes a tracked file, needs idempotent-insert detection, interacts awkwardly with `--tags`/`--skip-tags`), Tangsible builds an *ephemeral* trimmed copy at invocation time: `internal/source/source.go`'s `TrimPlaybookToPlay(playbookPath, playName)` slices the original file from the chosen top-level play's own start line through EOF and writes that slice to a new file **in the same directory as the original playbook**, never a system temp directory — so any `roles:`/`include_tasks`/`import_tasks` reference, resolved relative to the playbook's own directory, still finds exactly what it would have found for the original file. `ansible-playbook` runs against the trimmed copy; it's removed once that generation finishes. `ListTopLevelPlayNames` (named plays only, in file order) backs the dialog's Play-field autocomplete.

**v1 scope, deliberately**: only a playbook's own top-level plays are addressable — a play reached only via `import_playbook` is out of scope, for the same "classify files by shape, don't trace references" reasoning `source.go`'s own doc comment already applies to role/include resolution elsewhere. An unnamed play can't be targeted (nothing to type or autocomplete). Duplicate play names are ambiguous exactly like duplicate task names were for `--start-at-task` itself — first match in file order wins, not specially reported. A known, documented gap, not a partial implementation pretending to be complete.

**A drill-down gap this surfaced, and the fix.** Spawning against a trimmed copy means every `RawEvent.task.path` for a task defined directly in the top-level playbook now points into the trimmed copy's own path/line numbers, not the original file `TaskSourceIndex` was built from at session startup — left unfixed, the "Task definition" tab silently disappears for exactly those tasks (a source-lookup miss is already "nothing to show," never an error, so this degraded silently until checked directly). Fixed by `source.MergeSourceIndex(dst, trimmedPlaybookPath)`, re-indexing the trimmed file and merging it into the existing index in place — safe with no locking since it always runs on the same single event-loop goroutine `state.Reset()` and every `TaskSourceIndex` read already run on.

**CLI form:** `tangsible run --start-at-play <name>` and `tangsible rerun --start-at-play <name>` (`internal/config/rerunargs.go`'s `ExtractStartAtPlay`) offer the same mechanism outside the dialog. `--start-at-play` is Tangsible's own synthetic flag, understood by no real `ansible-playbook` — stripped from the passthrough list before anything else touches it, so it's never recorded into `.tangsible/state.toml` history (a later bare `tangsible rerun` replays history's `Rest` verbatim, straight at `ansible-playbook`, which would reject an unrecognized flag). `run` resolves/validates the named play synchronously before spawning, failing immediately with a clear error if it doesn't match — before anything is recorded to history and before `ansible-playbook` or the TUI is ever involved. `rerun` only pre-fills the dialog's Play field with it (there's no generation to spawn yet at that point); a bad name there isn't caught until the dialog is confirmed.

Modal style matches the search dialog, not the filter menu — every key but Ctrl-C passes through to whichever field has focus. Two exceptions handled centrally: Escape closes the dialog outright (rather than `Form`'s own default of resetting focus to the first field); Enter submits (since `Form` otherwise treats Enter as Tab, never as submit).

**Rerun dialog visibility (`internal/config/dialogflag.go`, `design-docs/RerunDialog.md`).** Whether the dialog opens automatically at a session's *startup* (as opposed to being opened later via `r`) is resolved by `ResolveDialogVisibility(override, pref, verbDefault)` in priority order: an explicit `--dialog`/`--no-dialog` CLI flag (`ExtractDialogFlag`, only recognized by `run`/`rerun`/`role` — every other verb rejects it via `HasDialogFlag` as a usage error rather than letting it leak through to `ansible-playbook` unrecognized) beats the `run_dialog` config preference, which beats each verb's own built-in default (true for `rerun`, false for `run`/`role`). Neither flag is ever persisted into invocation history, the same reasoning `ExtractStartAtPlay`/`ParsePassthroughArgs` already apply to their own synthetic flags.

**Run logs (`internal/config/runlog.go`).** Every generation's raw jsonl stdout is teed byte-for-byte (not re-serialized from the decoded event, which would drop unmodeled fields) into `.tangsible/runs/<RunID>.jsonl` as it streams (an optional `logFile` param on `runner.ScanEvents`), with collected stderr saved alongside as `<RunID>.stderr` once the generation finishes. `RunID` (`config.NewRunID`, nanosecond-precision timestamp) is threaded through `SpawnGeneration` → `FinalizeInvocation`, which stamps it onto that invocation's history record. This is what backs the `revisit` verb and diff mode (both below) — `PruneMissingRunLogs` self-heals a manifest whose `.jsonl` has gone missing on disk (clears `RunID` only, leaving `Args`/`Time`/`ExitCode`, which still feed rerun's tags/hosts pre-fill independent of revisitability). Best-effort throughout: a failed `CreateRunLog` just means that generation isn't revisitable, never fatal.

**Progress indicator (`internal/runner/progress.go`, `design-docs/ProgressIndicator.md`).** The top bar's proportional fill is driven by `ProgressTracker`, seeded from a throwaway `ansible-playbook --list-tasks --list-hosts` probe (`BuildProgressSkeleton`/`ParseListTasksOutput`) run with the exact passthrough args the real generation uses. Matching is a bounded-forward-window (`Advance`, window doubles on consecutive misses up to `ProgressMaxMissShift`), not a plain lookup, because task names repeat across a playbook. `AdvanceToPlay` resyncs on play boundaries (which always fire) to recover from plays with zero matching hosts, whose tasks never produce real events at all. A `strategy: free` play's tasks are excluded from the skeleton entirely too, for a different reason (`source.FreeStrategyPlayNames`, a static per-play YAML scan — `design-docs/StrategyFree.md`): its tasks genuinely do fire real events, but feeding `free`'s own per-host events into `Advance` 1:1 would risk overcounting the moment a task name repeats, exactly the failure mode the bounded window already guards against. The literal "Task x/y" text was deliberately dropped from the top-bar composition — only the background fill remains — because the prediction structurally can't see handlers or looped `include_tasks`/`import_tasks`, and a live run showed it diverging wildly from the recap's own exact "Completed N tasks" count; the recap count (below) is the one trustworthy number.

**The `rerun` verb (`internal/config/rerunresolve.go`, `internal/session/main.go`).** `ResolveRerun(args, cfg)` is a pure function implementing precedence: explicit CLI playbook wins over `LastTarget`; CLI `--tags`/`--skip-tags`/`-l` win over that playbook's own history; any other CLI passthrough arg replaces history's `Rest` outright. `ok` is false only when no playbook can be determined at all (no explicit one, no `LastTarget`). A `rerun` invocation records nothing into `state.toml` until the dialog is actually confirmed (via the same `requestRerun`/`submitRerun` path every later rerun uses) — a Ctrl-C before that leaves no trace.

**Test fixtures (`testdata/`).** `basic.yml` (sequential + sleep, live-streaming demo), `outcomes.yml` (all four original outcome buckets incl. ignored failure), `multihost.yml` + inventory (per-host divergence), `hostnames.yml` + inventory (varied-length hostnames for the shrink algorithm, plus one unreachable host for `v2_runner_on_unreachable` — run with `--forks 1` for an observable grey-to-lit transition), `free-strategy.yml` (`strategy: free`, one host deliberately slower on its first task so the other visibly races ahead onto later tasks — run with `-i multihost-inventory.ini`, `design-docs/StrategyFree.md`), `diff.yml` (diff-mode fixture), `vault.yml`/`vault-nested.yml`/`vault-password.txt` (vault verb fixtures).

## Recap (`internal/session/recap.go`, `design-docs/Recap.md`)

Once a run finishes, the tree grows a "Summary" section below the trailing status rows: one line per host, right-aligned `ok=N skipped=N changed=N unreachable=N failed=N warnings=N` counts (matching ansible-playbook's own recap line, plus a tangsible-specific `warnings` field — a task can be both, e.g. Changed *and* warned, so it isn't one more mutually-exclusive outcome bucket). Above the host lines, a plain-prose narrative sentence (elapsed time, task/host counts, failed/unreachable call-outs, one clause per optional fact so any can be omitted without punctuation cleanup) answers "what actually happened" faster than scanning six numbers per host.

Expansion is three levels deep, reusing the tree's own Enter-to-expand mechanism rather than a new widget: host row → non-empty categories only (a category with zero tasks never renders) → individual task rows, each showing the same detail the live tree's expanded host rows already show, or the task's own warning text for the `warnings` category. Built entirely from data `PlaybookState` already tracks — a scan over `Plays`/`Tasks`/`Hosts` per host, cheap at this project's ~10-host target scale. Deliberately excludes `rescued`/`ignored`: neither is derivable per-task from the jsonl event stream this app consumes (a rescued task is an ordinary `v2_runner_on_ok`; `ignore_errors` never appears, per the same gap Aggregation notes above). Deliberately ignores the tree's active filter — unlike the long chronological tree above it, the recap is already a short complete index of the whole run.

Colors are entirely reused, not reinvented: `recapCategoryColor` maps straight onto `uikit.ColorTag`'s five outcome colors plus a warning color; zero-count fields gray out via the same convention the collapsed-row summary mode uses, since a live experiment showed six always-colored segments reading as one uniform "wall of color" otherwise.

## `--check` mode chrome (`internal/uikit/tui_style.go`, `internal/session/livesession_rebuild.go`, `design-docs/CheckMode.md`)

`ansible-playbook --check` needs no data-layer changes — it's a plain passthrough flag and the jsonl shape is identical either way — but a `--check` session otherwise looks indistinguishable from a real one, which is actively misleading: modules with no check-mode support (`command`/`shell`/`script`) get silently skipped by Ansible core itself rather than predicting an outcome, so a task that would fail or change for real can render as plain Skipped. Deliberately does *not* try to flag that case itself — that's real `ansible-playbook --check` behavior, not something to paper over.

Detected once, at session start (`config.HasCheckFlag`, an exact-token match against passthrough args — same heuristic gap as `-tfoo`) and never re-derived: a rerun always carries the original invocation's passthrough args forward unedited, so check-mode is fixed for the session's whole lifetime, live/rerun/revisited alike — there's no re-run-dialog field to toggle it. When set, every chrome surface (top/bottom bars, output drill-down bars, two-pane divider) switches from the ordinary navy to `uikit.CheckBarStyle` (white on olive — the next unused base-16 slot after revisit's purple and diff mode's fuchsia, below), and appends a plain-text `[CHECK MODE - dry run]` note to the bottom bar regardless of color support, since chrome color alone doesn't reach a `NO_COLOR`/monochrome terminal. Takes lower precedence than revisit's purple: a revisited `--check` run still shows purple, since "this isn't live" is judged the higher-priority signal.

## Revisit (`internal/revisit/`, `tangsible revisit`, `design-docs/Revisit.md`)

`tangsible revisit [<playbook>] [args...]` browses previous generations (via the run logs above) and reopens one as a frozen tree. `internal/revisit/revisitresolve.go`'s `ResolveRevisitEntries` flattens `state.toml`'s `Invocations` (each carrying its `RunID`) into a filtered, newest-first list with zero filesystem I/O; `PruneMissingRunLogs` does the stat/cleanup separately, self-healing if `.jsonl` files vanish externally.

Reopening an entry (`OpenRevisitEntry`) replays the saved `.jsonl` through the same `ScanEvents` line scanner used for a live pipe, into a fresh `PlaybookState`, then hands it to an ordinary `NewLiveTUI` call already frozen (`processDone` pre-true, `exitCode`/`HadUnreachable` seeded from the manifest, not re-derived). Everything downstream — tree, filtering, two-pane drill-down — is unchanged, since none of it cares whether data arrived live or replayed.

**Import-cycle avoidance.** `package revisit` can't import `internal/session` (where `NewLiveTUI` lives) to call it directly, nor can `NewLiveTUI` move without a much larger refactor. `NewLiveTUIFunc` in `revisit.go` mirrors `NewLiveTUI`'s exact signature; `session.Main` passes its own `NewLiveTUI` as the argument to `RunRevisitVerb` — Go's assignability rules need no adapter since the underlying function types match. Same callback-injection shape `requestRerun`/`revisitReturn` already use one level down (see Rerun above).

Two sequential `tview.Application`s, not one folded page: `RunRevisitListTUI` (flat, `TreeList`-based, same shape as `tangsible hosts`) blocks until Enter/`r` (rerun)/quit, then `OpenRevisitEntry` runs a second, real `NewLiveTUI` Application. `RunRevisitVerb` loops between them, re-pruning/re-resolving on every return so a rerun started mid-session shows up next time. Re-running from within a revisited session un-freezes it — chrome reverts from purple to navy, Esc stops meaning "back to the list," and the new generation gets its own independent `RunID`, revisitable later. A role-originated entry's replayed events still point at the original (already-deleted) stub, so its historical "Task definition" tab stays empty — accepted gap; a fresh stub is still regenerated eagerly so a *rerun's* own new tasks get one (see Role below).

## Diff mode — comparing two runs (`internal/diff/`, `d` key, `design-docs/Diff.md`)

`d` (tree view only, `processDone`-gated like `r`) compares the current `PlaybookState` against a past one. **This is unrelated to the single-run Diff tab** covered under Architecture above — same word, different feature. Diff mode reuses revisit's own `RunRevisitListTUI` picker, just fed `ResolveDiffCandidates` (`internal/diff/diffresolve.go`) instead of `ResolveRevisitEntries` — filtered to exact playbook/role **and** exact tag/host set equality (`CsvSetEqual`, not a looser overlap check: a partial match would compare runs that didn't execute the same tasks).

`internal/diff/diffmatch.go` is pure, no I/O: `AlignPlays`/`AlignTasks` use `difflib.NewMatcher(...).GetOpCodes()` (already a dependency, reused rather than a custom LCS) to align two ordered name sequences — matched by **name**, not `task.Path`, because editing the playbook between debug runs shifts line numbers for everything below the edit, and a role session's `task.Path` is a fresh stub path every single run regardless of real changes. A same-position `'r'` opcode is deliberately *not* forced into a pairing — correctness over cleverness. `TaskDiffers`/`HostDiffers` compare outcome plus output (stdout/msg, stderr, warnings) per host present on **both** sides; a host on only one side is skipped entirely (host-set differences don't count).

`d`'s whole flow (`RunDiffFlow`) runs inside `app.Suspend` — the same primitive the output view's `e` ($EDITOR) uses (see Template below) — so the original live tree resumes exactly where it left off once the candidate list and diff tree both return. `RunDiffTreeTUI` is its own standalone `tview.Application`, not another `NewLiveTUI`: the data model here is pairs of tasks, which would fight `NewLiveTUI`'s single-state plumbing. Rows are colored normally (no separate diff palette) with underline for a changed matched task/host and strikethrough+italic for old-only (plain `(old only)`/`(new only)` text markers too, since strikethrough alone is invisible over some terminals, e.g. mosh). Chrome uses a fourth fixed color, fuchsia, distinct from navy (live), purple (revisit), and olive (check mode).

Drill-down renders a `difflib.UnifiedDiff` per tab (Task/Output/Task definition/Details) between the two runs' plain-text content — Docs shown once undiffed, the per-run Diff tab dropped entirely. An unmatched task falls back to that one run's ordinary single-run tabs, prefixed with a note explaining *why* nothing is being compared (absence is itself the difference — e.g. a handler only notified in one run).

## Role (`tangsible role <role>`, `internal/role/role.go`, `design-docs/Tangsible role.md`)

`WriteRoleStub` generates a minimal `hosts: all\nroles:\n  - <role>` stub — roles are host-agnostic, so the real target is narrowed the normal way via `-l`/`-i` passthrough, not baked into the stub. The stub is written to `.tangsible-role-<role>.yml` **in the current working directory**, never a system temp dir — this matters beyond tidiness: `internal/source`'s task-source lookup finds a task's own source by walking the *playbook's own* directory tree, never by tracing `roles:`/`include_role` references, so a stub in `/tmp` would start that walk from an empty directory and silently blank the "Task definition" section for every role run. Dot-prefixed so it doesn't clutter a listing; should be `.gitignore`'d (not automated, same restraint `state.toml` gets).

`RoleFoundNearby` is a best-effort `./roles/<role>` check, purely informational (warns to stderr, doesn't gate anything) — it deliberately doesn't also search `$ANSIBLE_ROLES_PATH`, since the stub always lives in the cwd, so only a role reachable from *there* can ever have its source found anyway. If the role can't be found this way, the stub is still generated and handed to `ansible-playbook` regardless — same "omit rather than fail" fallback the drill-down already has for any other source-lookup miss.

`StartRoleSession` writes the stub and returns a `cleanup func()` that removes it — shared by `role` itself and by `rerun` resolving to a role. A mid-session re-run (`r` key) reuses the *same* stub, generated once per process, not regenerated per generation.

## Template (`tangsible template <path> [<hostSpec>]`, `internal/template/template.go`, `design-docs/Tangsible template.md`)

A standalone Jinja2 debugger verb — a single-view program with no tree/live-jsonl pipeline behind it, since each render is exactly one synchronous `ansible-playbook` invocation. Only `q`/Ctrl-C quit; Esc is deliberately inert here (it used to double as quit, but that made it too easy to close the whole program by reflex while browsing tabs).

**Host/group resolution.** `hostSpec` (`ParseTemplateArgs`) is a comma-separated list of tokens (`SplitHostTokens`); each resolves as a group name first — including the reserved `all` group, which needs no special-casing at all since every inventory already has one (`inventory.IsGroup`/`GroupHosts`, sourced from `inventory.ListInventoryRaw`, not the already-flattened `ListInventoryHosts`) — falling back to a literal hostname, or a usage error if neither (`resolveHostTokens`). Mixing hosts/groups/`all` is a harmless deduplicated union. No `hostSpec` at all falls back to the first inventory host, deterministically — not "run against `hosts: all` and take whoever reports first," which would actually execute (and write output on) every host in the inventory just to show one result. If resolution ends up with more hosts than `config.TemplateHostsMax` (`.tangsible/config.toml`'s `general.template_hosts_max`, default 10), `ConfirmManyHosts` prompts in the terminal's own cooked mode (before the TUI exists) — anything but y/yes exits immediately.

**The stub (`WriteTemplateStub`).** Always targets `hosts: all`; the actual host is narrowed per-render via `--limit`, not baked into the stub — this is what lets one stub (and its single shared `dest:` output path) survive unchanged across every host switch and every additional host tab in a session (an earlier version regenerated `hosts: <hostname>` per switch, which meant `h` only changed which host's JSON event `RenderTemplate` looked for while the play itself kept targeting the original host). The template task always runs `delegate_to: localhost`, confirmed live as a real bug otherwise: without it the rendered file lands on the *target* host, never locally where Tangsible can read it back — `delegate_to` only changes *where* the module executes, not whose variables are in scope, so `inventory_hostname`/host_vars/group_vars still resolve to the play's targeted host.

**Role-owned templates.** If the path matches `roles/<name>/templates/...` (the same pattern the drill-down's own source lookup already uses for tasks/handlers), `RoleVarsFiles` adds `defaults/main.yml`/`vars/main.yml` via `vars_files:`. Deliberately *not* `roles: [name]` — that would actually execute the role's `tasks/main.yml` as a side effect, which a read-only template preview must never do.

**Multi-host tabs and rendering.** One tab per resolved host (titled with that host's own name), plus one shared, host-independent "Source" tab — the header above them shows only the template's own path, not a host (redundant now that each host has its own tab title). `RenderTemplate` scans one host's own render synchronously; a task failure (typically a Jinja traceback) is shown as the result, not treated as a hard error — that's the expected, normal outcome this tool exists to surface. Multiple hosts render sequentially (one `ansible-playbook` invocation after another, each tab updating as its own finishes) rather than concurrently, both as the simplest option at this app's own ~10-host target scale and because the single shared `dest:` file (above) would otherwise race under concurrent invocations. Every render this view runs — the initial load, `e`'s reprocess-every-host, `h`'s single-host reprocess — is serialized through a `rendering`/`pendingRerenderAll` guard: a render requested while one's already in flight is never dropped, just coalesced into one trailing full reprocess once the current one finishes.

**Editing.** `e` suspends the screen (`tcell.Screen.Suspend`/`Resume` — this codebase's first real use of it) to hand the terminal to `$VISUAL`/`$EDITOR`/`vi` on the real source file, then unconditionally reprocesses **every open host tab** on exit regardless of whether anything was saved, matching `git commit`/`crontab -e` — every tab is stale, not just whichever was active, since the template file itself changed.

**Changing hosts.** `h` opens a single-field dialog targeting whichever host tab was last active (remembered even while the host-independent Source tab is the current one) — renames that one tab and reprocesses just it, or switches to an already-open tab rather than duplicating it. Autocompletes against literal hostnames only, not group names (`uikit.MatchSingleValue`) — unlike the command line's own `hostSpec`, this dialog only ever swaps in one literal host, so a group here wouldn't do anything useful; confirmed live before scoping it down, when a group suggestion here just produced "no result reported for host `<group>`" once picked.

## Autocomplete (`internal/session/autocomplete.go`, `design-docs/Autocomplete.md`)

Covers the re-run dialog's `tagsField`/`skipTagsField`/`hostsField` (comma-separated) and `playField` (single-value, sourced from `ListTopLevelPlayNames` — see Start with a play above), built on `tview.InputField`'s own `SetAutocompleteFunc`/`SetAutocompletedFunc` rather than a hand-rolled widget — unlike `TreeList`, the built-in drop-down already has the right keyboard model. Suggestions are purely advisory: any typed value is always valid to submit, matched or not.

**Matching (pure, unit-tested).** The core matcher (`uikit.FilteredMatch`) lives in `internal/uikit`, not `internal/session`, specifically so the `template` Verb's own single-value host-swap field (above) can share it without an import cycle — `internal/session/autocomplete.go`'s `matchToken`/`matchTaskName` are now thin wrappers around `uikit.FilteredMatch`/`uikit.MatchSingleValue`. Case-insensitive prefix match; substring match as fallback if empty; capped at `uikit.AutocompleteMaxEntries` (8). For the multi-value fields, `lastToken` scopes completion to the substring after the last comma — a hard constraint of `tview`'s callback API (full text only, no cursor position), so editing an earlier token gets no suggestions, and candidates already present earlier in the field are excluded. `replaceLastToken` replaces only that trailing token (not `tview`'s own whole-field default) and appends `", "`. `playField` (and `template`'s own host-swap field) share `uikit.MatchSingleValue` instead — no token/exclusion concept, matching the whole field, and additionally returns nil once the text already exactly equals a candidate, since without that check the leftover text from a pick would keep self-matching and permanently steal Enter away from submit.

**Sources.** The re-run dialog's own `hostsField` combines two independent candidate lists: live `PlaybookState.AllHosts` (already sorted/deduplicated, grows as the run discovers hosts) plus `knownGroups` — every inventory group name (`inventory.ListInventoryRaw`/`GroupNames`), fetched once at session startup the same "has to work before any generation has run" way `knownTags`/`knownPlayNames` are (main.go, and `internal/revisit/revisit.go`'s own mirrored fetch for a revisited session) — best-effort, since `--limit` already accepts a hand-typed group name regardless of what autocomplete offers. Tags come from a static YAML scan (`internal/source`'s `BuildTaskSourceIndex`) since Ansible's jsonl callback never reports a task's `tags` — unioned with the five reserved names (`always`/`never`/`tagged`/`untagged`/`all`). Play names come from `ListTopLevelPlayNames`, also a static scan, for the same startup-ordering reason. The `template` Verb's own host-swap field (above) has no live tree at all and is deliberately hosts-only (no groups — see its own doc comment for why), sourcing candidates from a single `inventory.ListInventoryRaw`/`FlattenInventoryHosts` call made once at startup.

**Enter/Escape conflict.** `SetInputCapture` normally swallows Enter (submit) and Escape (close dialog) before they'd reach the focused field's own drop-down handling. Fixed by recomputing whether the drop-down is currently open from the same matching functions on every keypress (avoiding a stale mirrored bool across `Blur()`), plus a narrow dismissed-flag so a second Escape can still close the dialog once the drop-down itself is already gone.

## Show file contents (`internal/session/fetchfile.go`, `design-docs/ShowFileContents.md`)

Backs the drill-down's File tab: a clean, fully-copyable view of a file a task modified — as opposed to the (single-run) Diff tab, which only shows Ansible's own diff (partial for line-oriented modules like `lineinfile`, and not clean to `y`-copy since it carries diff markup).

**Remote files.** `fetchRemoteFileContents` runs a throwaway `ansible.builtin.fetch` stub playbook, reusing the original invocation's exact passthrough args so it sees the same inventory/connection/vault context. The remote path is written into the stub via `quoteYAMLString` — a deliberately minimal YAML double-quote encoder (Go's `%q` is a superset-compatible escaping for the common case) rather than pulling in a full YAML encoder just to embed one scalar path safely into generated playbook text. Guarded by `config.HasInteractiveCredentialFlag`: `--ask-become-pass`/`--ask-vault-pass` aren't cached to disk, and replaying them verbatim on this second process — spawned *while the TUI already owns the terminal* — would trigger a bootstrap prompt fighting the raw terminal, so the fetch is skipped outright rather than attempted (this is a specific instance of the broader "interactive input after the TUI starts" limitation under Current scope constraints below).

**Local files.** `readLocalFileContents` reads straight off disk — no Ansible invocation — for control-host actions and for `delegate_to: localhost` tasks (detected via `_ansible_delegated_vars.ansible_host == "localhost"`, since there's no literal `delegate_to` field on a result).

**Binary detection.** `isBinaryContent` checks for a NUL byte in the first 8000 bytes (git's own long-standing heuristic). Binary content, and every failure mode (unreachable host, permission denied, missing file, interactive-credential guard, non-zero exit) all resolve to the same outcome: the File tab simply stays hidden — never a placeholder or visible error, unlike Docs/Resolved's "Could not fetch: ..." convention.

**Caching.** Fetched once per (task, host) per drill-down visit; cleared on every drill-down close and on each new rerun generation — bounding staleness without refetching on every tab switch.

## Resolved values (`internal/session/resolved.go`, `design-docs/Drilldown, Resolved Values.md`)

Backs the drill-down's Resolved tab: re-renders a task's key fields with variables filled in, by generating a real `ansible.builtin.template` task against the task's own source text (`resolveTaskValues`) rather than attempting any Jinja evaluation in Go — the same "let Ansible do the actual work" principle `Purpose.md` applies to the whole event pipeline. `wrapJinjaDefaults`/`jinjaStringLiteral` handle quoting so the generated task is valid YAML regardless of what the original expression contains. Same async-fetch-on-open, `resolveCache`-keyed, and interactive-credential-guarded pattern as Show file contents above.

## Host / hosts (`internal/host/host.go`, `design-docs/HostVerb.md`)

`tangsible host <hostname>` and `tangsible hosts` are standalone verbs — own `tview.Application`, no jsonl tree, no `NewLiveTUI`, same precedent as `template`. `hosts` adds a `TreeList` host picker in front of the identical detail view, rebuilt fresh per selection rather than cached (cheap enough at this project's ~10-host target scale); the only behavioral difference from `host <name>` is that Esc returns to the list instead of being inert.

The detail view is five tabs, all fetched concurrently on their own goroutines starting the instant the view opens (not lazily per tab-open), each populating its `TextView` via `app.QueueUpdateDraw` once done: **Summary** (live gathered facts), **Groups** (full transitive inventory chain), **Plays** (which plays/tasks would actually run), **host_vars** (raw file contents), **Everything known** (`ansible-inventory --host <hostname>` verbatim).

**`internal/inventory`** exists purely to break a cycle: `host.go` and `template.go` both needed `ansible-inventory --list` plus the group-tree flattening logic, so that one shared piece was pulled into its own package rather than merging the two much larger files. `FlattenInventoryHosts` walks the group tree from `all` since `_meta.hostvars` silently omits any host with no vars of its own. `HostGroupChain` (`host.go`) builds the *reverse* index this package doesn't provide: the JSON's `children` pointers only ever go parent→child, so showing a host's ancestor chain means building a child→parents map first, then BFS-ing outward from direct membership. `all`'s own entry deliberately gets no `(via ...)` annotation — technically true of any child but never informative, since every host reaches `all` regardless of path.

**Plays tab** reuses `internal/runner/progress.go`'s `--list-tasks --list-hosts` probe narrowed via `--limit <hostname>` (both flags are required together — `--list-tasks` alone ignores `--limit`), inheriting its caveat that a dynamic `include_tasks:` won't expand.

**Summary tab gotcha:** originally used `gather_facts: true`; under `gathering = smart` with any warm fact cache for the host, Ansible silently skips the implicit gather task with zero jsonl output at all. Fixed by an explicit `ansible.builtin.setup:` task instead, which always fires a real event — but that alone meant paying for a live connection even with a fresh cache. `FetchHostSummary` recovers the fast path explicitly: it runs `ansible-inventory --host` first and checks for `ansible_architecture` (part of the default gather_subset) as a cache-hit canary, since `--host` merges cached facts into its output too (confirmed empirically) and drops them once `fact_caching_timeout` expires — a hit is shown with a `(from fact cache)` note, a miss falls through to the live `setup:` run.

## Vault (`tangsible vault <filename>`, `design-docs/Vault.md`)

Edits individually vault-encrypted variables as if editing plain text — real `ansible-vault` only encrypts/decrypts whole files, so the standard workaround for touching one secret (`encrypt_string`, paste the block back in by hand, or maintain a second vars file that references an all-encrypted one) is what this verb replaces. It decrypts every top-level `!vault` value into a plaintext view, opens `$EDITOR`, and on close re-encrypts only what actually changed — never touches `tview`, unlike every other verb.

**Three packages, dependency order.** `internal/vaultcrypto` is a native Go reimplementation of Vault's AES256-CTR+HMAC format (`Encrypt`/`Decrypt`) — tractable to reimplement directly (unlike Ansible's own execution engine, which `Purpose.md` deliberately avoids), and avoids shelling out per secret. Validated both directions against a real `ansible-vault` binary in tests (skipped if the binary's missing, not just a one-off manual check). `internal/vaultfile` holds the actual logic: `BuildDecryptedView` (source → plaintext view via a `yaml.Node` decode/mutate/encode) and `Reassemble` (the per-key diff plus reconstruction), plus annotate/strip helpers for the reopen loop. `internal/vault` is the verb itself — arg parsing, password resolution, the editor loop.

**The salt problem.** AES-CTR uses a random salt per encryption, so blindly "decrypt all → edit → re-encrypt all" would change every secret's ciphertext on every save, not just the touched ones. A plain key-set comparison (unchanged/changed/new/removed — only top-level keys are in scope) decides what actually needs re-encrypting, rather than a structural merge, since the real use case is one or two secrets changing in an otherwise stable file.

**Diffs stay minimal, the hard way.** The first shipped `Reassemble` re-encoded the whole `yaml.Node` tree on save, reusing only the original node for an unedited key. That kept ciphertext *values* correct but not formatting: `yaml.v3`'s encoder silently clamps `SetIndent` to `[2,9]`, while real `ansible-vault`'s `encrypt_string` output indents 10 spaces — so every untouched vaulted block got reformatted (10→2 spaces) on any save, making `git diff` show every secret as changed even though none were. Fixed by abandoning re-encoding entirely: `keyContentSpans` splices raw source-text spans instead — an unedited key's exact original bytes are reused verbatim; only a genuinely changed/new value gets hand-formatted text, at the source file's own detected indent (deliberately *not* clamped to `[2,9]` since it isn't going through `SetIndent`).

**Never silently write something wrong.** Three cases reject a save outright: a previously-vaulted key resolving to a non-string, a hand-typed `!vault` tag (the view only ever contains plain values), or invalid YAML. Following `visudo`/`crontab -e`: annotate the offending line inline and reopen, so edits are never lost. **The way out is an explicit fix-or-revert prompt, not Ctrl-C** — confirmed via a minimal repro that a raw-mode editor (vim) disables the whole terminal's `ISIG` flag, so no signal is ever generated for *any* attached process, Tangsible included, while it's open; the prompt works because it runs after the editor hands the terminal back, in Tangsible's own cooked-mode terminal.

**No secrets on the command line.** Password resolution mirrors `ansible-vault`'s own flags (`--vault-password-file`/`--ask-vault-pass`, mutually exclusive) with added precedence: flag → `$ANSIBLE_VAULT_PASSWORD_FILE` → the project's `ansible.cfg` (`[defaults] vault_password_file`, located the same way `ansible` itself does) → interactive no-echo prompt as a last resort (a deliberate divergence from real `ansible-vault`, acceptable since this verb has no CI/batch use case). The decrypted plaintext lives in a 0700 scratch dir (not a bare 0600 file in shared `/tmp`) so an editor's own spill files (`.swp`, backups) get swept up by `os.RemoveAll` too; `SIGTERM`/`SIGHUP` are trapped alongside `SIGINT` so the scratch dir isn't left behind on an unhandled signal.

## Version (`tangsible version`, `internal/session/version.go`)

No TTY, no inventory, no config — runs before any of that setup, same posture as `vault`. `RunVersion` prints build stamps (version/commit/date, injected via `-ldflags -X` at release, falling back to `debug.ReadBuildInfo()`'s embedded VCS metadata for a plain `go build`), Go/OS info, then shells out to `ansible-playbook --version` and reports whether `runner.ResolveCallbackPluginDir` actually finds the bundled callback plugin (reusing that function's own error message, which already names every location tried, rather than inventing a second diagnostic that could drift from it) — this replaced an earlier `ansible-galaxy collection list ansible.posix` check once the bundled callback plugin (Data source above) dropped the `ansible.posix` dependency entirely; there's no longer a separate collection to version-check, and the plugin's own resolution is now the one thing that can actually go wrong. Every external lookup is best-effort — a missing binary/plugin prints a note, never a nonzero exit — since the point is a copy-pasteable environment block for a bug report, not a preflight check.

## Notifications (`internal/uikit/notify.go`, `design-docs/Notifications.md`)

Playbook runs are often long enough that the user isn't watching. `notify_playbook_finished`/`notify_task_failed` (`.tangsible/config.toml`, see Commands) each independently pick `off`/`osc9`/`osc777`/`osc99`/`bell` (default off for both); `SendNotification` builds the matching escape sequence (OSC 9 body-only; OSC 777/Kitty's OSC 99 title+body; BEL carries no text). `notify_task_failed_max` (default 5) caps per-run failure spam, reset on every rerun; the limit's own final notification states how many further failures were suppressed, then goes silent for the rest of that generation. `PlaybookFinishedBody` treats the benign-unreachable case as "finished," not failure, matching Exit codes above; it deliberately does *not* fire on a direct, immediate result of user interaction (Ctrl-C, a pre-flight-gate failure) — those are actions the user just took, not news to be pushed at them. Same `ignore_errors` gap as Aggregation above: `notify_task_failed` fires for every recorded failure, ignored or not, since the jsonl callback can't tell the difference — tracked to revisit once the deferred own-callback-plugin fork ships and can carry that field.

## In-tab search (`design-docs/Search.md`)

`/` opens a "find text in the currently active tab" prompt in every tab-bearing view (main drill-down, the diff view, `tangsible hosts`/`host`, `tangsible template`) — scoped to the one tab on screen, never cross-tab or cross-run.

**Core mechanism (`internal/uikit/search.go`)** is built on `TextView`'s own region/highlight API. `TextSearch` reads a tab's plain text via `GetText(true)`, finds every case-insensitive match's byte span, and re-renders the tab wrapping each match in its own colored region tag (black-on-yellow, black-on-orange for the current match). Deliberate simplification: this redraws from *plain* text, so a tab's own supplementary coloring (Diff's line colors, Task's YAML key-highlighting) isn't shown while a search is active — reinserting match tags into already-tagged text would need a hand-rolled tview-tag parser. `Stop()` restores the view's original tagged text and clears highlight state, called whenever a search is cleared.

**Two wiring shapes**, matching how each surface builds its tabs: `internal/session/livesession_output.go`/`internal/diff/diff.go` rebuild every tab's `TextView` from scratch on each navigation, so search state is wired inline with `s.search.clear()` at the top of that rebuild; `internal/host/host.go`/`internal/template/template.go` build their `TabbedPane` once and populate long-lived `TextView`s later via `SetText`, so they share `internal/uikit/tabsearchbar.go`'s `TabSearchBar` component, with `ClearForView(view)` called right before each individual `SetText` so an async fetch landing on an inactive tab doesn't clear a still-valid search on the active one.

**A real tview dispatch bug**, not just app-level state: focusing a nested `InputField` three `Pages`/`Flex` layers deep doesn't receive forwarded keystrokes via tview's normal path, even though every ancestor correctly reports `HasFocus()`. Worked around by calling `tabSearchInput.InputHandler()` directly from `SetInputCapture` while composing, rather than returning the event for normal dispatch (the same workaround style already used for `TreeList`).

**Follow-up fixes worth knowing if touching this again:** switching tabs while a search is active must clear it (`TabbedPane.SetChangedFunc`, covers keyboard *and* mouse tab-switching); `TextView.Highlight()` swaps fg/bg *on top of* whatever color tag a region already carries, so the current-match color must be written pre-swapped into the tag rather than relying on `Highlight()`'s automatic inversion alone; `InputField.SetLabelColor` only sets foreground, so the composing prompt's label needs `SetLabelStyle` with both channels set to avoid black-on-black.

## Copy to clipboard (`design-docs/CopyToClipboard.md`)

`y` copies the currently active tab's plain-text content (same `GetText(true)` source in-tab search reads) to the system clipboard, in every tab-bearing view — main drill-down, the diff view, `tangsible hosts`/`host`, `tangsible template`.

**`internal/uikit/clipboard.go`** builds and sends an OSC 52 escape sequence (`ESC ] 52 ; c ; <base64> ESC \`) written directly to `os.Stdout`, not through `tcell.Screen.SetClipboard` — that path only fires when the active terminfo entry is marked `XTermLike`, which tmux's and screen's own terminfo entries deliberately aren't (confirmed against `tcell`'s terminfo database), making it a silent no-op for exactly this feature's motivating case (tmux). Writing straight to `os.Stdout` is safe against a concurrent screen redraw because every caller reaches it from inside `SetInputCapture`, which — like every `Draw()` tview itself triggers — runs on the application's single event-loop goroutine (the same assumption `internal/playbook`'s `PlaybookState.Apply` already relies on). Under `$TMUX`, the sequence is wrapped in tmux's own DCS passthrough envelope (`ESC P tmux ; <seq, ESC doubled> ESC \`) first — the standard workaround real OSC 52 tools use (vim-oscyank, neovim's built-in provider), since tmux's own OSC 52 interception (`set-clipboard`) has historically been inconsistent, while passthrough reaches the outer terminal directly — at the cost of needing `set -g allow-passthrough on` in tmux ≥ 3.3, the one piece of setup this doesn't automate away. Payloads whose base64 encoding exceeds `osc52MaxEncoded` (xterm's own long-standing ~100KB default) fail with an error rather than sending a truncated sequence some terminals would silently drop.

**Feedback** reuses each view's existing hint/footer bar rather than a new toast mechanism: `CopyActiveTabStatus` formats a ready-to-show status line, set via `TabSearchBar.ShowMessage` (`host.go`/`template.go`) or the same inline `SetText` `internal/session/livesession_output.go`/`internal/diff/diff.go` already use for search's own "match N of Y" status. It has no timer and no lifecycle of its own — it's superseded exactly when a real search status would be: `TabSearchBar.Clear()` unconditionally resets the footer, and `clear()` in the two rebuild-from-scratch views got the same change, since both already run on every tab switch/host-task navigation/view-close that should also retire a stale "copied" message.

## Current scope constraints (from `design-docs/Purpose.md`, `README.md`)

These are explicit decisions, not accidental omissions:

- `--ask-become-pass`/`--ask-vault-pass` need no implementation — both prompt during `ansible-playbook`'s bootstrap, strictly before any jsonl event fires, i.e. before the TUI is even constructed, so the prompt reaches the real terminal in its normal (non-raw) state for free.
- **Genuinely unsupported: interactive input requested after the TUI already owns the terminal.** A bare `pause:` (no duration) does *not* hang — Ansible detects non-interactive stdin and skips waiting, completing with a warning visible only in the drill-down's full-JSON fallback. `--step` is worse: it crashes outright (`EOFError`, exit 250) since its confirmation prompt fires from a bare Python `input()` with no non-interactive detection, right at the same event that opens the pre-flight gate. `tcell.Screen.Suspend()`/`Resume()` (proven out by `template`'s `e`-to-edit flow and diff mode's picker flow, both above) is the right primitive if a mid-run prompt is ever supported — still unexplored beyond that for genuinely *mid-run* interactive input specifically.
- **`strategy: free` is supported** (`design-docs/StrategyFree.md`) — Ansible's jsonl callback never emits `v2_playbook_on_task_start` under `free` (only per-host `v2_runner_on_start`/`v2_runner_on_ok`, no shared task-start moment), so the old single-`currentTask`-pointer data model stayed permanently `nil` and every result was silently dropped; `findOrCreateTask`'s ID-based resolution (Aggregation, above) fixes this for both strategies at once, and `IncompleteTasks()` correctly tracks more than one simultaneously-active task where `strategy: free` genuinely has one. `testdata/free-strategy.yml` is the live-verified fixture. Known, accepted gap: a *globally*-configured `strategy = free` (`ansible.cfg`'s `[defaults]`, or `$ANSIBLE_STRATEGY`, with no per-play `strategy:` key in the YAML) isn't detected by the progress-fill skeleton's own static per-play scan (`source.FreeStrategyPlayNames`) — that play's progress fill just keeps today's pre-existing imprecise behavior, not a regression. Separately, and **not a tangsible issue at all** (confirmed by reproducing with a plain `ansible-playbook` invocation, no tangsible involved): ansible-core's own `free` strategy plugin hard-refuses any module whose action plugin sets `BYPASS_HOST_LOOP = True` (stock install: just `pause`/`add_host`) — see `design-docs/StrategyFree.md`'s own note for the fix (playbook-side, not tangsible-side).
- **Execution environments / ansible-runner** are not supported — Tangsible always shells out to a locally-installed `ansible-playbook` directly.
- Ctrl-C behaves the same as running `ansible-playbook` directly — implemented (see Architecture's Ctrl-C/`q` section above).
- Target scale is ~10 hosts, not hundreds/thousands — an interactive dev tool, not a fleet-management tool. This shapes several concrete decisions above: eager-not-lazy per-selection fetches in `host`, unbounded but rarely-exercised host-column shrinking, no pagination anywhere.
- Only a limited subset of `ansible-playbook`'s CLI surface is exposed; expand only as needed.
- Own callback plugin (a GPL fork of `ansible.posix.jsonl`, bundled to gain fields like `ignore_errors` the stock callback never emits) is an approved-but-deferred idea, not yet implemented — see the two `ignore_errors` gaps called out above (Aggregation, Notifications) for the concrete motivating cases.
