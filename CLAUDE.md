# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Tangsible is a TUI wrapper for `ansible-playbook`, aimed at interactive use (e.g. during development). The problem it solves and the product decisions behind it are documented in `Purpose.md` — read that first for the "why" before making design choices; this file only covers the "how".

The TUI (built with `tview`) is live: it comes up immediately and updates incrementally as jsonl events arrive, while `ansible-playbook` is still running — arrow-key/j-k navigation (no wraparound at the ends), Enter/Space to expand/collapse a task's host rows, cursor Right/Left to expand/collapse a task directly, `E`/`C` to expand/collapse every task at once, `n`/`p` to hop to the next/previous task (preserving the selected host across tasks where possible), Home/End/`'G'`/Ctrl-A/Ctrl-E to jump to the first/last row, `q`/Ctrl-C to quit (or, while the process is still running, to interrupt it — see below). The view auto-follows the newest row while nothing has been navigated away from; disengages the moment the user scrolls (including via End/`'G'`/Ctrl-E, which are deliberately plain navigation), and only `'F'` re-engages it. Full shortcut reference: `Keyboard-shortcuts.md`. Play rows are white and bold; task rows are a plain regular gray. A task's collapsed row shows every host discovered so far this run, right-aligned, each individually colored by its outcome for that task (green/yellow/cyan/red/maroon for OK/Changed/Skipped/Failed/Unreachable) or grey if it hasn't reported for that specific task yet — not aggregate counts. The row under the cursor renders differently from a flat highlight: black bold text throughout, a light gray background on the title, and each hostname's outcome color as a background instead of a foreground, with adjacent hostnames' colors blended together in the cell between them. An expanded host row shows its outcome plus a short contextual detail where one's defined — OK shows the single line of output verbatim or a line count; Skipped shows its `skip_reason`/`false_condition`. Expanding a task and pressing Enter/Space on one of its host rows opens a full-screen view of that host's complete result for that task (one of MSG/STDOUT plus STDERR, plus the full result as JSON); Escape or Enter closes it, leaving the tree's cursor on whatever (task, host) was last shown there. While that view is open, cursor Left/Right switch to the previous/next host for the same task, and `n`/`p` switch to the previous/next task for the same host. The top and bottom bars are white-on-navy. The top bar ticks a spinner + total elapsed time so it's visibly obvious the app hasn't hung, freezing once the run finishes; whichever task is currently active also shows that same spinner frame next to its title. Because it opens a real terminal UI, running it requires an actual TTY (not a piped/headless shell).

## Commands

```
go build ./...                                          # build
go vet ./...                                             # lint
go run . run [<playbook.yml>] [ansible-playbook args...] # run
```

The leading verb is mandatory (`resolve.go`'s `parseVerb`) — `run` as
above, or `rerun` (see the Rerun section below for the full feature).

Try it against the bundled fixtures, e.g.:
```
go run . run testdata/outcomes.yml -i localhost,
go run . run testdata/multihost.yml -i testdata/multihost-inventory.ini
```

`go test ./...` runs the unit test suite (`go test -run <Name> ./...` for a single test) — see `TESTING.md` for the phased plan behind it. `go test -tags e2e ./...` additionally runs a small set of tmux-driven end-to-end smoke tests (`e2e_rerun_test.go`), excluded from the plain invocation above since they need `tmux`/`ansible-playbook` installed and are slower — see `TESTING.md`'s "hard-to-test tier" for why they exist.

The playbook argument is optional (`resolve.go`) — if omitted (no leading
non-flag argument), it's resolved in order from `$TANGSIBLE_PLAYBOOK`,
`./.tangsible`, `$XDG_CONFIG_HOME/tangsible/config.toml` (falling back to
`~/.config/tangsible/config.toml` per the XDG Base Directory Spec when
that variable's unset), then `./site.yml` if present; a usage error
otherwise. Both config files share one minimal TOML shape:
```toml
[general]
default_playbook = "myplaybook.yml"
```

Running it requires `ansible-playbook` and the `ansible.posix` collection (`ansible-galaxy collection install ansible.posix`) to be installed locally.

## Architecture

**Verb dispatch (`resolve.go`, `main.go`).** `os.Args[1]` must now be a verb — `run` or `rerun` (`verb`, `parseVerb`) — a breaking change from the original bare-playbook invocation. There's no shape-based way to make the verb itself optional the way the playbook argument is (every verb looks like a plain word, same as a playbook path), and Rerun.md's own rationale for introducing `rerun` alongside it expects more verbs to follow, so requiring one explicitly was simpler than inventing a new heuristic. `main()` switches on it early and funnels both branches into the same TUI/generation machinery further down — see Rerun below for the full split.

**Playbook resolution (`resolve.go`, `main.go`).** `splitPlaybookArgs` (now given everything *after* the verb, not `os.Args[1:]` directly) decides whether a playbook was given positionally at all: Tangsible's calling convention has always put the playbook first with everything after it passed straight through to `ansible-playbook`, so the only way to make that leading argument optional without disturbing any invocation that already works is to check its *shape* — empty or starting with `-` means no playbook was given (the whole slice becomes passthrough args instead), anything else is the playbook, exactly as before this existed. This is the `run` verb's own resolution; `rerun` has a separate, history-aware one — see Rerun below.

When not given explicitly, `resolvePlaybook()` tries, in order: `$TANGSIBLE_PLAYBOOK`; `.tangsible` in the cwd; `$XDG_CONFIG_HOME/tangsible/config.toml` (via `configHome()`, which implements the XDG Base Directory Spec's own fallback rule — `$XDG_CONFIG_HOME` if set and non-empty, else `$HOME/.config`, `os.UserHomeDir()` — rather than hardcoding `~/.config`); `./site.yml` if it exists. `readDefaultPlaybook` backs the two TOML sources (`playbookConfig`, a single `[general].default_playbook` key deliberately — the user's own spec for this format explicitly expects it to grow later) — a missing file returns `""` silently (the common case for 3 of the 4 sources isn't worth a warning), but an existing, unparseable one prints a one-line warning to stderr before falling through, so a broken config never fails invisibly. Whatever string is ultimately found (env var value, TOML value, or the literal `"site.yml"`) is passed straight through with no path joining of Tangsible's own — `ansible-playbook` (and `buildTaskSourceIndex`, see Task source lookup below) resolve a relative path against Tangsible's own cwd on their own, identically to how an explicit command-line argument always has been handled.

`main.go` prints a one-line resolution note to stderr (which source won) whenever the playbook wasn't given explicitly — safe to print directly rather than queue like other diagnostics, since this all happens before the TUI is ever constructed. Two call sites elsewhere in `main.go` that used to read `os.Args[1]` directly — `filepath.Base(...)` for the TUI's `playbookName`, and `buildTaskSourceIndex(...)` — now read the resolved `playbook` variable instead; missing either would silently show the wrong name in the top bar or break task-source lookup whenever the playbook came from anywhere other than the command line.

**Data source.** The app never talks to Ansible's Python API and never implements a custom callback plugin (deliberately — see Purpose.md's Platform section for the rationale). Instead it shells out to `ansible-playbook` as a subprocess with `ANSIBLE_STDOUT_CALLBACK=ansible.posix.jsonl` and `ANSIBLE_JSON_INDENT=0` set in its environment. That callback writes one JSON object per line to stdout as each event happens, which is what makes live consumption possible — the built-in `json` callback was considered and rejected because it buffers everything and only writes a single blob after the run completes. Pinning `ANSIBLE_JSON_INDENT=0` guards against a user's `ansible.cfg` overriding the default and breaking the one-event-per-line assumption the line-based scanner depends on.

**Concurrency (`main.go`).** The TUI (`app.Run()`) and the event stream now run concurrently, coordinated by two `atomic.Bool` flags:
- `processDone` — set once `cmd.Wait()` returns; read by `tui.go`'s input-capture handler to decide whether Ctrl-C/`q` should interrupt the child or close the TUI (see below). Since Rerun (below), this is per-*generation*, not per-process: `requestRerun` flips it back to `false` right before spawning a new one, so the same flag means "no generation currently in flight" across however many the process's lifetime ends up covering, not just its original one.
- `quitting` — set once the user has actually chosen to quit (or, defensively, right after `app.Run()` returns for any reason); read by `streamEvents` before every event so it stops pushing updates into a closed/closing UI.

`streamEvents(r io.Reader, applyLive func(rawEvent), quitting *atomic.Bool) []string` reads stdout line-by-line and calls `applyLive(ev)` for each decoded event — `applyLive` (from `tui.go`'s `NewLiveTUI`) wraps `app.QueueUpdateDraw(func() { state.Apply(ev) })`, so `state.Apply` (and the hooks it invokes, see Aggregation below) always runs on tview's event-loop goroutine. Once `quitting` is set, the loop keeps draining `r` (so `ansible-playbook`'s stdout pipe never backs up and blocks *it*) but stops calling `applyLive` — necessary because tview's update queue is a fixed 100-slot buffer that nothing drains once the app has stopped; without this, the goroutine could block forever and the program would hang instead of exiting. A narrow, intentionally-accepted residual race remains in the handoff between checking `quitting` and the in-flight `QueueUpdateDraw` call — documented in the code rather than engineered away, consistent with this project's style elsewhere.

`streamStderr` and the diagnostic prints that used to go straight to stdout (the `v2_playbook_on_stats` cross-check, "(not JSON)" notices, scanner errors) are now all collected into string slices instead, and only flushed by `main` after `app.Run()` returns and the real terminal is restored — printing directly to the terminal while tview's alternate screen is active would corrupt the display. `cmd.Wait()`'s error is likewise captured but not acted on until after the TUI closes, so a failed/interrupted run's tree is still viewable first.

**The TUI is never shown for a pre-flight `ansible-playbook` failure (`main.go`).** A bad playbook path, a parse error, a missing inventory, etc. are all caught by `ansible-playbook`'s own CLI layer before any callback event ever fires — confirmed against `ansible.posix.jsonl`'s source, every line it ever writes to stdout is triggered from a real callback hook. So these failures write *zero* bytes to stdout; the message goes to stderr only, with a nonzero exit. Showing the TUI unconditionally (as `main` used to) meant these runs opened a blank, ticking, empty screen that just sat there until the user quit — only then did the real error print. `scanEvents(r io.Reader) <-chan streamItem` (replacing the old synchronous `streamEvents`) reads stdout on its own goroutine and sends one `streamItem` per line (`isEvent` true for anything that decoded as JSON, `diag` set for a malformed line, the `v2_playbook_on_stats` cross-check dump, or a final scan error — the two aren't mutually exclusive, `v2_playbook_on_stats` sets both), closing the channel at EOF. `main` peeks exactly one item (`first, ok := <-stdoutCh`) *before* ever constructing `state`/`NewLiveTUI`: if the channel closed having produced nothing (`!ok`), `ansible-playbook` never got far enough to run anything real — `main` drains `stderrLines`, calls `cmd.Wait()` (safe here specifically because `scanEvents`'s goroutine only closes its channel after its scan loop already hit real EOF, satisfying `exec.Cmd`'s "fully read the pipes before `Wait()`" contract), prints the stderr lines and the exit error the same way the normal path does, and exits — the TUI is never constructed in this branch. If `ok`, `main` proceeds as before, but replays `first` through the same `apply` closure (append `item.diag` if set; call `applyLive(item.ev)` if `item.isEvent && !quitting.Load()`, reproducing the old per-event quitting-check exactly) before ranging over the rest of `stdoutCh`. `v2_playbook_on_play_start` fires unconditionally as the very first thing any real run does — even for a play with zero tasks (confirmed against `ansible-core`'s `TaskQueueManager.run()`) — so "at least one line arrived" is a reliable, general gate, not a heuristic specific to this one bug.

Deliberately not handled: the fast-fail branch doesn't replicate the exit-99/benign-exit-4 special-casing from above — `state.HadUnreachable` can only ever become true after a real `v2_runner_on_unreachable` event, structurally impossible when zero events ever arrived, and an exit-99 in the sub-millisecond window before the TUI even exists is left to the OS's default SIGINT disposition (which also kills Tangsible itself, consistent with "Ctrl-C behaves like running ansible-playbook directly" for the one window where Tangsible's own forwarding isn't active yet). Also unaffected by this gate, unfixed and out of scope: `--list-tasks`/`--list-hosts`/`--syntax-check` bypass ansible's callback system entirely (confirmed via `playbook_executor.py`) and print their listing text straight to stdout — still ≥1 line, so the gate opens and today's same empty, ticking TUI shows for those flags. Minor accepted side effect of the gate itself: `tui.go`'s top-bar elapsed timer (`NewLiveTUI`'s `startedAt := time.Now()`) now measures from whenever the gate opens rather than from `cmd.Start()`, since the TUI is constructed slightly later — the gap is whatever `ansible-playbook`'s own parsing takes, normally well under a second at this project's target scale.

**Exit codes: a user-requested interrupt or a benign unreachable-host run is not an error (`main.go`, `tui.go`).** `ansible-playbook`'s own exit codes are overloaded and not safe to trust literally:
- **99** is its documented "user interrupted execution" code. In Tangsible specifically it's unambiguous: `tcell`'s raw mode disables the OS's normal Ctrl-C-to-SIGINT delivery (see `SetInputCapture` note below), so the only way the child ever receives `SIGINT` is Tangsible's own forwarding — 99 can only mean "the user asked, via `q`/Ctrl-C, for this run to stop," never an external signal. `main.go`'s `ansibleUserInterruptedExitCode` constant and `exitCodeOf(err error) int` (pulls the code out of `cmd.Wait()`'s `*exec.ExitError` via `errors.As`, returning `-1` for a non-`ExitError` failure — distinct from every real code, so it never accidentally matches 0 or 99) exist to let `main` and `tui.go` reason about this without re-deriving it.
- **4** is ansible-core's own `ExitCode` enum value for *both* `HOST_UNREACHABLE` and `PARSER_ERROR` (a static-include syntax error) — confirmed directly against ansible-core's source, which has its own `FIXME: conflicts` comment acknowledging the collision. Exit 4 alone can't be trusted to mean "benign." Tangsible disambiguates using evidence it already independently observed rather than the exit code alone: `aggregate.go`'s `playbookState.HadUnreachable` (set in `recordHost` whenever a host is recorded `outcomeUnreachable`, same funnel as `AllHosts`; never cleared) is only ever `true` if at least one real `v2_runner_on_unreachable` event occurred — which structurally cannot happen for a `PARSER_ERROR`, since that's a parse-time failure resolved before any task in any play begins. `main.go` computes `benignHostUnreachable := result.exitCode == 4 && state.HadUnreachable` and only treats it as benign for exactly that combination — exit 6 (`HOST_FAILED|HOST_UNREACHABLE`, a real task failure alongside an unreachable host) still reports as an error, since a genuine failure happened too.

Both cases fall through to a normal `main` return (exit 0) instead of `os.Exit(1)`, and skip the `"ansible-playbook exited with error:"` line. Only the 99 case additionally suppresses `childStderr` (the `[ERROR]: User interrupted execution` line is pure noise about an intentional action); exit-4's real stderr — e.g. the SSH connection-timeout line, when there is one — is left intact, since it's genuinely useful context alongside the maroon row already visible in the tree. (In practice, ansible's SSH-timeout messages tend to live entirely in the `msg` field of the `v2_runner_on_unreachable` event, visible via the drill-down view rather than on stderr at all — so there's often nothing to suppress either way.)

`state.HadUnreachable` is read from `main`/`rebuild()` with no atomic, deliberately: every write happens inside a `state.Apply` call, and every `state.Apply` call runs on whichever goroutine is executing `app.Run()`'s event loop — since `main()` calls `app.Run()` directly (not via `go`), that's `main`'s own goroutine, making this a single goroutine reading its own prior sequential writes, unlike `processDone`/`quitting`/`exitCode` (see Concurrency above), which genuinely cross goroutines and correctly need atomics.

`tui.go`'s `statusRowText(code int, hadUnreachable bool) string` renders the inline status message appended below the last task row once the run is frozen (see Heartbeat below for `processDone`/frozen framing) — green `"Playbook completed successfully"` only for a genuine `code == 0`; yellow `"Playbook completed - one or more hosts were unreachable"` for `benignHostUnreachable` (`code == 4 && hadUnreachable`); red `"Playbook stopped, press q again to quit tangsible."` for `code == ansibleUserInterruptedExitCode`; red `"Playbook failed (exit code N)"` for anything else. Every terminal case gets an explicit line now - this used to fall through to `""` (nothing shown) for a genuine failure, reasoning that the red host rows already made it obvious, but a real run (one host, one task, that task failed, nothing else ever executed) showed no closing line at all, reading as "did this even finish?" rather than a clear verdict. The green/yellow split above it is similarly deliberate, not cosmetic: `code == 0` and `benignHostUnreachable` used to render identical green text, but they're not the same situation - confirmed live, a single-host playbook whose one host is unreachable on its very first task exits 4 with `hadUnreachable == true` and *nothing else in the run ever having executed*, which "completed successfully" actively misrepresented. `main.go`'s own decision to still treat a genuine failure as a hard tool error (`os.Exit(1)`, unlike `benignHostUnreachable`/user-interrupted) is unaffected by any of this - that's about whether Tangsible's own process should exit nonzero, a different question from what this status line honestly reports while the TUI is still up.

Making every terminal case show a status row surfaced a second, previously-latent bug in `rebuild()`'s own selection logic: `statusRowID`/`statusDividerRowID` rows have no selected-row rendering variant (see Row text below - by design, there's nothing to select there), so once a finished run always appends one, `following`'s old `selectedIndex = len(currentRows) - 1` could land the cursor on one of those two rows - which then rendered *identically* whether selected or not, i.e. the cursor visibly vanished (reported live: "I have to press Cursor up a few times until it reappears"). Fixed by walking backward from the end past any trailing `statusRowID`/`statusDividerRowID` entries before settling on `selectedIndex`, landing on the last real (play/task/host) row instead - which does have a selected variant.

`genuineFailure(code int, hadUnreachable bool) bool` is `statusRowText`'s own default-case condition, pulled out separately so it can't silently drift out of agreement with a second consumer: right on the running-to-frozen transition (guarded by a one-time `failureCursorPlaced` latch, so this can never re-fire and yank the cursor back after the user has since navigated elsewhere), `rebuild()` calls `lastFailedTaskAndHost(state)` - walking `state.Plays`/`Tasks` backward, then each task's own `HostOrder` forward, for the most recent task with a Failed or Unreachable host - and if one is found *and it still matches the currently active filter* (`taskVisible(t, currentFilter, sourceIndex, false)` - `isActive` is unconditionally `false` here, since a frozen run has no in-progress task by definition, so there's no need to even call `activeTaskNow()`), force-expands that task and points `currentID` there (`following = false`), so a genuine failure lands the user on a single `Enter` away from the drill-down, no navigation required. The filter check is what resolves Filters.md's own once-open question about this interaction (see Filtering below): "filter wins, skip the auto-jump" rather than forcing a non-matching row into view, which would quietly break the filter's own promise that only matching tasks are ever shown. In practice this only ever skips the jump for the search filter - a failed task always matches "Changed" and "Failed" by definition, so `A`/`C`/`F` can never trigger it. This runs *before* `flattenRows` in the same `rebuild()` pass specifically so the newly-expanded host row is already present in `currentRows` by the time the selection logic above runs against it - setting `expanded` any later would miss it until the next rebuild.

**Event shape (`events.go`).** `rawEvent` decodes the subset of the jsonl schema the app cares about. Empirically confirmed (not formally documented upstream, so re-verify against real output before depending on new fields): `v2_playbook_on_play_start` carries `play.name`; `v2_playbook_on_task_start` carries `task.name`, and neither of these carries any host list — there's no event that reveals a task's target hosts before its first per-host result; `v2_runner_on_ok` / `v2_runner_on_skipped` / `v2_runner_on_failed` / `v2_runner_on_unreachable` all share the shape `task` + `hosts: {<hostname>: {...}}`, with the per-host `changed` bool distinguishing OK from Changed within an `_on_ok` event (skipped/failed/unreachable are their own distinct event names, not a flag). `v2_playbook_on_stats` carries Ansible's own final per-host tallies, useful as a sanity check against this app's own counts (see caveat below).

`rawEvent.Hosts` is `map[string]json.RawMessage`, not a typed struct — each host's full original JSON is preserved (not just the fields `hostResult` decodes) since different Ansible modules return wildly different result shapes (command: `stdout`/`stderr`/`cmd`/`rc`; most modules: `msg` on failure; others: arbitrary module-specific fields), and hand-modeling all of them isn't worth it. `decodeHostResult` extracts just the classification fields `Apply` needs from those raw bytes; the full bytes themselves get stored for later display (see `taskNode.Raw` below).

`rawEvent.TimestampText` (every event's own `_timestamp`, empirically RFC3339 with fractional seconds) is deliberately a plain `string`, not `time.Time`, with the fallible parsing done separately by a `Timestamp() time.Time` method that swallows errors (same convention as `decodeHostResult`). A `time.Time` struct field's own `UnmarshalJSON` failing on a malformed value would make `json.Unmarshal` return an error for the *whole* `rawEvent`, which `streamEvents` treats as "not JSON" and discards the entire event — task and hosts included — over nothing but a bad timestamp. Real bug caught during design, not a hypothetical.

**Aggregation (`aggregate.go`).** `playbookState.Apply` consumes one `rawEvent` at a time and builds a `Plays []*playNode` → `Tasks []*taskNode` → `Hosts map[string]outcome` tree. Plays and tasks are created lazily (a play only gets a row once its first task starts), so plays with no executed tasks never appear — matches the decision in `TUI.md`. Ansible's default/linear strategy runs one task across all hosts before starting the next task, so a simple `currentTask` pointer (updated on task-start) is enough to attribute later `runner_on_*` events to the right task, without needing to correlate by task ID. Counts are computed on demand by scanning `taskNode.Hosts` rather than tracked as separate counters, to avoid a second source of truth.

`v2_playbook_on_task_start` and `v2_playbook_on_handler_task_start` are handled identically, in the same `case` — two entirely distinct event names (confirmed empirically, not documented upstream) for a regular task vs. a `notify:`-triggered handler, but otherwise carrying the identical `task{name,path,...}` shape. This was a real bug, not a hypothetical: handling only the regular-task event meant a handler run never got its own `taskNode` and never advanced `currentTask` at all, so its later `v2_runner_on_*` events still fired and still went through `recordHost`, silently attributing the handler's own result onto whatever task genuinely started last - which could corrupt an *already-displayed, already-correct* task's own `Raw`/`Hosts` entries for a host the handler happened to run for afterward (a task's `Task:`/title bar stayed correct throughout, since those come from the task-start event that created the node - only `Output`/`Details`, sourced from `Raw[host]`, silently became the handler's data instead). Treating both events identically - own `taskNode`, own row, own `currentTask` - is what makes a handler run visible in the tree at all instead of silently overwriting something else's data.

`playbookState` also exposes three optional, nil-checked hooks — `OnPlayAdded`, `OnTaskAdded`, `OnHostRecorded` — invoked by `Apply` right as each thing happens, deliberately typed using only this file's own types so it stays free of any UI dependency. `tui.go` wires these to grow the tview tree incrementally instead of rebuilding it from scratch on every event (a rebuild would reset all expand/collapse state and the current selection each time). Because `Apply` always runs from inside `app.QueueUpdateDraw` (see Concurrency above), `playbookState` is safe to mutate with no mutex — but only because it's always that one goroutine doing it; it's not a general-purpose concurrent structure.

`playbookState.AllHosts` is the run-wide, alphabetically-sorted set of hosts that have reported anything, for any task, so far — it only ever grows, via `noteHost` (called from `recordHost`, the same funnel every outcome-recording event type goes through), using a plain linear scan + `append`+`sort.Strings` rather than a membership map or smarter insertion (needless machinery at this project's ~10-host target scale). `tui.go`'s `taskLabel` uses this to show every known host on every task's row, greying out any that haven't reported for that *specific* task yet, instead of showing only the hosts that particular task has itself heard from — since there's no event that reveals a task's hosts in advance (see Event shape above), a task's very first appearance in a run necessarily starts this list from empty; only later tasks benefit from the "grey until lit up" effect.

`outcomeUnreachable` is its own outcome now, not folded into `outcomeFailed` — the collapsed-row redesign (see TUI (`tui.go`) below) made that distinction visually worth having, whereas it wasn't when the only display was an aggregate count.

`taskNode.Raw map[string]json.RawMessage` sits parallel to `Hosts`, populated alongside it in `record` — each host's full original result payload for that task, kept so `tui.go`'s output drill-down view can show it later. `aggregate.go` stays free of any formatting logic here too: `Raw` is read but never interpreted in this file.

`taskNode.StartedAt` comes from the starting event's own `rawEvent.Timestamp()`, not our wall-clock `time.Now()` at the moment we process it — "when did Ansible itself start this task." Currently unused by any renderer (`tui.go` shows a spinner rather than an elapsed readout for the active task — see Heartbeat below); kept because Ansible provides it for free and a future summary/history view (see `Findings.md`) would likely want it. `playbookState.CurrentTask()` is a read-only accessor for the same unexported `currentTask` field `Apply`/`recordHost` already maintained — added so `tui.go` reads it deliberately through an accessor (to mark the active task's row with a spinner) rather than reaching into a field clearly meant as this file's own private bookkeeping, even though same-package access would technically compile.

`aggregate.go`'s no-mutex safety story is now also worth restating precisely: `tui.go`'s ticker goroutine (see below) is the first thing in this codebase that triggers reads of `playbookState` on a schedule rather than strictly in response to an event or keypress — still safe, since the ticker's reads happen inside `app.QueueUpdateDraw`, which runs on the same single event-loop goroutine `Apply` itself always runs on.

One remaining deliberate simplification: failed-but-ignored tasks (`ignore_errors: true`) still show as `Fail`. This is *not* how Ansible's own `v2_playbook_on_stats` counts them — Ansible counts an ignored failure toward `ok` (plus a separate `ignored` tally), so this app's rollup will not numerically reconcile with Ansible's own recap stats for playbooks that use `ignore_errors`. Expected, not a bug.

**Plain-text rendering (`render.go`).** `Render` prints the whole tree in one shot, always showing every host line under every task. No longer called from `main`'s normal flow (superseded by the tview UI below) but kept around as a still-useful, dependency-free dump — e.g. for debugging or a future non-interactive mode.

**TUI (`tui.go`).** Built with `github.com/rivo/tview` (on top of `github.com/gdamore/tcell/v2`) — chosen over Bubble Tea's Elm-style architecture specifically because it's a smaller conceptual jump from `tcell`, which prior project experience already covered. Originally used `TreeView` (which maps directly onto the play/task/host shape), but migrated to `List`: `TreeView` renders each node with one uniform `tcell.Style` (confirmed from its source), so there was no way to color the OK/Chgd/Skip/Fail segments of a task row differently from each other. `List` parses inline `[color]text[-]` style tags in its item text (same tag-aware print path `TextView` uses), which is what makes the per-segment coloring below possible. Migrated a second time, later, from `List` to a hand-rolled `treeList` (`treelist.go`) — see Mouse below for why; the rest of this section describes behavior that carries over unchanged between the two (`treeList` was written specifically to preserve it) except where a note says otherwise.

Since `List` is flat (no built-in hierarchy/expand-collapse), `tui.go` owns:
- **Expand state** — `map[*taskNode]bool`. A newly-added task's own initial entry isn't just the zero value (`false`/collapsed) anymore: `state.OnTaskAdded` sets it to whatever the *previously* added task's current entry is (derived from `allTasks(state)` - by the time this hook fires, the new task is already the last element, so the second-to-last is "the task added right before it"; no separate tracked "last added task" variable needed, since `state.Plays` only ever grows during a run). Only the very first task of a generation (fewer than 2 tasks exist yet) falls back to `startExpanded` (`NewLiveTUI` param, from `.tangsible`'s `general.default_tree_state` - see `resolve.go`'s `defaultTreeExpanded`, defaults to collapsed if unset/unrecognized). This is what makes `E` (expand all) "sticky" for a still-running playbook: `expandAll` sets every *existing* task's entry to `true`, including whichever one was added most recently - so every task added afterward inherits `true` too, not just the ones already on screen at the moment `E` was pressed. No explicit reset needed on a rerun either - `requestRerun`'s `state.Reset()` (`main.go`) already clears `state.Plays` before this hook can fire again, so `allTasks(state)` is correctly empty for the new generation's own first task.
- **Flattening** — `flattenRows(state, expanded, width) []row` walks `Plays → Tasks → (if expanded) Hosts` into an ordered row list, rebuilt fresh on every event (cheap at ~10-host scale; no incremental patching needed, unlike the old `TreeView` bookkeeping maps this replaced).
- **Selection preservation across rebuilds** — `rebuild()` (inside `NewLiveTUI`) tracks the *identity* of the selected row (a `*playNode`, `*taskNode`, or `hostRowID`, not a raw index, since row order shifts as things are appended). It now computes `selectedIndex` (via `currentID`/`following`, same logic as before) *before* the `Clear()`+`AddItem()` loop, not after — needed because the cursor row's styling (see Row text below) is baked into that row's own text rather than applied by `List` automatically, so `rebuild()` must know which row that is in order to re-render it with its `selected=true` variant first. Non-obvious gotcha hit here: `List.Clear()` followed by re-`AddItem()` fires a spurious "changed" event the instant the first row lands back in the now-empty list, which will silently overwrite the tracked selection *during* the rebuild if you're not careful — guarded against with a `rebuilding bool` flag that `SetChangedFunc`'s handler checks before recording anything.
- **Autoscroll** — a `following bool` (default `true`) makes `rebuild()`'s `selectedIndex` resolve to the newest row instead of restoring by identity. Any genuine (non-`rebuilding`) `SetChangedFunc` event disengages it — that's what "the user navigated" reduces to, since `Up`/`Down`/`PageUp`/`PageDown`/`Home`/`End` are all handled by `List`'s own `InputHandler` and each fires that same callback. Only `'F'` is intercepted in `SetInputCapture` to re-engage it, by setting `following = true` before jumping to the last row — a second guard, `jumpingToEnd bool`, exists only so that jump's own resulting `changed` event doesn't immediately flip `following` back off again. End/`'G'`/Ctrl-E are deliberately *not* wired to this — see Keyboard shortcuts below for why they're plain navigation instead. Wraparound at the list's ends is off (tview's own `List` default was `true`, so this used to be an explicit `list.SetWrapAround(false)` call; `treeList` has no wraparound behavior to begin with, so there's nothing to configure — see Mouse below).
- **Navigation now triggers a full `rebuild()`, not just data events or the heartbeat tick** — added because the cursor row's look is baked into row text (see Row text below); without this, moving the cursor via a plain arrow key wouldn't visually move the highlight at all until something else happened to call `rebuild()` (and once a run finishes, the heartbeat ticker stops entirely — see Heartbeat below — so it would never move again). Added inside `SetChangedFunc`'s already-existing genuine-navigation branch, gated behind the same `rebuilding` check used for the `Clear()`/`AddItem()` gotcha above. That gating is what makes this safe, not incidental: `treeList.SetCurrentItem` (`treelist.go`) updates its own `currentItem` field *before* firing its `changed` callback (the opposite order from `tview.List.SetCurrentItem`, chosen deliberately when `treeList` was written specifically so a same-index recursive call is a self-terminating no-op on its own — see Mouse below) — but `rebuild()`'s own trailing `SetCurrentItem` call can still legitimately look like a changed index purely from `Clear()`/`AddItem()` churn (see Mouse below), so the `rebuilding` guard is still load-bearing regardless of ordering. Since `rebuild()` sets `rebuilding = true` for its entire body — including its own closing `SetCurrentItem` call — any `changed` event that cascades from within it lands back here while `rebuilding` is still true and is correctly ignored.

- **Expanding a task scrolls to reveal its newly-added host rows (`revealExpandedTask`)** — expanding via Enter/Space/click or the Right-arrow handler (`handleRight`) leaves the cursor on the task row itself (only a toggle, not a jump). `treeList` (like `List` before it) never re-clamps the viewport to the cursor's position on its own except in response to a genuine `SetCurrentItem` index change (see Mouse below) — since the cursor doesn't move here, nothing does that automatically, even when the newly-revealed host rows land entirely below the bottom of the screen with no visible change at all - a real, reported case. `revealExpandedTask` runs right after `rebuild()` in the row's own `selected` wrapper (and again in `handleRight`) and, if the task's own row plus all its hosts don't already fit in the current viewport, nudges `list`'s scroll offset (`GetOffset`/`SetOffset`) down just far enough to reveal as much of that block's tail as fits - only ever further down from wherever the view already was, never up. Deliberately doesn't try to keep the task row anchored at any particular position or guard against over-scrolling itself: it relies on `Draw()`'s own defensive bound (itemOffset can't exceed the last row) as its only safety net, which is enough since the cursor never leaves the task row here.

`NewLiveTUI` returns both the `*tview.Application` and an `applyLive func(rawEvent)` closure — `main.go` calls `app.Run()` and feeds events through `applyLive` but never imports `tview` itself, keeping `tui.go` (plus `treelist.go`, its widget) the only files that touch `tview`/`tcell`.

**Heartbeat (`tui.go`).** A ticker goroutine (`spinnerInterval` = 200ms) is the first *self-driven* source of `QueueUpdateDraw` calls in this codebase — every other trigger so far has been an incoming jsonl event or a keypress. Each tick calls `app.QueueUpdateDraw(rebuild)`, which now also refreshes `topBar` (`topBarText`: playbook name, spinner frame, total elapsed time since `NewLiveTUI` was called) and computes `activeTask := state.CurrentTask()` (nil once `processDone`) for `flattenRows` to attach a spinner prefix to (see `taskLabel` below — no longer an elapsed-time readout; removed because it made the active task's row shrink its hostnames slightly more aggressively than every other row's, an inconsistency the fixed-width spinner slot doesn't have). `spinnerAt(elapsed time.Duration) rune` is shared by `topBarText` and `taskLabel` so both tick the identical frame at the same instant when driven from the same `elapsed` value, computed once per `rebuild()` call. The ticker needs — and has — the same `quitting`-checked-before-`QueueUpdateDraw` guard `main.go`'s `streamEvents` already uses, for the same underlying reason (tview's update queue is a fixed 100-slot buffer nothing drains once the app has stopped), though the stakes differ slightly: nothing in `main.go` waits on this goroutine the way it waits on `streamEvents`, so a hang here wouldn't itself block process exit — worth guarding anyway. Once `processDone` is observed true, the goroutine pushes one final frozen frame (spinner dropped, elapsed held static) and returns, rather than continuing to tick forever over an unchanging screen — this is also why navigation had to be taught to trigger its own `rebuild()` (see Selection preservation above): once frozen, this ticker is the *only* other thing that used to keep the cursor's rendering fresh. "Elapsed held static" needed its own fix, though: `rebuild()` itself unconditionally computed `elapsed := now.Sub(startedAt)` on every call, not just the ticker's — so any later `rebuild()` triggered by cursor navigation (`SetChangedFunc`'s genuine-navigation branch, see Selection preservation) or mouse panning (see Mouse below) recomputed a fresh, still-climbing elapsed and made the top bar's timer visibly keep ticking well after the run had actually finished. Fixed with `haveFrozenElapsed`/`frozenElapsed`, latched the first time `rebuild()` observes `frozen == true`: every later call while frozen reuses that one captured value instead of recomputing it. It's started *after* `app = tview.NewApplication()...` — not just style: the `go` statement's happens-before edge is what makes reading `app` from that goroutine well-defined, per the Go memory model.

`taskLabel`'s `active bool, frame rune` parameters render a fixed-cost 2-rune prefix in place of the row's leading `taskIndent` — the spinner frame plus one space for the active task, or `taskIndent`'s own plain spaces otherwise. Originally this was a trailing `" <frame>"` suffix reserved from the width budget right after the title; moved to the front (reusing indent's already-reserved width instead of carving out more) so hostnames get that width back on the right. Either way the width is fixed and reserved unconditionally, so every row's hostnames still shrink identically regardless of which task, if any, is active — only the *content* of that fixed slot differs.

**Resize watcher (`tui.go`).** A second, permanent ticker, started once right after `startHeartbeat()`'s own first call and deliberately *not* folded into it: `startHeartbeat`'s ticker already permanently stops once `processDone` is observed true (see Heartbeat above), so without a second mechanism, nothing is left to notice a bare terminal resize with no other incoming event once a run is frozen — `taskLabel`'s width comes from whatever `list`'s size was at the *last* `rebuild()` call, and `treeList.Draw()` only ever paints whatever static row text it was last given, never re-wrapping on its own. This ticker's own tick (also `spinnerInterval`, reused only as a convenient existing interval, not tied to spinner-animation cadence) skips its entire body while `!processDone.Load()` — while a run is still live, `startHeartbeat`'s own ticker already re-syncs everything, resize included, within `spinnerInterval` regardless, so there's nothing for this one to do until frozen. Once frozen, each tick calls `app.QueueUpdate` (not `QueueUpdateDraw`) to compare `list.GetInnerRect()`'s current width against `lastRebuildWidth` (a var set at the same place `rebuild()` computes its own `width` local, recorded regardless of what triggered that particular rebuild) — only differing once a genuine resize has happened — and calls `rebuild()` followed by `app.ForceDraw()`, but *only* on that difference, so an idle frozen screen costs a cheap channel round-trip every tick with no actual redraw. `app.Draw()` specifically must never be used here instead of `ForceDraw()`: `Draw()` is `QueueUpdate` under another name, and calling it from a closure that's already executing via `QueueUpdate` — i.e. already running on the single event-loop goroutine — is a genuine self-deadlock (it enqueues a second update and blocks forever waiting for the event loop to dequeue it, which it structurally cannot do while stuck inside the very call that's waiting). `ForceDraw()` calls `a.draw()` directly with no channel round-trip, and `tview`'s own doc comment sanctions exactly this usage: "safe to call this function during queued updates and direct event handling." (`SetBeforeDrawFunc`/`SetAfterDrawFunc` were both checked and ruled out as alternatives: the former fires before child rects are updated on resize, so `list`'s width isn't current yet; the latter runs while `a.draw()` still holds `a.Lock()`, so even `ForceDraw()` would deadlock there specifically, on the mutex itself rather than the channel.) Because this ticker is fully independent of `startHeartbeat`/`submitRerun`'s own per-generation restart lifecycle, it needs no "restart on rerun" handling at all — it just runs for the whole process's lifetime, across however many generations that ends up covering, same `quitting`-checked-before-queueing guard as `startHeartbeat`'s own ticker, same underlying reason.

**Task source lookup (`source.go`).** `buildTaskSourceIndex(playbookPath) taskSourceIndex` (a `map[string]string`) backs the output drill-down view's `TASK:` section — showing the task exactly as written in the playbook/role source, alongside its result, without switching views. Built once in `main.go`, synchronously, right after the pre-flight gate confirms a real run is happening (so a bad playbook path doesn't pay for it), and threaded into `NewLiveTUI` as a new parameter.

Two things worth knowing about how this works, both confirmed empirically (throwaway test playbooks, not kept in the repo) before committing to the design:
- **Matching a task to its source doesn't require modeling Ansible's own include/role resolution.** Every event's `task.path` (now captured by `events.go`'s `taskRef.Path` and carried onto `taskNode.Path` in `aggregate.go`, both previously dropped) is an *absolute* `file:line` — true even for a `include_tasks:` path built from a Jinja expression, since Ansible resolves it and reports the real target file. So instead of reimplementing `roles:`/`import_tasks`/`include_tasks`/`include_role` resolution (including dynamic-path templating, which would need Ansible's own variable/Jinja engine), `buildTaskSourceIndex` just discovers and parses every `.yml`/`.yaml` file under the playbook's own directory tree (`filepath.WalkDir`, skipping `.git`) and indexes each task by its own `(absolute path, start line)` — independent of *how* anything references it. A role's `tasks/main.yml` is picked up this way with no special-case role-resolution logic at all; the index is keyed by exactly the string `task.Path` already contains, so lookup is a direct map read. A miss (unusual file layout, a task genuinely generated at runtime) just means no `TASK:` section for that one entry — `formatHostOutput` treats this identically to "nothing found," never an error.
- **`gopkg.in/yaml.v3`'s line-tracking gives exact task boundaries through `block:`/`rescue:`/`always:` nesting and multi-line block scalars, without being Ansible-schema-aware.** `indexFile` parses each file into a `*yaml.Node` tree (not a typed struct — the file's shape is only assumed loosely: is the top level a sequence of mappings with a `hosts:` key each (playbook-shaped, walk each play's `tasks`/`pre_tasks`/`post_tasks`/`handlers`), or a bare sequence of task mappings directly (task-list-shaped — covers role files and any include/import target)). `indexTaskList`/`walkMappingForTaskLists` compute each task's end line as the start line of the next sibling **at whichever ancestor level actually has one** — an immediate sequence sibling, or (walking up) the next key in an enclosing mapping — falling back to EOF only at the very top. This one rule, applied generically, is what correctly stops a `block:`'s last task right before a sibling `rescue:` key rather than swallowing it (verified live: a task inside `block:` immediately followed by `rescue:` shows a `TASK:` span ending cleanly before `rescue:`, not extending into or past it) — no special-casing of `block`/`rescue`/`always` beyond recursing into them, and no special-casing of multi-line scalars either (a multi-line `when: >` value falls inside its task's span automatically, since the boundary comes from the *next task's* line, never from measuring the scalar itself).

The source text stored per task is verbatim — sliced directly from the file's own lines, never reformatted/re-serialized — so the user's own formatting, comments, and exact YAML (tags, `become`, `when`, `loop`, `delegate_to`, etc.) show up exactly as written. Nothing is templated or evaluated; a `{{ ... }}` expression renders as literal text, deliberately — resolving it would need Ansible's own variable/fact engine, well outside this mechanism's scope.

**Output drill-down (`tui.go`).** The app's root is a `tview.Pages` (not the main `Flex` directly) with two pages: `"main"` (the existing top bar/list/bottom bar) and `"output"` (a single, reused `TextView` in its own small `Flex` with its own bars). Host rows' `selected` callback — previously always `nil` — now calls `showOutput(task, host)`, which formats `task.Raw[host]` via `formatHostOutput`, updates the output view, and switches pages; the `TextView`'s own `SetDoneFunc` (fires on Escape/Enter/Tab/Backtab) switches back. Hiding a page only flips a `Visible` flag — the list's selection/state is never touched by this, confirmed via `tview`'s source rather than assumed.

Two non-obvious things a design-review pass caught here that are easy to reintroduce if this code is restructured:
- `TextView.SetText` does **not** reset scroll position (`lineOffset`/`trackEnd`). Since the output view is one `TextView` reused across every drill-down (never recreated), `showOutput` must call `outputView.ScrollToBeginning()` after every `SetText` — otherwise opening a second host's output right after scrolling through the first would open already scrolled to (or bottom-pinned from) the old position.
- Left/Right and `n`/`p` mean different things on each page (host-nav/task-nav in the output view vs. expand-collapse/task-hop in the main tree — see Keyboard shortcuts below), so `SetInputCapture` needs to know which page is frontmost before dispatching them. Fixed with a `viewingOutput bool` (same locally-owned-flag style as `following`/`jumpingToEnd`), checked before the page-specific bindings dispatch.

`formatHostOutput` decodes `task.Raw[host]` into a generic `map[string]interface{}` (not a fixed struct, for the same reason `events.go`'s `rawEvent.Hosts` doesn't decode into one), leads with a colored status line and a `TASK:` section looked up from `sourceIndex[task.Path]` (see `source.go` below and Color below) when found, then shows one labeled section for `primaryOutputField`'s chosen text (see below), then `stderr` if present and non-empty, followed unconditionally by the complete result as pretty-printed JSON — the fallback that makes this work for any module's result shape without special-casing.

**Color in the output view (`tui.go`).** `outputView.SetDynamicColors(true)` (flipped from `false` when this view first shipped) is what makes any of this possible — but it also means every piece of dynamic/external content `formatHostOutput` writes now has to be individually `tview.Escape()`'d before going in (task source, stdout/stderr/msg, the full JSON, even the raw bytes on a decode-failure fallback), since a literal `[` in any of it (a YAML `tags: [a, b]`, a JSON array) would otherwise be misread as a color tag — confirmed live against exactly that `tags: [rolestuff]` case (this project's own earlier test fixture) that the escaped text renders as literal brackets, not a broken tag. Only `formatHostOutput`'s own fixed label/status strings go in unescaped, since they're never external content.
- A status line (`[colorTag(o)::b]● OUTCOME[-::-]`) leads every view, reusing the tree's own outcome palette (`colorTag`, see Row text above) rather than inventing a second one — the host's result for this task is visible before reading anything else.
- Each section gets a renamed, un-suffixed heading (`Task`/`Output`/`Errors`/`Details` — "Output" regardless of whether `primaryOutputField` actually picked `stdout` or `msg`, since that's an internal selection detail not worth surfacing) via the small `sectionLabel` helper: the heading itself bold, followed on its own line by a plain (non-bold) `=` underline of the same rune length, both in the section's own color. Colors are deliberately chosen *outside* `colorTag`'s green/yellow/teal/red/maroon set so a section color is never mistaken for an outcome color: `orange` for Task, `aqua` for Output, `red` for Errors (an intentional exception — reusing red here *is* meant to echo "problem," unlike the other section colors), `gray` for Details (deliberately de-emphasized, matching `grayTag`'s existing "not the important part" convention elsewhere — it's the everything-else fallback, not primary reading material).
- `colorizeYAML` gives the `Task` section a light, line-based "key:" highlight (`yamlKeyLine`, a regexp — not a real YAML parser) — colors the key portion of a `key:` or `- key:` line in Task's own orange, leaves anything that doesn't match that shape (a multi-line scalar's continuation lines, a plain `- item` list entry) unstyled. Key characters deliberately include `.`/`-` beyond the usual `A-Za-z0-9_`, to cover FQCN module names like `ansible.builtin.debug:` as well as plain fields - good enough for every real task shape checked against, not exhaustive by design (same "documented heuristic, not chased to 100%" style as `taskLabel`'s truncation algorithm or `primaryOutputField`'s stdout-vs-msg choice).
- `taskSourceLocation(task.Path)` renders a dim gray `[<file>, line <n>]` right below the `Task` section's own YAML, split from `task.Path` on its last `:` (matching how `source.go` constructs that key in the first place) - the same escape-then-tag discipline applies, since the literal `[`/`]` here are real displayed characters, not tag syntax.

`primaryOutputField(decoded) (label, text string)` picks a single field to show as "the output" — `stdout` if non-empty, else `msg` — rather than showing both. On a command/shell task with a non-zero return code, `msg` is often just a fixed status string (`"non-zero return code"`) alongside the real output already sitting in `stdout`; for modules that only set `msg` (most non-command modules), that's the fallback. Shared between `formatHostOutput` (the drill-down view) and `outputSummary` below (the collapsed treeview OK line) so both agree on what "the output" means for a given result.

`hostLabel`'s expanded-row text gets an outcome-specific parenthesized detail, computed from `task.Raw[host]`, in addition to the base "host: OUTCOME": `outputSummary` (OK/Changed/Failed) shows `primaryOutputField`'s text verbatim if it's a single line, or `"N lines of output"` otherwise, or nothing if there's no output text at all (e.g. `copy`/`template`, which only report `changed`) — for Failed specifically, this is usually the failure's own `msg`, since `stdout` is typically empty for a command that never produced output before failing. `skipDetail` (Skipped only) shows `skip_reason`/`false_condition` straight from the recorded result, falling back to just `skip_reason` if `false_condition` isn't a plain string (e.g. a literal `when: false` serializes it as JSON `false`, not a string). Unreachable renders exactly as before — undefined for now, not a gap that was missed.

**Row text (`taskLabel`/`hostLabel`/`playRowText`/`colorTag`).** `colorTag(outcome) string` maps OK/Changed/Skipped/Failed/Unreachable to tag color names — `green`/`yellow`/`teal`/`red`/`maroon`. `teal` is `tcell`'s/W3C's closest named match for ANSI cyan; `maroon` (not `brown`/`darkred`) for Unreachable specifically because it's in the same base-16 ANSI palette family as the other four (index 1, vs `red`'s index 9 — a different terminal-configured slot, not just a different-looking RGB value), whereas `brown`/`darkred` are RGB-approximated extended-W3C names that render less predictably across terminal themes.

The `PLAY:`/`TASK:` label prefixes are gone — `playRowText` renders just the play's name (white, bold); `taskLabel` shows every host in `allHosts` (see `AllHosts` above) after the plain task title (silver, regular weight — deliberately not `grayTag`'s plain `"gray"` either, to keep "this is a task's own title" visually distinct from "this host hasn't reported for this task yet"), colored by `task.Hosts[host]`'s outcome if present, `"gray"` otherwise — the "grey until lit up" effect, which falls straight out of that map lookup with no extra bookkeeping. `hostLabel` (the expanded per-host detail view) still colors its whole line uniformly by its single outcome, unaffected by any of the layout logic below (no width-based truncation applies there).

**Host column layout, third iteration (`computeHostColumnLayout`/`taskLabel`, per `TUI.md`'s "Tree View - third iteration").** Hosts are now left-aligned, starting at the same column on every task row, regardless of that row's own title length — a real change from the previous two iterations, which right-aligned each row independently (no row knew anything about any other row's width). A shared column needs a value some rows (the ones with short titles) can only get by looking at *other* rows first, so this moved the layout computation out of `taskLabel` and into a new function, `computeHostColumnLayout(state, allHosts, avail) hostColumnLayout`, called once per `rebuild()` rather than once per row. `hostColumnLayout{TitleColWidth int; HostDisplay []string}` bundles the two values every row then shares: how wide the title "column" is, and the (possibly globally-shrunk) display text for each host — text only, never color; each row still resolves its own host colors from `task.Hosts[host]`, same as before.

`TitleColWidth` is normally the widest *natural* (untruncated) title width across `allTasks(state)` — every task the run has produced so far, deliberately unconditional (ignores expand/collapse and the active filter), so the column never shifts just because the user expanded or collapsed something. This also makes the column monotonically non-decreasing for free, with no separate tracked state: `state.Plays` only ever grows during a run (tasks are appended, never removed — see `aggregate.go`) and resets to empty via `Reset()` on a rerun, so recomputing the widest title fresh from `state.Plays` on every rebuild already can't produce a smaller value than the previous rebuild's, within one generation.

If the widest title, the full host list, and `titleHostGapFloor`'s worth of breathing room don't all fit within `avail`, the *same* two-step algorithm the previous iterations used still applies, just now to the shared column instead of one row's own title: shrink the column first, down to `minTaskTitleName` (still 30, unchanged); only if that alone isn't enough, shrink hostnames next — same "reduce the currently-longest hostname by one, repeat" loop as before (no ellipsis, 1-rune floor each, accepted overflow beyond that), but now run *once* here rather than once per row. That's not just an optimization: with a shared column and a shared `avail`, every row's own available host-list width is identical by construction, so per-row-independent shrinking would only ever reproduce the same result anyway — running it once is what makes the truncated host *text*, not just the column's start, line up column-by-column down every row, without a second alignment mechanism.

Per-row rendering (`taskLabel`) is now mostly bookkeeping against the shared `layout`: truncate the row's own title (still `…`, same convention) only if its own natural width exceeds `TitleColWidth` — this is how a title that isn't itself the widest can still end up truncated, if the shared column was shrunk below that title's own natural length; otherwise pad with spaces up to `TitleColWidth`, plus `titleHostGapFloor` more before the host list. This padding is now **deterministic** from `TitleColWidth` (`layout.TitleColWidth - nameWidth + titleHostGapFloor`), not "whatever's left over" — the old `minRenderedGap` constant (the hard floor on leftover-space padding) is gone; there's no leftover-space computation left for it to floor. One case is unchanged on purpose: when `allHosts` is empty (true for every row, briefly, before the very first host of the *entire run* has reported anything at all), there's no shared column to align to yet — `taskLabel` falls back to fitting the title against the raw `avail` width directly, exactly as every iteration before this one did for that same edge case.

The selected-row rendering (black bold text, light gray title background, per-host colored backgrounds with `halfBlock` transitions between adjacent hosts) keeps its exact previous structure — only the *source* of the `padding` value it consumes changed, from leftover-space arithmetic to the new deterministic formula above; the downstream blending code just consumes `padding` as a plain int either way.

**The row under the cursor renders with its own look, not a flat, widget-applied highlight (`tui.go`).** The desired appearance — black bold text; light gray background confined to the title; each hostname's outcome color as a *background* instead of a foreground, blended into its neighbor — can't be expressed as one `tcell.Style` applied uniformly to a row's whole text, since different runs within the same row need different foreground/background combinations. `treeList` (`treelist.go`) has no built-in per-row highlighting to begin with, so there's nothing to neutralize (back when this was `tview.List`, `list.SetSelectedStyle` had to be set to match `mainTextStyle`'s own colors exactly, as a no-op, to get the same starting point). `playRowText`/`taskLabel`/`hostLabel` each take a `selected bool` that switches their tag construction entirely — `rebuild()` determines which one row is current (see Selection preservation above) and re-renders just that row's text with `selected=true` before `AddItem`.
- **No neutral gap anywhere**: the light gray title background extends through the whole padding gap except the last space before the first hostname; that space, and every hostname's own leading space thereafter, is folded into that hostname's own color block instead of staying a plain, uncolored separator. Deliberately *not* extended to blending the title's own grey into the first hostname's color (see next point) — only the gaps between hostnames get that treatment, per direct request; the title→host0 transition stays a flat handoff.
- **`halfBlock` (U+258C LEFT HALF BLOCK, `▌`)** renders the cell between two adjacent hostnames with the left one's color as foreground and the right one's as background, blending them instead of an abrupt full-cell jump (`hostTransition(leftTag, rightTag)`). Tried on unselected rows too and reverted after visual inspection — looked wrong there, since unselected hostnames are foreground-colored text on a plain background, not background-colored blocks, so there's no matching "two solid colors" context for the blend to sit in. Selected-row-only.
- **`pureBlack = "#1a1a1a"`, not `tcell.ColorBlack` or `"#000000"`**: checked directly against `tcell`'s `FindColor`/`colorfit.go` — on a reduced-palette (256-color, non-truecolor) terminal, a value that exactly matches a base-16 slot's nominal RGB is *always* preferred by `tcell`'s nearest-color search, even when given as a hex value, so `"#000000"` resolves identically to the named `black` — and some terminal themes remap that exact slot to a dark gray rather than true black (the same base-16-vs-fixed-value trap already noted above for `red`/`maroon`). Nudging just off pure black forces selection from the fixed, non-remappable extended-256 grayscale ramp instead (confirmed via the actual escape codes emitted: `38;5;234`, not `30`) — visually indistinguishable from black, immune to that remap.

Two things worth knowing if touching this file:
- `Application.SetInputCapture` maps `Ctrl-C` and `'q'` identically, and their behavior depends on `processDone`: while `ansible-playbook` is still running, both forward `SIGINT` to it (`proc.Signal(os.Interrupt)`) and leave the TUI open so the run's outcome stays visible; once the process has finished, both close the TUI instead. This restores Purpose.md's "Ctrl-C behaves like running ansible-playbook directly" decision, which `tcell`'s raw mode would otherwise silently break — raw mode disables the OS's own Ctrl-C-to-SIGINT delivery, so without this explicit forwarding the child would stop receiving the interrupt it used to get for free.
- `taskLabel`'s width still comes from whatever the list's size was at the last rebuild — but a bare terminal resize is no longer silently ignored: the Resize watcher (above) permanently polls for exactly this once a run is frozen (while still running, `startHeartbeat`'s own unconditional 200ms tick already covers it) and re-triggers a rebuild the moment it notices the width has actually changed.

**Keyboard shortcuts (`tui.go`).** `Keyboard-shortcuts.md` is the source-of-truth reference; this section covers the implementation. The main tree's own key handling (`treeList.InputHandler`, `treelist.go`) natively handles Up/Down/PgUp/PgDn/Home/End/Enter/Space (Space behaves identically to Enter) - deliberately ported from, and verified against, `tview@v0.42.0`'s own `List` (`list.go`) at the time `treeList` replaced it (see Mouse below), minus the features this app never used (shortcuts, secondary text, horizontal scroll). `TextView` (output view) is still real `tview`, and natively handles all of that plus the vim runes `g`/`G`/`j`/`k`/`h`/`l` and Ctrl-F/Ctrl-B (confirmed against `textview.go`/`application.go`). Neither natively handles j/k or Ctrl-A/Ctrl-E; the main tree also has no native Ctrl-F/Ctrl-B/`'G'`.

`SetInputCapture`'s body is three tiers, in order:
1. **Quit** (`q`/Ctrl-C) — unchanged from before.
2. **Universal key aliases**, applied regardless of which page is frontmost: `j`/`k` → synthesize `KeyDown`/`KeyUp`; Ctrl-F/Ctrl-B → `KeyPgDn`/`KeyPgUp`; Ctrl-A/Ctrl-E → `KeyHome`/`KeyEnd`; `'G'` → `KeyEnd`. Returning a *different* `*tcell.EventKey` than the one received makes `Application` forward the synthesized event to whichever primitive is currently focused, exactly as if the user had typed that key (confirmed from `application.go`) — so these ride the exact same code path plain Home/End/PgUp/PgDn already use, on both `List` and `TextView`, with no duplicated logic. This is also what makes `'G'`/Ctrl-E deliberately plain navigation rather than resuming autoscroll: they're indistinguishable, once translated, from the user having pressed the real End key.
3. **Page-specific bindings**, `if viewingOutput { ... } else { ... }`: output view gets Left/Right → `navigateOutputHost` (steps through `outputTask.HostOrder`, no wraparound) and `n`/`p` → `navigateOutputTask` (steps through `tasksForHost(state, outputHost)`, no wraparound); main tree gets `'F'` (the sole surviving "jump to bottom + resume follow" binding — see Autoscroll above), `E`/`C` → `expandAll`/`collapseAll`, Right/Left → `handleRight`/`handleLeft`, `n`/`p` → `navigateMainTask`.

`expandAll`/`collapseAll` set every task's `expanded` entry at once. `collapseAll` has a cursor-fallback: if `currentID` is currently a `hostRowID` (about to disappear), it's reassigned to that row's own task first, so the cursor lands on the now-collapsed task row rather than `rebuild()`'s generic "unknown id → index 0" fallback.

`handleRight`/`handleLeft` act on whichever row is under the cursor right now (`currentRows[list.GetCurrentItem()]`, not `currentID` — the two are normally the same row, but the cursor's on-screen position is what "this element" means here). Right expands a collapsed task; on an already-expanded task, a host row, or a play row, it's a no-op — collapsed→expanded is a one-way trip per keypress, not a "descend into children" gesture. Left collapses an expanded task in place; on a host row it collapses that row's *parent* task and moves `currentID` there (Left always means "close/go up," never a no-op on a leaf); on a play row it's a no-op (plays aren't collapsible — there's no `playNode` expand state to speak of).

`navigateMainTask(delta)` hops the cursor to the previous/next task, via `allTasks(state)` (the host-agnostic sibling of `tasksForHost`, flattening every task across every play in run order) — bounds-checked, no wraparound. If the cursor started on a specific host of the current task, that same host is carried to the destination task, but only if the destination has actually recorded a result for it (`target.Hosts[host]` present) — otherwise the cursor falls back to the destination task's own row, since there's no host row to land on yet. Starting from a play row is a special case with no `allTasks` index to step from: "next" targets that play's own first task, "prev" targets the *previous* play's last task (a no-op from the very first play). Either way, the destination task is force-expanded (`expanded[target] = true`) so the landing row is actually visible.

Closing the output view (`outputView.SetDoneFunc`) now does more than flip `viewingOutput` and switch pages: it sets `expanded[outputTask] = true`, points `currentID` at `hostRowID{outputTask, outputHost}`, and calls `rebuild()` *before* switching back to the main page — so the tree's cursor always reflects whatever the output view was last showing, even if that moved via `navigateOutputHost`/`navigateOutputTask` since the view was first opened, per `Keyboard-shortcuts.md`'s explicit requirement.

**Mouse (`tui.go`).** `app.EnableMouse(true)` (on `NewLiveTUI`'s `app` construction) turns events on. Scrolling in the output view (a plain `tview.TextView`) is free — its wheel handling just pans, and there's no "selected line" concept to fight. The main tree's own mouse handling is now backed by `treeList` (see below) rather than `tview.List`.

The main tree's wheel handling went through two reverted approaches before landing on a real fix. `tview.List`'s own wheel handling only pans an internal `itemOffset`, but `List.Draw()` *unconditionally* re-clamps that offset on every redraw to keep `currentItem` visible (checked directly against `list.go` — there's no flag to disable this), so plain panning could only ever get as far as the current item's own distance from the edge before the next redraw snapped it back. A first attempt drove that clamp instead of fighting it — consuming `MouseScrollUp`/`MouseScrollDown` and moving `currentItem` by one row via `list.SetCurrentItem`, so the clamp itself became the panning mechanism with no cap on range. That traded away more than intended and was reverted: it made the cursor itself visibly move with every wheel tick, which reads as wrong for a wheel/trackpad gesture — confirmed the hard way, since `List.SetCurrentItem` wraps a negative index around to `len(items)+index` (`list.go`, unconditionally — independent of `list.SetWrapAround(false)`, which only ever governed the arrow-key `InputHandler`), so scrolling up from the very first row silently wrapped the cursor to the last row instead of stopping. It also meant every wheel tick ran a full `rebuild()` via the same `SetChangedFunc` path arrow keys use, which — combined with `rebuild()` unconditionally recomputing `now.Sub(startedAt)` even once the run was frozen (see Heartbeat below) — made the top bar's elapsed timer visibly climb again on every wheel tick (and on every arrow-key press) long after the run had actually finished; fixed together with this revert (see Heartbeat's `frozenElapsed` latch). The second attempt just reverted to `List`'s own default wheel handling (plain, already-correctly-bounded `itemOffset` panning, no wraparound, cursor untouched) — a real fix for the cursor-movement and wraparound bugs, but it left the *original*, narrower limitation in place: panning still couldn't move the viewport past wherever the cursor already was, since `List.Draw()`'s clamp is unconditional regardless of what drives `itemOffset`.

**`treeList` (`treelist.go`) replaces `tview.List` for the main tree entirely**, to remove that remaining limitation for real rather than working around it again. It's a minimal, purpose-built `tview.Primitive` (embeds `*tview.Box`, same pattern `List` itself uses) implementing only the slice of `List`'s behavior this app actually exercises: single-line rows (this app never used `List`'s secondary-text mode), no shortcuts, no horizontal scrolling (Left/Right never reach this widget at all — `SetInputCapture` intercepts them itself before dispatch, see Keyboard shortcuts below), and no wraparound. Row text is still rendered through the exported `tview.Print`, the same tag-parsing entry point `List`'s own internal rendering uses, so every existing `[color]...[-]`-tagged row-text producer (`playRowText`/`taskLabel`/`hostLabel`) needed no changes at all.

The key structural difference from `List`: `itemOffset` (the scroll position) and `currentItem` (the cursor) are fully decoupled. `treeList.Draw()` renders whatever `itemOffset` currently is, with no relation to `currentItem` — no per-draw clamp exists at all. Keeping the cursor visible after a *genuine* navigation (arrow keys, `n`/`p`, `F`, closing the output view, the failure-cursor auto-placement, etc.) is instead handled by `ensureVisible()`, called only from `SetCurrentItem` when the index actually changes, and from the widget's own `InputHandler`. This distinction is what makes unbounded panning possible: `rebuild()` calls `list.SetCurrentItem(selectedIndex)` on essentially every redraw (data events, the heartbeat tick, genuine navigation alike — see Selection preservation above), and after `list.Clear()` resets `currentItem` to `-1` with the first `AddItem()` afterward setting it straight to `0` (mirroring `tview.List`'s own `Clear()`/first-`InsertItem()` behavior, kept deliberately for symmetry with the pre-existing `rebuilding`-guarded `SetChangedFunc` handler — see Selection preservation above), that trailing `SetCurrentItem` call looks like a "genuine" index change on nearly every rebuild purely from `treeList`'s own point of view. If `ensureVisible` ran unconditionally there, it would re-clamp the viewport to the cursor on every single rebuild — reintroducing the exact bug this type exists to fix. It's safe specifically because every one of those rebuild-driven calls happens while `rebuilding == true`, and the existing `SetChangedFunc` handler in `tui.go` already no-ops entirely while that flag is set — so `ensureVisible`'s side effect on the viewport happens, but the callback that would otherwise treat it as user navigation (and disengage `following`) never fires. Mouse wheel panning (`treeList.MouseHandler`, ported from `list.go`'s own bounded scroll-up/scroll-down logic almost verbatim) touches only `itemOffset` directly, calling neither `SetCurrentItem` nor `ensureVisible` — so it never triggers a rebuild or a viewport snap-back at all, and can move arbitrarily far from wherever the cursor happens to be, in either direction, bounded only by the actual row count (no wraparound). `app.SetMouseCapture` at the `tui.go` level still exists solely to set `following = false` on a wheel event before it reaches `treeList.MouseHandler`, since panning-only never fires `SetChangedFunc` the way keyboard navigation does.

`revealExpandedTask` (see above) is unaffected by any of this: it already called `SetOffset` directly rather than relying on any clamp, specifically because the cursor staying on the task row itself while its newly-expanded children need revealing was never something a `currentItem`-driven clamp would help with in the first place — true of both `List` and `treeList`.

`treeList`'s click handling (`MouseHandler`'s `MouseLeftClick` case) ports `list.go`'s exact ordering: a row's own `selected` callback fires *before* `SetCurrentItem` moves the cursor there, matching `tview.List`'s own click ordering (`Selected()`, then `changed` only if the index actually differs) — needed because a click's own effect (a task's expand/collapse toggle, or opening a host's output) may itself trigger a `rebuild()`, and that must happen before the cursor-move callback fires against the post-rebuild row list. A single click on a host row still opens its output on the first press (identical to Enter) — no separate double-click wiring is needed on top of that, same as before.

**Filtering (`tui.go`).** `Filters.md` is the feature spec; both steps - the `A`/`C`/`F` filters and the `M`/"Contents" search filter - are implemented. `filterMode` is an `int` enum (`filterAll`/`filterChanged`/`filterFailed`/`filterSearch`) for the *kind* of filter; `filterQuery` bundles it with the search term (`{mode filterMode; search string}`) into the one value everything actually passes around as "the current filter," since `filterSearch` alone doesn't say what to search *for*. Both fields are comparable (an `int` and a `string`), so switching filters is still a plain `!=` - deliberately not also carrying `sourceIndex` (needed by the search predicate), since that's a `map` and maps aren't comparable in Go; it travels as its own separate parameter everywhere instead, the same parameter `NewLiveTUI` already receives and passes to `formatHostOutput`. `NewLiveTUI`'s local for the currently active one is named `currentFilter`, not `filterQuery` - that specific name collision was a real compile error hit once during development (a local variable's name always wins over a same-named package-level type within its own scope, including in later statements in the same scope that need the type), not a hypothetical worth avoiding preemptively.

`taskVisible(t *taskNode, q filterQuery, sourceIndex taskSourceIndex, isActive bool) bool` is the single predicate everything else in this feature is built from. Per Filters.md, a task's status for filtering purposes is host-level, not task-level: it matches "Changed"/"Failed" if *at least one* of its hosts has that outcome - a task can have hosts in different states, and there's no single aggregate "this task's status" otherwise. `outcomeUnreachable` counts as a failure for this purpose too (folded into both "Changed" and "Failed"), matching the same bucketing `lastFailedTaskAndHost`/`genuineFailure` already use for the auto-jump-on-failure feature - not explicitly specified in Filters.md, but chosen for consistency with that existing precedent rather than leaving Unreachable-only runs unable to match anything but "All". `isActive` (true for the run's current in-progress task, `state.CurrentTask()`, nil once frozen - see Heartbeat above) always forces a match regardless of filter, per Filters.md's explicit requirement: an in-progress task may simply not have recorded any host outcome yet (or any output to search, for `filterSearch`), and hiding it until one arrives would make it flicker in and out of view. `activeTaskNow()` is `NewLiveTUI`'s single source of truth for this (`nil` if `processDone`, else `state.CurrentTask()`) - extracted from what `rebuild()` used to compute inline, once `navigateMainTask`/`navigateOutputTask`/`applyFilter` (all outside `rebuild()`) also needed the identical value to stay consistent with what `flattenRows` is about to render.

**The search filter's own matching (`taskMatchesSearch`, `taskOutputText`).** Per Filters.md's "Contents" user story, a task matches if the term is found (case-insensitively, plain substring - no regex/fuzzy matching, matching this project's existing "documented heuristic, not chased further" style elsewhere, e.g. `taskLabel`'s truncation or `primaryOutputField`'s own stdout-vs-msg choice) in any of three places: the task's own title (`t.Name`); its source ("ansible command" in Filters.md's wording, interpreted as the task's own YAML - the exact same `sourceIndex[task.Path]` text `formatHostOutput`'s `TASK:` section already shows); or any host's Output - `taskOutputText` decodes `t.Raw[host]` and calls `primaryOutputField` on it, the same decode-then-extract path `outputSummary`/`formatHostOutput` already use, so "the output" means the same thing everywhere in this app rather than introducing a second definition of it just for search. An empty search term matches everything (same as `filterAll`) rather than hiding everything - chosen so that applying an empty box (e.g. clearing it and hitting Enter by accident) doesn't look like the feature is broken.

`flattenRows` applies `taskVisible` per task, skipping non-matching ones entirely - when a task matches, *all* of its hosts are still shown, not just the matching ones (Filters.md is explicit about this: filtering hides whole tasks, never individual host rows within a shown task). A play whose tasks are all filtered out gets no row either, the same rule (and same mechanism - both are just "was anything appended for this play" checks) as a play with zero *executed* tasks.

Three helper functions mirror this filtering for navigation, so nothing ever targets a task `flattenRows` wouldn't actually have rendered a row for: `visibleTasks`/`visibleTasksForHost` are `allTasks`/`tasksForHost`'s filtered siblings (same run order, just skipping non-matching tasks), used by `navigateMainTask` (`n`/`p` in the main tree) and `navigateOutputTask` (`n`/`p` in the drill-down view) respectively - both per Filters.md's explicit requirement that filtered-out tasks are skipped during navigation, not just hidden from the initial view. `navigateMainTask`'s play-row case (`n`/`p` starting from a play row) needed a genuine rework, not just a swap-in-the-filtered-list: the old logic looked at `state.Plays[playIdx-1].Tasks[last]` directly, which breaks once a whole intervening play can be entirely hidden - reformulated instead around position within the flat `visibleTasks` sequence itself (`firstVisibleTask` finds the play's own first visible task; "prev" is just whatever precedes it in that flat sequence), which correctly skips over any number of fully-hidden plays for free, without needing to search play-by-play backward for one that still has something visible.

**Cursor fallback on a filter switch (`tui.go`'s `applyFilter`).** Per Filters.md, if the filter changes and the row the cursor was pinned to disappears, the cursor should land on the nearest still-visible task rather than snapping to the top of the list. This only needs to run when `following == false`: when it's `true`, `rebuild()` already re-resolves the selection to the newest *visible* row on every call regardless of what disappeared, so there's nothing to fix up. `nearestVisibleTask(all, anchor, visible)` walks `allTasks(state)` forward from `anchor`'s position looking for the first task present in the new filter's `visibleTasks` result, falling back to searching backward if nothing survives after it - "removed" always means a whole task (and, transitively, a whole play with nothing left) disappearing at once here, never an individual host row on its own (see `taskVisible` above), so a task is always the right granularity to land on, unlike `collapseAll`'s existing host-row fallback (which snaps to the row's own now-collapsed parent task - a case that still exists, just structurally different from what a filter switch produces). The anchor resolution differs slightly by what the cursor was on: a `*taskNode`/`hostRowID` anchor is that task itself; a `*playNode` anchor is only set (to the play's first task) if *none* of that play's own tasks survive the new filter - if at least one does, the play's own row is untouched by the switch and needs no fallback at all. This path is shared by all four filter kinds - `applyFilter` doesn't know or care whether the switch came from `a`/`c`/`f` or from typing a new search term and pressing Enter.

**Filter and search dialogs (`tui.go`'s `NewLiveTUI`, `centeredModal`).** Two separate `Pages` entries (`"filter"`, `"search"`), both added *last* (after `"main"`/`"output"`) so they draw on top (`Pages` draws visible pages back to front in the order they were added, confirmed against `pages.go` - getting this ordering wrong was a real bug hit during development: adding a dialog page first drew it underneath the others, invisibly). Shown/hidden via `ShowPage`/`HidePage` rather than `SwitchToPage`, which is what makes each a true overlay rather than a full page swap like the output view - the other pages' `Visible` flags are left alone. `centeredModal(p, width, height)` wraps each dialog's contents in nested fixed-size `Flex`es (the standard tview pattern for a partial-screen overlay, since `Pages` itself has no built-in centering) to get a small, screen-centered box regardless of the terminal's actual size.

These were originally one combined dialog (`a`/`c`/`f`/`m` all in the same menu, `m` moving focus into a search box that was also part of that same layout). Split into two after live use showed the combined version made it too easy to hit the wrong key. `filterDialog` (opened by `f`) is a plain `tview.TextView` - `filterDialogText` renders a static `a`/`c`/`f` menu, no text entry at all. `searchDialog` (opened by `/`) is a headline `TextView` plus a real `tview.InputField` (`searchInput`) stacked in their own `Flex` (`searchDialogFlex`) - a `TextView` can display text but never accepts edits, and search needs genuine text entry. Unlike the old combined dialog's search box (which started unfocused, needing `m` to activate), `openSearchDialog` calls `app.SetFocus(searchInput)` immediately - there's nothing else in this dialog to browse first, so there's no "menu mode" to be in before typing. It still pre-fills the box from `currentFilter.search` whenever `currentFilter.mode == filterSearch`, per Filters.md's "reopening the dialog while a search filter is already active shows the previous term right away."

Both dialogs are modal - mouse is fully blocked via `SetMouseCapture` checking `filterDialogOpen || searchDialogOpen` first and swallowing everything, same reasoning as before (neither dialog needs mouse interaction, and a dialog's own `MouseHandler` would only ever block clicks landing inside its own small rect, not ones landing elsewhere on the treeview underneath) - but the two are modal in *different ways*, and that difference is the entire reason they're two dialogs instead of one:

- `filterDialogOpen` (checked in `SetInputCapture`, after the Ctrl-C check but before the vim-alias translation block, the `viewingOutput` branch, and the plain `q`-quit check) is a discrete-key menu: every key except Esc/`q`/`a`/`c`/`f` is swallowed outright. `q` closes it *without* quitting - deliberately different from bare `q` everywhere else in the app - because in a plain menu with no text entry, pressing `q` is almost always a reflex to close the thing, never a considered decision to quit. (The dialog *displays* `a`/`c`/`f` as `A`/`C`/`F` to stand out next to each option's description - `filterDialogText`'s own rendering choice, independent of what `SetInputCapture` actually listens for, which is lower case.)
- `searchDialogOpen` (checked immediately after the Ctrl-C check, before even `filterDialogOpen`) is the opposite: every key except Ctrl-C is returned completely untouched (`return event`), letting `tview.InputField`'s own native editing (typed runes, backspace, arrow keys, its own emacs-style Ctrl-A/Ctrl-E-within-the-field bindings, etc.) run exactly as it would in any other tview app - including `q`, `a`, `c`, `f`, and anything else that's a shortcut elsewhere, since a real search term can legitimately contain any of those letters (`q` was the concrete case that mattered: "request", "queue", etc.). There's no "q closes this one too" here at all, unlike the filter dialog - a search box has no invalid keystrokes to rescue the user from the way a menu does.

Ctrl-C is the one behavior explicitly shared, unconditionally, by both dialogs *and* every other part of the app: checked first in `SetInputCapture`, before `filterDialogOpen`/`searchDialogOpen` are even looked at, it always closes whichever dialog is open (`closeDialogs()`, a harmless no-op if neither is) and *still* performs the normal abort/quit (`proc.Signal(os.Interrupt)` if running, `app.Stop()` if not) - per Purpose.md's "Ctrl-C behaves like running `ansible-playbook` directly" guarantee, which this project treats as exception-free. The rationale volunteered for this whole q/Ctrl-C split: pressing `q` is frequently just reflexive "get me out of here," where intent is genuinely ambiguous, but Ctrl-C's intent (abort, now) is never ambiguous - so it's the one key that's allowed to do both things (close *and* abort) at once.

`searchInput.SetDoneFunc` (fires on Enter/Esc/Tab/Backtab - `InputField`'s own fixed "done" key set, confirmed against `inputfield.go`) is where the search dialog actually closes on a non-Ctrl-C path: Enter applies the typed text via the same `applyFilter` every other filter kind uses (`filterQuery{mode: filterSearch, search: ...}`); Esc/Tab/Backtab all just call `closeDialogs()` - there's nothing else in this one-field dialog to Tab to, and Filters.md only ever specifies Esc for "close with no change" anyway. `closeDialogs()` (shared by both dialogs' Esc/q paths, the Ctrl-C path, and `applyFilter`) resets both `filterDialogOpen`/`searchDialogOpen`, hides both pages, and calls `app.SetFocus(list)` unconditionally (a harmless no-op on the `filterDialog` paths, where focus never left `list` in the first place) - needed so keyboard input reaches the main tree again immediately, rather than tview's focus pointer being left stuck on the now-hidden `InputField`.

## Rerun (Rerun.md)

Re-running a finished playbook — the whole thing again, or from a specific task, with editable tags/hosts — without leaving Tangsible, plus the equivalent from the command line via a `rerun` verb. Built in four dependency-ordered phases (verb/history plumbing → process-restart mechanics → the dialog → the `rerun` verb); the sections below follow that same order.

**Invocation history (`rerunargs.go`, `history.go`).** `.tangsible` now accumulates history alongside its original `[general].default_playbook` (`playbookConfig.History []playbookHistory`, `playbookConfig.General.LastPlaybook` — both deliberately added to the *existing* struct rather than a new one, since the format's own spec always expected it to grow). `appendInvocation(path, playbook, argsString)` is the single funnel every invocation of either verb goes through: it caps `Invocations` at `maxHistoryPerPlaybook` (20, arbitrary — "enough to be useful without growing forever," no principled number behind it) per playbook, oldest dropped first, and — same call, same write — sets `General.LastPlaybook = playbook`, which is what makes it possible to answer "which playbook was run most recently" at all. That's a real question `History` alone can't answer: `History` preserves *first-seen* order (a playbook's entry stays wherever it was first appended, even if run again later), not recency — `LastPlaybook` is a separate field specifically because reordering `History` itself on every touch would make hand-inspecting the file more confusing for no benefit. `lastPlaybook(cfg)` reads it back, with one fallback: if unset but `cfg.History` has exactly one playbook entry, that entry wins anyway — a real gap, not hypothetical, covering a `.tangsible` written entirely by a build that predates `LastPlaybook` (has `[[history]]`, no `general.last_playbook`); a single-playbook project isn't actually ambiguous even without a recorded answer, since there's only one candidate. Two or more playbooks with no `LastPlaybook` genuinely can't be disambiguated this way and correctly fall through to "not ok."

Each `Invocations` entry is one generation's full passthrough-arg list, collapsed to a single string via `argsToHistoryString`/`historyStringToArgs` (`rerunargs.go`) — the same shape the user would type after the playbook name on the command line, including `""` for "no args at all." A minimal, POSIX-ish tokenizer (single/double-quoted spans, backslash escaping inside double quotes and unquoted text) handles values containing spaces or quotes (`-e msg="hello world"` round-trips correctly) — not a general shell parser (no variable expansion, no command substitution: neither is meaningful for a stored, literal argument list), good enough for this project's own invocation patterns, not chased further, same "documented heuristic" style as `taskLabel`'s truncation or `primaryOutputField`'s stdout-vs-msg choice elsewhere in this codebase.

`parsePassthroughArgs(args) parsedPassthroughArgs{Tags, Hosts, Rest}` (`rerunargs.go`) pulls `--tags`/`-t` and `--limit`/`-l` out of an already-tokenized arg list — both `--flag value` and `--flag=value` forms, multiple occurrences comma-joined into one value (not attempting to replicate `ansible-playbook`'s own per-flag merge-vs-override semantics, just giving one editable value per dialog field) — leaving everything else in `Rest`, untouched and in original order. An attached short form like `-tfoo` (no separator) isn't recognized and falls through to `Rest` — an accepted, documented gap, not chased further. `.Reassemble()` is the inverse, always emitting the long-form flags regardless of which form the original used (round-tripping the exact original spelling isn't worth tracking separately). This is what both the re-run dialog's Tags/Hosts pre-fill and the final "what args does this generation actually run with" reconstruction are built on.

**Process-restart mechanics (`main.go`).** Starting a second (or third, or Nth) `ansible-playbook` invocation without exiting Tangsible meant the child-process lifecycle — previously a single, unrepeatable sequence baked into `main()` — had to become something callable more than once, while the *TUI itself* never restarts: `tview.Application.Run()` is still called exactly once, for the process's entire lifetime; "starting a new generation" means spawning a new child and streaming its events into the *same already-running* `app` via the same `QueueUpdateDraw`-wrapped `applyLive` closure every generation already shares.

- `procHandle` (a thin `atomic.Pointer[os.Process]` wrapper) replaces the plain `*os.Process` `NewLiveTUI` used to take once at construction — Ctrl-C/`q` forwarding (`tui.go`'s `SetInputCapture`) now reads `procH.Load()` fresh every time, so it always signals whichever generation is actually current. Never observed nil once the first `spawnGeneration` call has run: that first call always happens before the TUI (and so before `SetInputCapture`) can receive any input at all, and every later `Store` only ever replaces an already-non-nil value.
- `spawnGeneration(playbook, args, procH) (cmd, stdoutCh, stderrLines, err)` is the shared "start one invocation" step — `exec.Command`, env, pipes, `cmd.Start()`, `procH.Store(cmd.Process)`, `scanEvents`/`streamStderr` wiring — identical for the very first generation and every rerun since.
- `runGeneration(cmd, stdoutCh, stderrLines, peeked...)` drains one generation's stdout to completion (starting from whatever was already peeked off it, if anything — see below), waits for the process, computes its exit code, and records a `generationOutcome{exitCode, waitErr, childStderr, diagnostics}`. `main` now accumulates one of these *per generation* (`outcomes []generationOutcome`, mutex-guarded) instead of the old single `runResult` sent once down a `resultCh` — necessary because a rerun's own tree is gone from the screen by the time Tangsible finally exits (a rerun forgets the previous generation's results, per Rerun.md), so its stderr/diagnostics would otherwise be lost entirely rather than just delayed. All accumulated outcomes print in generation order once `app.Run()` returns (each still individually suppressing its own stderr on a 99/user-interrupted exit); only the *last* one decides Tangsible's own process exit code, via `genuineFailure` (`tui.go`) — reused here rather than re-derived, so the two can't silently drift apart on what "failed" means, replacing `main`'s own previously-duplicated `benignHostUnreachable` computation.
- `requestRerun(startAtTask, tags, hosts string)` — passed into `NewLiveTUI`, called once the re-run dialog is confirmed (see below) — is the actual restart trigger: synchronously resets `state` (`playbookState.Reset()`, `aggregate.go` — clears `Plays`/`AllHosts`/`HadUnreachable`/current play/task back to zero, deliberately leaving the `On*Added`/`OnHostRecorded` hooks wired, since those are what let the next `Apply` sequence grow a fresh tree the same incremental way the first one did) plus `exitCode`/`processDone`, reassembles the new arg list (`startAtTask`, if non-empty, prepended as `--start-at-task`; `tags`/`hosts` from the dialog; everything else — inventory, extra-vars, verbosity — carried forward unedited from the *original* invocation's own `Rest`, since the dialog never exposes it for editing), records it into `.tangsible` (silently on failure here specifically — unlike the top-level `run` call, the TUI's alternate screen is already active by this point, so nothing can be printed without corrupting the display), then spawns the new generation in a fresh goroutine. A spawn failure here (rare — `ansible-playbook` vanishing, a pipe failing) is *not* fatal the way it is for the very first invocation: the TUI already exists and the user is mid-session, so it's just recorded as this one generation's own failed outcome (`exitCode: -1`) instead of exiting the whole program.
- `run` vs. `rerun` diverge only in how their *first* generation starts, converging on everything above: `run` spawns immediately and runs the pre-flight gate (peeking one item off `stdoutCh` before ever constructing the TUI — see "The TUI is never shown..." above) exactly as before, handing the result to `main` as a `pendingGeneration{cmd, stdoutCh, stderrLines, first}`; `rerun` constructs the TUI with `pending == nil` and `processDone` pre-set `true` (see `startWithRerunDialog` below) and starts nothing until the user confirms the startup dialog — which fires the *exact same* `requestRerun` path every later re-run already uses, rather than a separate first-generation code path. `rerun` has no pre-flight gate of its own: by the time anything spawns, its TUI is already visible, so a pre-flight failure has nowhere to hide from and nothing to skip — it just renders as a failed, zero-event generation like any other (see `everStarted` below for why that renders correctly rather than misleadingly).

**The re-run dialog (`tui.go`).** `rerunForm` is a real `tview.Form` — the first multi-field input this app needed, and the first place `Form`'s own Tab/Backtab focus-cycling is used instead of hand-rolling it (unlike `treeList`, which replaced `tview.List` because *its* behavior fell short — here `Form`'s default behavior already matches what's needed). Three plain `tview.InputField`s (`taskField`/`tagsField`/`hostsField`), built directly rather than via `Form`'s `AddInputField` convenience method so `openRerunDialog`/`submitRerun` can keep direct references.

The original design paired `taskField` with a `startAtTaskCheckbox` gating it via `SetDisabled` (pre-filled from the cursor's current task either way, disabled/greyed until checked) — dropped after live testing (via tmux `send-keys`/`capture-pane`, not a human) surfaced a genuine `tview` quirk: `InputField.SetDisabled()` unconditionally calls its own `finished(-1)` internally, which — once any real Tab/Enter has happened anywhere in the form's lifetime — `Form`'s shared handler (`form.go`) treats as "repeat the last navigation key." So toggling the checkbox silently advanced focus by one, *in addition to* whatever Tab the user pressed right after — text reproducibly landed one field over from where it was typed. Confirmed against `form.go`/`inputfield.go`/`checkbox.go` directly rather than guessed. Rather than fight that side effect, the dialog fell back to the plainer alternative agreed as the explicit contingency for exactly this outcome: no checkbox, `taskField` always enabled, never pre-filled from the cursor (unlike Tags/Hosts — see below), empty means "whole playbook," matching Tags/Hosts' own "remembers whatever was last typed across reopens" behavior for consistency rather than special-casing it.

`rerunDialogOpen` follows `searchDialogOpen`'s modal style, not `filterDialogOpen`'s (see Filtering below) — every key but Ctrl-C passes straight through to whichever field has focus, since any field might legitimately contain `q` or any other shortcut letter. The two exceptions, handled centrally in `SetInputCapture` rather than via each field's own `SetDoneFunc`: **Escape** — because `Form`'s own default Escape behavior (reset focus to the first item, unless a cancel func is set) isn't what's wanted; Esc should close the dialog outright, per Rerun.md. **Enter** — because `tview.Form` treats Enter identically to Tab on a `FormItem` (just advances focus, confirmed against `form.go`'s own `Focus()`), never submits on its own, so submission has to be driven from here regardless of which field currently has focus, matching Rerun.md's "Re-run shall be initiated by pressing return" for the whole dialog, not just one field. `openRerunDialog` pre-fills Tags/Hosts from `initialTags`/`initialHosts` (`NewLiveTUI` params, computed once from the session's own baseline `originalArgs` in `main.go`) only the first time each is opened while still empty; `submitRerun` reads the form's current values, resets the same view-state latches (`expanded`/`currentID`/`following`/the freeze latches) and restarts the heartbeat ticker (`startHeartbeat`, pulled out of `NewLiveTUI`'s constructor into a named, re-callable closure specifically for this — the original ticker permanently exits once it observes `processDone`) that `requestRerun` itself used to reset directly back in Phase B, before the dialog existed.

`startWithRerunDialog` (`NewLiveTUI` param, true only for the `rerun` verb's own startup) opens the dialog immediately instead of waiting for `r`, with `processDone` expected already `true` (set by `main` before construction) — accurate ("no generation is in flight"), even though nothing has actually run yet. That one distinction — "frozen because nothing has started" vs. "frozen because a run finished" — is exactly what `everStarted` (`NewLiveTUI` local, `!startWithRerunDialog` initially, latched `true` inside `submitRerun`) exists to paper over: `rebuild()`'s status-row append is now gated on `frozen && everStarted`, not `frozen` alone, since without it a fresh `rerun` invocation would render a "Playbook completed successfully" status line before anything had ever run (`exitCode` defaults to 0). The failure-cursor-placement latch (`failureCursorPlaced`) needed no equivalent gate — it's already unconditionally reset inside `submitRerun`'s own view-state reset, so a premature latch during the pre-confirmation window is harmless, self-healed before the real first generation begins.

**The `rerun` verb (`rerunresolve.go`, `main.go`).** `resolveRerun(args, cfg) (rerunResolution{Playbook, Tags, Hosts, Rest}, ok)` is a pure function (no I/O of its own — `main` is the only caller, and the one that actually reads `.tangsible` and prints the resolution note) implementing Rerun.md's precedence rules: an explicit CLI playbook (via `splitPlaybookArgs`, same shape-based detection `run` uses) wins over `lastPlaybook(cfg)`; CLI `--tags`/`-l` (parsed via the same `parsePassthroughArgs` the dialog's own pre-fill uses) win over that playbook's own `lastInvocation` history; any *other* CLI passthrough arg (e.g. a custom `-i`) replaces history's `Rest` outright rather than merging with it — "whatever you actually typed wins for its own category, whatever you didn't type falls back to history." A playbook with no history at all resolves every field to its zero value with no special-casing needed: `historyStringToArgs("")` is `nil`, and `parsePassthroughArgs(nil)` is the zero `parsedPassthroughArgs` — exactly Rerun.md's "or no arguments if never run for this playbook." `ok` is false only when no playbook could be determined at all (no explicit one, no `lastPlaybook`), which `main` treats as a usage error, same shape as `run`'s own "no playbook given, and none could be determined."

`main`'s `verbRerun` case never records anything into `.tangsible` itself — unlike `run`, which always records immediately (the invocation already happened by definition), a `rerun` invocation the user Ctrl-C's out of before ever confirming the dialog leaves no trace, since nothing was actually invoked. Recording only happens once `requestRerun` fires, from inside `submitRerun` — for `rerun`'s own first generation exactly as much as for any later one, since both go through the identical path.

**Test fixtures (`testdata/`).** Playbooks (and inventory files) used to manually exercise the aggregation logic: `basic.yml` (simple sequential tasks including a sleep, demonstrates live streaming), `outcomes.yml` (single host, all four original outcome buckets including an ignored failure), `multihost.yml` + `multihost-inventory.ini` (two hosts diverging on the same task, to exercise per-host aggregation within one task), `hostnames.yml` + `hostnames-inventory.ini` (varied-length hostnames to exercise `taskLabel`'s shrink algorithm, plus a host pointed at an unreachable address with a short SSH connect timeout, to trigger `v2_runner_on_unreachable` for real — run with `--forks 1` to serialize per-host completion for an observable grey-to-lit transition).

## Current scope constraints (from Purpose.md)

These aren't accidental omissions — they're explicit v1 decisions and should inform what "done" means for near-term work:

- No *browsable* run history within the TUI itself — a rerun still forgets the previous generation's tree (see Rerun above), and there's no way to page back through past runs' results. `.tangsible` does now remember past invocation *arguments* (Rerun.md) - that's argument history for re-running, not a results/outcomes history; revisit the browsable-results question separately if it's ever needed.
- `--ask-become-pass`/`--ask-vault-pass` need no implementation at all - verified empirically (`--ask-vault-pass` against a throwaway vaulted fixture, run live via `tangsible run ... --ask-vault-pass` under tmux; `--ask-become-pass` inferred rather than separately tested, since `ansible.cli.CLI.ask_passwords()` drives both through the identical prompt mechanism, only what happens *after* the password differs), not assumed. The reason it works with zero code changes: both are asked once, up front, during `ansible-playbook`'s own bootstrap, strictly before any jsonl event ever fires - the same pre-flight window `main.go` already treats specially (TUI construction is deferred until the first real event arrives, via the `first, ok := <-stdoutCh` peek). Python's `getpass.getpass()` (what both flags use) always tries opening `/dev/tty` directly first, falling back to `sys.stdin` only if that fails entirely (no controlling terminal at all) - since the child inherits Tangsible's own controlling terminal/session by default (`spawnGeneration`, `main.go`, no special `SysProcAttr` detaching it), that open succeeds, and the prompt renders on the real terminal in its normal (non-raw, non-alternate-screen) state, since `tcell`/`tview` haven't initialized yet at that point. No terminal-arbitration machinery needed - the existing architecture already keeps out of the way by construction.
- Genuinely still unsupported: interactive input requested *after* the TUI already owns the terminal. A bare `pause:` task (no `seconds:`/`minutes:`) was checked empirically too (a throwaway fixture, `tangsible run` under tmux) rather than assumed: it does *not* hang - Ansible's own `pause` action plugin detects non-interactive stdin and skips waiting immediately, completing with `rc: 0`, `changed: false`, and a `warnings: ["Not waiting for response to prompt as stdin is not interactive"]` entry embedded in the task result (visible via the drill-down view, `formatHostOutput`'s full-JSON fallback - not surfaced anywhere else; no `[WARNING]:` line appears on stderr, likely because `ansible.posix.jsonl` doesn't implement whatever hook the default display callback uses for that). A timed `pause: seconds:`/`minutes:` is a pure sleep and was never in question - no stdin involvement at all. A `vars_prompt` on any play after the first would likely hit the same problem as a bare `pause:` (untested) - unlike `--ask-become-pass`/`--ask-vault-pass`, it isn't guaranteed to happen before the TUI takes over. `--step` was checked empirically too (`tangsible run ... --step` under tmux) and is worse than `pause:`, not just similarly affected: its first confirmation prompt fires right after `v2_playbook_on_play_start` - the same event that opens the pre-flight gate and constructs the TUI - so by the time `ansible-core`'s `StrategyBase._take_step` calls `display.prompt()` (a bare Python `input()`, with none of `pause`'s own non-interactive-stdin detection), stdin is no longer a readable line stream and it crashes outright: an unhandled `EOFError` surfaces as `ansible.errors.AnsibleError: Unexpected Exception, this is probably a bug` with a full traceback on stderr, exit code 250 - not a graceful skip, not a hang. If a mid-run prompt is ever made to actually work, `tcell.Screen.Suspend()`/`Resume()` (built for exactly "hand the terminal to something else temporarily") looks like the right primitive - unexplored beyond that; the same fix would cover `--step` too, since it's the identical class of problem.
- **`strategy: free` shows nothing at all** — confirmed live (a two-host, two-task `strategy: free` fixture run through the real `tangsible` binary under tmux), not just inferred from reading the code. `ansible-playbook`'s jsonl callback never emits `v2_playbook_on_task_start` under `free` - confirmed directly against the raw event stream (`ANSIBLE_STDOUT_CALLBACK=ansible.posix.jsonl` piped straight to a small Python dumper): only `v2_runner_on_start`/`v2_runner_on_ok` fire, per host, as each host independently reaches a task, with no shared "this task starts now" moment the way `linear` (the default, and the only strategy this app was ever designed around) has one. `aggregate.go`'s `Apply()` only ever creates a `playNode` or advances `currentTask` inside the task-start case (`case "v2_playbook_on_task_start", "v2_playbook_on_handler_task_start"`) - since that case never fires under `free`, `currentPlay` stays `nil` for the entire run, and every `recordHost` call hits its `if s.currentTask == nil { return }` guard and silently drops the result. Net effect, watched live: the tree stays completely empty the whole run - no play, no task, no host, just the top bar's ticking spinner and a final "Playbook completed successfully" over a blank screen - while the playbook itself runs and finishes correctly underneath. Not a partial degradation or a cosmetic gap; real data that's silently never recorded. Fixing this isn't a small patch: the entire data model assumes one `currentTask` shared by every host (this file's own Aggregation section says as much), which `free` structurally violates - a host-scoped "current task per host" tracking scheme, with task identity inferred some other way since there's no task-start event to key off at all, would need to reach `taskNode`'s own shape, the shared host-column layout (`computeHostColumnLayout`), filtering, and task-hop navigation, not just `aggregate.go`. Treated as a distinct, not-yet-planned effort rather than an incremental fix.
- Ctrl-C should behave the same as it does when running `ansible-playbook` directly — implemented, see `tui.go`'s `SetInputCapture` note above.
- Target scale is ~10 hosts, not hundreds/thousands — this is an interactive dev tool, not a fleet-management tool.
- Only a limited subset of `ansible-playbook`'s CLI surface should be exposed initially; expand only as needed.
