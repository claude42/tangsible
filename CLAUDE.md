# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Tangsible is a TUI wrapper for `ansible-playbook`, aimed at interactive use (e.g. during development). The problem it solves and the product decisions behind it are documented in `Purpose.md` — read that first for the "why" before making design choices; this file only covers the "how".

The TUI (built with `tview`) is live: it comes up immediately and updates incrementally as jsonl events arrive, while `ansible-playbook` is still running — arrow-key/j-k navigation (no wraparound at the ends), Enter/Space to expand/collapse a task's host rows, cursor Right/Left to expand/collapse a task directly, `E`/`C` to expand/collapse every task at once, `n`/`p` to hop to the next/previous task (preserving the selected host across tasks where possible), Home/End/`'G'`/Ctrl-A/Ctrl-E to jump to the first/last row, `q`/Ctrl-C to quit (or, while the process is still running, to interrupt it — see below). The view auto-follows the newest row while nothing has been navigated away from; disengages the moment the user scrolls (including via End/`'G'`/Ctrl-E, which are deliberately plain navigation), and only `'F'` re-engages it. Full shortcut reference: `Keyboard-shortcuts.md`. Play rows are white and bold; task rows are a plain regular gray. A task's collapsed row shows every host discovered so far this run, right-aligned, each individually colored by its outcome for that task (green/yellow/cyan/red/maroon for OK/Changed/Skipped/Failed/Unreachable) or grey if it hasn't reported for that specific task yet — not aggregate counts. The row under the cursor renders differently from a flat highlight: black bold text throughout, a light gray background on the title, and each hostname's outcome color as a background instead of a foreground, with adjacent hostnames' colors blended together in the cell between them. An expanded host row shows its outcome plus a short contextual detail where one's defined — OK shows the single line of output verbatim or a line count; Skipped shows its `skip_reason`/`false_condition`. Expanding a task and pressing Enter/Space on one of its host rows opens a full-screen view of that host's complete result for that task (one of MSG/STDOUT plus STDERR, plus the full result as JSON); Escape or Enter closes it, leaving the tree's cursor on whatever (task, host) was last shown there. While that view is open, cursor Left/Right switch to the previous/next host for the same task, and `n`/`p` switch to the previous/next task for the same host. The top and bottom bars are white-on-navy. The top bar ticks a spinner + total elapsed time so it's visibly obvious the app hasn't hung, freezing once the run finishes; whichever task is currently active also shows that same spinner frame next to its title. Because it opens a real terminal UI, running it requires an actual TTY (not a piped/headless shell).

## Commands

```
go build ./...                                    # build
go vet ./...                                       # lint
go run . <playbook.yml> [ansible-playbook args...] # run
```

Try it against the bundled fixtures, e.g.:
```
go run . testdata/outcomes.yml -i localhost,
go run . testdata/multihost.yml -i testdata/multihost-inventory.ini
```

No tests exist yet; once added, run with `go test ./...` (`go test -run <Name> ./...` for a single test).

Running it requires `ansible-playbook` and the `ansible.posix` collection (`ansible-galaxy collection install ansible.posix`) to be installed locally.

## Architecture

**Data source.** The app never talks to Ansible's Python API and never implements a custom callback plugin (deliberately — see Purpose.md's Platform section for the rationale). Instead it shells out to `ansible-playbook` as a subprocess with `ANSIBLE_STDOUT_CALLBACK=ansible.posix.jsonl` and `ANSIBLE_JSON_INDENT=0` set in its environment. That callback writes one JSON object per line to stdout as each event happens, which is what makes live consumption possible — the built-in `json` callback was considered and rejected because it buffers everything and only writes a single blob after the run completes. Pinning `ANSIBLE_JSON_INDENT=0` guards against a user's `ansible.cfg` overriding the default and breaking the one-event-per-line assumption the line-based scanner depends on.

**Concurrency (`main.go`).** The TUI (`app.Run()`) and the event stream now run concurrently, coordinated by two `atomic.Bool` flags:
- `processDone` — set once `cmd.Wait()` returns; read by `tui.go`'s input-capture handler to decide whether Ctrl-C/`q` should interrupt the child or close the TUI (see below).
- `quitting` — set once the user has actually chosen to quit (or, defensively, right after `app.Run()` returns for any reason); read by `streamEvents` before every event so it stops pushing updates into a closed/closing UI.

`streamEvents(r io.Reader, applyLive func(rawEvent), quitting *atomic.Bool) []string` reads stdout line-by-line and calls `applyLive(ev)` for each decoded event — `applyLive` (from `tui.go`'s `NewLiveTUI`) wraps `app.QueueUpdateDraw(func() { state.Apply(ev) })`, so `state.Apply` (and the hooks it invokes, see Aggregation below) always runs on tview's event-loop goroutine. Once `quitting` is set, the loop keeps draining `r` (so `ansible-playbook`'s stdout pipe never backs up and blocks *it*) but stops calling `applyLive` — necessary because tview's update queue is a fixed 100-slot buffer that nothing drains once the app has stopped; without this, the goroutine could block forever and the program would hang instead of exiting. A narrow, intentionally-accepted residual race remains in the handoff between checking `quitting` and the in-flight `QueueUpdateDraw` call — documented in the code rather than engineered away, consistent with this project's style elsewhere.

`streamStderr` and the diagnostic prints that used to go straight to stdout (the `v2_playbook_on_stats` cross-check, "(not JSON)" notices, scanner errors) are now all collected into string slices instead, and only flushed by `main` after `app.Run()` returns and the real terminal is restored — printing directly to the terminal while tview's alternate screen is active would corrupt the display. `cmd.Wait()`'s error is likewise captured but not acted on until after the TUI closes, so a failed/interrupted run's tree is still viewable first.

**The TUI is never shown for a pre-flight `ansible-playbook` failure (`main.go`).** A bad playbook path, a parse error, a missing inventory, etc. are all caught by `ansible-playbook`'s own CLI layer before any callback event ever fires — confirmed against `ansible.posix.jsonl`'s source, every line it ever writes to stdout is triggered from a real callback hook. So these failures write *zero* bytes to stdout; the message goes to stderr only, with a nonzero exit. Showing the TUI unconditionally (as `main` used to) meant these runs opened a blank, ticking, empty screen that just sat there until the user quit — only then did the real error print. `scanEvents(r io.Reader) <-chan streamItem` (replacing the old synchronous `streamEvents`) reads stdout on its own goroutine and sends one `streamItem` per line (`isEvent` true for anything that decoded as JSON, `diag` set for a malformed line, the `v2_playbook_on_stats` cross-check dump, or a final scan error — the two aren't mutually exclusive, `v2_playbook_on_stats` sets both), closing the channel at EOF. `main` peeks exactly one item (`first, ok := <-stdoutCh`) *before* ever constructing `state`/`NewLiveTUI`: if the channel closed having produced nothing (`!ok`), `ansible-playbook` never got far enough to run anything real — `main` drains `stderrLines`, calls `cmd.Wait()` (safe here specifically because `scanEvents`'s goroutine only closes its channel after its scan loop already hit real EOF, satisfying `exec.Cmd`'s "fully read the pipes before `Wait()`" contract), prints the stderr lines and the exit error the same way the normal path does, and exits — the TUI is never constructed in this branch. If `ok`, `main` proceeds as before, but replays `first` through the same `apply` closure (append `item.diag` if set; call `applyLive(item.ev)` if `item.isEvent && !quitting.Load()`, reproducing the old per-event quitting-check exactly) before ranging over the rest of `stdoutCh`. `v2_playbook_on_play_start` fires unconditionally as the very first thing any real run does — even for a play with zero tasks (confirmed against `ansible-core`'s `TaskQueueManager.run()`) — so "at least one line arrived" is a reliable, general gate, not a heuristic specific to this one bug.

Deliberately not handled: the fast-fail branch doesn't replicate the exit-99/benign-exit-4 special-casing from above — `state.HadUnreachable` can only ever become true after a real `v2_runner_on_unreachable` event, structurally impossible when zero events ever arrived, and an exit-99 in the sub-millisecond window before the TUI even exists is left to the OS's default SIGINT disposition (which also kills Tangsible itself, consistent with "Ctrl-C behaves like running ansible-playbook directly" for the one window where Tangsible's own forwarding isn't active yet). Also unaffected by this gate, unfixed and out of scope: `--list-tasks`/`--list-hosts`/`--syntax-check` bypass ansible's callback system entirely (confirmed via `playbook_executor.py`) and print their listing text straight to stdout — still ≥1 line, so the gate opens and today's same empty, ticking TUI shows for those flags. Minor accepted side effect of the gate itself: `tui.go`'s top-bar elapsed timer (`NewLiveTUI`'s `startedAt := time.Now()`) now measures from whenever the gate opens rather than from `cmd.Start()`, since the TUI is constructed slightly later — the gap is whatever `ansible-playbook`'s own parsing takes, normally well under a second at this project's target scale.

**Exit codes: a user-requested interrupt or a benign unreachable-host run is not an error (`main.go`, `tui.go`).** `ansible-playbook`'s own exit codes are overloaded and not safe to trust literally:
- **99** is its documented "user interrupted execution" code. In Tangsible specifically it's unambiguous: `tcell`'s raw mode disables the OS's normal Ctrl-C-to-SIGINT delivery (see `SetInputCapture` note below), so the only way the child ever receives `SIGINT` is Tangsible's own forwarding — 99 can only mean "the user asked, via `q`/Ctrl-C, for this run to stop," never an external signal. `main.go`'s `ansibleUserInterruptedExitCode` constant and `exitCodeOf(err error) int` (pulls the code out of `cmd.Wait()`'s `*exec.ExitError` via `errors.As`, returning `-1` for a non-`ExitError` failure — distinct from every real code, so it never accidentally matches 0 or 99) exist to let `main` and `tui.go` reason about this without re-deriving it.
- **4** is ansible-core's own `ExitCode` enum value for *both* `HOST_UNREACHABLE` and `PARSER_ERROR` (a static-include syntax error) — confirmed directly against ansible-core's source, which has its own `FIXME: conflicts` comment acknowledging the collision. Exit 4 alone can't be trusted to mean "benign." Tangsible disambiguates using evidence it already independently observed rather than the exit code alone: `aggregate.go`'s `playbookState.HadUnreachable` (set in `recordHost` whenever a host is recorded `outcomeUnreachable`, same funnel as `AllHosts`; never cleared) is only ever `true` if at least one real `v2_runner_on_unreachable` event occurred — which structurally cannot happen for a `PARSER_ERROR`, since that's a parse-time failure resolved before any task in any play begins. `main.go` computes `benignHostUnreachable := result.exitCode == 4 && state.HadUnreachable` and only treats it as benign for exactly that combination — exit 6 (`HOST_FAILED|HOST_UNREACHABLE`, a real task failure alongside an unreachable host) still reports as an error, since a genuine failure happened too.

Both cases fall through to a normal `main` return (exit 0) instead of `os.Exit(1)`, and skip the `"ansible-playbook exited with error:"` line. Only the 99 case additionally suppresses `childStderr` (the `[ERROR]: User interrupted execution` line is pure noise about an intentional action); exit-4's real stderr — e.g. the SSH connection-timeout line, when there is one — is left intact, since it's genuinely useful context alongside the maroon row already visible in the tree. (In practice, ansible's SSH-timeout messages tend to live entirely in the `msg` field of the `v2_runner_on_unreachable` event, visible via the drill-down view rather than on stderr at all — so there's often nothing to suppress either way.)

`state.HadUnreachable` is read from `main`/`rebuild()` with no atomic, deliberately: every write happens inside a `state.Apply` call, and every `state.Apply` call runs on whichever goroutine is executing `app.Run()`'s event loop — since `main()` calls `app.Run()` directly (not via `go`), that's `main`'s own goroutine, making this a single goroutine reading its own prior sequential writes, unlike `processDone`/`quitting`/`exitCode` (see Concurrency above), which genuinely cross goroutines and correctly need atomics.

`tui.go`'s `statusRowText(code int, hadUnreachable bool) string` renders the inline status message appended below the last task row once the run is frozen (see Heartbeat below for `processDone`/frozen framing) — green `"Playbook completed successfully"` only for a genuine `code == 0`; yellow `"Playbook completed - one or more hosts were unreachable"` for `benignHostUnreachable` (`code == 4 && hadUnreachable`); red `"Playbook stopped, press q again to quit tangsible."` for `code == ansibleUserInterruptedExitCode`; and `""` (nothing shown) for any other code, since a genuine failure is already visible from the red host rows themselves. The green/yellow split is deliberate, not cosmetic: `code == 0` and `benignHostUnreachable` used to render identical green text, but they're not the same situation - confirmed live, a single-host playbook whose one host is unreachable on its very first task exits 4 with `hadUnreachable == true` and *nothing else in the run ever having executed*, which "completed successfully" actively misrepresented. `main.go`'s own decision not to treat `benignHostUnreachable` as a hard tool error (no `os.Exit(1)`, no stderr dump) is unaffected - that's about whether Tangsible's own process should fail, a different question from what this status line honestly reports.

**Event shape (`events.go`).** `rawEvent` decodes the subset of the jsonl schema the app cares about. Empirically confirmed (not formally documented upstream, so re-verify against real output before depending on new fields): `v2_playbook_on_play_start` carries `play.name`; `v2_playbook_on_task_start` carries `task.name`, and neither of these carries any host list — there's no event that reveals a task's target hosts before its first per-host result; `v2_runner_on_ok` / `v2_runner_on_skipped` / `v2_runner_on_failed` / `v2_runner_on_unreachable` all share the shape `task` + `hosts: {<hostname>: {...}}`, with the per-host `changed` bool distinguishing OK from Changed within an `_on_ok` event (skipped/failed/unreachable are their own distinct event names, not a flag). `v2_playbook_on_stats` carries Ansible's own final per-host tallies, useful as a sanity check against this app's own counts (see caveat below).

`rawEvent.Hosts` is `map[string]json.RawMessage`, not a typed struct — each host's full original JSON is preserved (not just the fields `hostResult` decodes) since different Ansible modules return wildly different result shapes (command: `stdout`/`stderr`/`cmd`/`rc`; most modules: `msg` on failure; others: arbitrary module-specific fields), and hand-modeling all of them isn't worth it. `decodeHostResult` extracts just the classification fields `Apply` needs from those raw bytes; the full bytes themselves get stored for later display (see `taskNode.Raw` below).

`rawEvent.TimestampText` (every event's own `_timestamp`, empirically RFC3339 with fractional seconds) is deliberately a plain `string`, not `time.Time`, with the fallible parsing done separately by a `Timestamp() time.Time` method that swallows errors (same convention as `decodeHostResult`). A `time.Time` struct field's own `UnmarshalJSON` failing on a malformed value would make `json.Unmarshal` return an error for the *whole* `rawEvent`, which `streamEvents` treats as "not JSON" and discards the entire event — task and hosts included — over nothing but a bad timestamp. Real bug caught during design, not a hypothetical.

**Aggregation (`aggregate.go`).** `playbookState.Apply` consumes one `rawEvent` at a time and builds a `Plays []*playNode` → `Tasks []*taskNode` → `Hosts map[string]outcome` tree. Plays and tasks are created lazily (a play only gets a row once its first task starts), so plays with no executed tasks never appear — matches the decision in `TUI.md`. Ansible's default/linear strategy runs one task across all hosts before starting the next task, so a simple `currentTask` pointer (updated on task-start) is enough to attribute later `runner_on_*` events to the right task, without needing to correlate by task ID. Counts are computed on demand by scanning `taskNode.Hosts` rather than tracked as separate counters, to avoid a second source of truth.

`playbookState` also exposes three optional, nil-checked hooks — `OnPlayAdded`, `OnTaskAdded`, `OnHostRecorded` — invoked by `Apply` right as each thing happens, deliberately typed using only this file's own types so it stays free of any UI dependency. `tui.go` wires these to grow the tview tree incrementally instead of rebuilding it from scratch on every event (a rebuild would reset all expand/collapse state and the current selection each time). Because `Apply` always runs from inside `app.QueueUpdateDraw` (see Concurrency above), `playbookState` is safe to mutate with no mutex — but only because it's always that one goroutine doing it; it's not a general-purpose concurrent structure.

`playbookState.AllHosts` is the run-wide, alphabetically-sorted set of hosts that have reported anything, for any task, so far — it only ever grows, via `noteHost` (called from `recordHost`, the same funnel every outcome-recording event type goes through), using a plain linear scan + `append`+`sort.Strings` rather than a membership map or smarter insertion (needless machinery at this project's ~10-host target scale). `tui.go`'s `taskLabel` uses this to show every known host on every task's row, greying out any that haven't reported for that *specific* task yet, instead of showing only the hosts that particular task has itself heard from — since there's no event that reveals a task's hosts in advance (see Event shape above), a task's very first appearance in a run necessarily starts this list from empty; only later tasks benefit from the "grey until lit up" effect.

`outcomeUnreachable` is its own outcome now, not folded into `outcomeFailed` — the collapsed-row redesign (see TUI (`tui.go`) below) made that distinction visually worth having, whereas it wasn't when the only display was an aggregate count.

`taskNode.Raw map[string]json.RawMessage` sits parallel to `Hosts`, populated alongside it in `record` — each host's full original result payload for that task, kept so `tui.go`'s output drill-down view can show it later. `aggregate.go` stays free of any formatting logic here too: `Raw` is read but never interpreted in this file.

`taskNode.StartedAt` comes from the starting event's own `rawEvent.Timestamp()`, not our wall-clock `time.Now()` at the moment we process it — "when did Ansible itself start this task." Currently unused by any renderer (`tui.go` shows a spinner rather than an elapsed readout for the active task — see Heartbeat below); kept because Ansible provides it for free and a future summary/history view (see `Findings.md`) would likely want it. `playbookState.CurrentTask()` is a read-only accessor for the same unexported `currentTask` field `Apply`/`recordHost` already maintained — added so `tui.go` reads it deliberately through an accessor (to mark the active task's row with a spinner) rather than reaching into a field clearly meant as this file's own private bookkeeping, even though same-package access would technically compile.

`aggregate.go`'s no-mutex safety story is now also worth restating precisely: `tui.go`'s ticker goroutine (see below) is the first thing in this codebase that triggers reads of `playbookState` on a schedule rather than strictly in response to an event or keypress — still safe, since the ticker's reads happen inside `app.QueueUpdateDraw`, which runs on the same single event-loop goroutine `Apply` itself always runs on.

One remaining deliberate simplification: failed-but-ignored tasks (`ignore_errors: true`) still show as `Fail`. This is *not* how Ansible's own `v2_playbook_on_stats` counts them — Ansible counts an ignored failure toward `ok` (plus a separate `ignored` tally), so this app's rollup will not numerically reconcile with Ansible's own recap stats for playbooks that use `ignore_errors`. Expected, not a bug.

**Plain-text rendering (`render.go`).** `Render` prints the whole tree in one shot, always showing every host line under every task. No longer called from `main`'s normal flow (superseded by the tview UI below) but kept around as a still-useful, dependency-free dump — e.g. for debugging or a future non-interactive mode.

**TUI (`tui.go`).** Built with `github.com/rivo/tview` (on top of `github.com/gdamore/tcell/v2`) — chosen over Bubble Tea's Elm-style architecture specifically because it's a smaller conceptual jump from `tcell`, which prior project experience already covered. Originally used `TreeView` (which maps directly onto the play/task/host shape), but migrated to `List`: `TreeView` renders each node with one uniform `tcell.Style` (confirmed from its source), so there was no way to color the OK/Chgd/Skip/Fail segments of a task row differently from each other. `List` parses inline `[color]text[-]` style tags in its item text (same tag-aware print path `TextView` uses), which is what makes the per-segment coloring below possible.

Since `List` is flat (no built-in hierarchy/expand-collapse), `tui.go` owns:
- **Expand state** — `map[*taskNode]bool`, default `false` (collapsed).
- **Flattening** — `flattenRows(state, expanded, width) []row` walks `Plays → Tasks → (if expanded) Hosts` into an ordered row list, rebuilt fresh on every event (cheap at ~10-host scale; no incremental patching needed, unlike the old `TreeView` bookkeeping maps this replaced).
- **Selection preservation across rebuilds** — `rebuild()` (inside `NewLiveTUI`) tracks the *identity* of the selected row (a `*playNode`, `*taskNode`, or `hostRowID`, not a raw index, since row order shifts as things are appended). It now computes `selectedIndex` (via `currentID`/`following`, same logic as before) *before* the `Clear()`+`AddItem()` loop, not after — needed because the cursor row's styling (see Row text below) is baked into that row's own text rather than applied by `List` automatically, so `rebuild()` must know which row that is in order to re-render it with its `selected=true` variant first. Non-obvious gotcha hit here: `List.Clear()` followed by re-`AddItem()` fires a spurious "changed" event the instant the first row lands back in the now-empty list, which will silently overwrite the tracked selection *during* the rebuild if you're not careful — guarded against with a `rebuilding bool` flag that `SetChangedFunc`'s handler checks before recording anything.
- **Autoscroll** — a `following bool` (default `true`) makes `rebuild()`'s `selectedIndex` resolve to the newest row instead of restoring by identity. Any genuine (non-`rebuilding`) `SetChangedFunc` event disengages it — that's what "the user navigated" reduces to, since `Up`/`Down`/`PageUp`/`PageDown`/`Home`/`End` are all handled by `List`'s own `InputHandler` and each fires that same callback. Only `'F'` is intercepted in `SetInputCapture` to re-engage it, by setting `following = true` before jumping to the last row — a second guard, `jumpingToEnd bool`, exists only so that jump's own resulting `changed` event doesn't immediately flip `following` back off again. End/`'G'`/Ctrl-E are deliberately *not* wired to this — see Keyboard shortcuts below for why they're plain navigation instead. `list.SetWrapAround(false)` removes wraparound at the list's ends (tview's default is `true`); `Home`/`End`/`PageUp`/`PageDown` were already unaffected by that flag even before this change, since `List` clamps them internally regardless — only plain `Up`/`Down` relied on it.
- **Navigation now triggers a full `rebuild()`, not just data events or the heartbeat tick** — added because the cursor row's look is baked into row text (see Row text below); without this, moving the cursor via a plain arrow key wouldn't visually move the highlight at all until something else happened to call `rebuild()` (and once a run finishes, the heartbeat ticker stops entirely — see Heartbeat below — so it would never move again). Added inside `SetChangedFunc`'s already-existing genuine-navigation branch, gated behind the same `rebuilding` check used for the `Clear()`/`AddItem()` gotcha above. That gating is what makes this safe, not incidental: checked directly against `tview`'s `List.SetCurrentItem` source, it fires its `changed` callback *before* updating its own `currentItem` field — so a naive unconditional `rebuild()` call here would recurse forever the moment anything (e.g. the `End`/`'G'` handler's own `SetCurrentItem` call) triggered a `changed` event whose callback issued another `SetCurrentItem` for the same target index, since from the *outer* call's perspective `currentItem` would still look stale on every recursive re-entry. Since `rebuild()` sets `rebuilding = true` for its entire body — including its own closing `SetCurrentItem` call — any `changed` event that cascades from within it lands back here while `rebuilding` is still true and is correctly ignored, terminating the recursion.

`NewLiveTUI` returns both the `*tview.Application` and an `applyLive func(rawEvent)` closure — `main.go` calls `app.Run()` and feeds events through `applyLive` but never imports `tview` itself, keeping this the only file that touches `tview`/`tcell`.

**Heartbeat (`tui.go`).** A ticker goroutine (`spinnerInterval` = 200ms) is the first *self-driven* source of `QueueUpdateDraw` calls in this codebase — every other trigger so far has been an incoming jsonl event or a keypress. Each tick calls `app.QueueUpdateDraw(rebuild)`, which now also refreshes `topBar` (`topBarText`: playbook name, spinner frame, total elapsed time since `NewLiveTUI` was called) and computes `activeTask := state.CurrentTask()` (nil once `processDone`) for `flattenRows` to attach a spinner prefix to (see `taskLabel` below — no longer an elapsed-time readout; removed because it made the active task's row shrink its hostnames slightly more aggressively than every other row's, an inconsistency the fixed-width spinner slot doesn't have). `spinnerAt(elapsed time.Duration) rune` is shared by `topBarText` and `taskLabel` so both tick the identical frame at the same instant when driven from the same `elapsed` value, computed once per `rebuild()` call. The ticker needs — and has — the same `quitting`-checked-before-`QueueUpdateDraw` guard `main.go`'s `streamEvents` already uses, for the same underlying reason (tview's update queue is a fixed 100-slot buffer nothing drains once the app has stopped), though the stakes differ slightly: nothing in `main.go` waits on this goroutine the way it waits on `streamEvents`, so a hang here wouldn't itself block process exit — worth guarding anyway. Once `processDone` is observed true, the goroutine pushes one final frozen frame (spinner dropped, elapsed held static) and returns, rather than continuing to tick forever over an unchanging screen — this is also why navigation had to be taught to trigger its own `rebuild()` (see Selection preservation above): once frozen, this ticker is the *only* other thing that used to keep the cursor's rendering fresh. It's started *after* `app = tview.NewApplication()...` — not just style: the `go` statement's happens-before edge is what makes reading `app` from that goroutine well-defined, per the Go memory model.

`taskLabel`'s `active bool, frame rune` parameters render a fixed-cost 2-rune prefix in place of the row's leading `taskIndent` — the spinner frame plus one space for the active task, or `taskIndent`'s own plain spaces otherwise. Originally this was a trailing `" <frame>"` suffix reserved from the width budget right after the title; moved to the front (reusing indent's already-reserved width instead of carving out more) so hostnames get that width back on the right. Either way the width is fixed and reserved unconditionally, so every row's hostnames still shrink identically regardless of which task, if any, is active — only the *content* of that fixed slot differs.

**Output drill-down (`tui.go`).** The app's root is a `tview.Pages` (not the main `Flex` directly) with two pages: `"main"` (the existing top bar/list/bottom bar) and `"output"` (a single, reused `TextView` in its own small `Flex` with its own bars). Host rows' `selected` callback — previously always `nil` — now calls `showOutput(task, host)`, which formats `task.Raw[host]` via `formatHostOutput`, updates the output view, and switches pages; the `TextView`'s own `SetDoneFunc` (fires on Escape/Enter/Tab/Backtab) switches back. Hiding a page only flips a `Visible` flag — the list's selection/state is never touched by this, confirmed via `tview`'s source rather than assumed.

Two non-obvious things a design-review pass caught here that are easy to reintroduce if this code is restructured:
- `TextView.SetText` does **not** reset scroll position (`lineOffset`/`trackEnd`). Since the output view is one `TextView` reused across every drill-down (never recreated), `showOutput` must call `outputView.ScrollToBeginning()` after every `SetText` — otherwise opening a second host's output right after scrolling through the first would open already scrolled to (or bottom-pinned from) the old position.
- Left/Right and `n`/`p` mean different things on each page (host-nav/task-nav in the output view vs. expand-collapse/task-hop in the main tree — see Keyboard shortcuts below), so `SetInputCapture` needs to know which page is frontmost before dispatching them. Fixed with a `viewingOutput bool` (same locally-owned-flag style as `following`/`jumpingToEnd`), checked before the page-specific bindings dispatch.

`formatHostOutput` decodes `task.Raw[host]` into a generic `map[string]interface{}` (not a fixed struct, for the same reason `events.go`'s `rawEvent.Hosts` doesn't decode into one) and shows one labeled section for `primaryOutputField`'s chosen text (see below), then `stderr` if present and non-empty (real newlines — the output `TextView` keeps style tags off, so nothing needs `tview.Escape()`), followed unconditionally by the complete result as pretty-printed JSON — the fallback that makes this work for any module's result shape without special-casing.

`primaryOutputField(decoded) (label, text string)` picks a single field to show as "the output" — `stdout` if non-empty, else `msg` — rather than showing both. On a command/shell task with a non-zero return code, `msg` is often just a fixed status string (`"non-zero return code"`) alongside the real output already sitting in `stdout`; for modules that only set `msg` (most non-command modules), that's the fallback. Shared between `formatHostOutput` (the drill-down view) and `outputSummary` below (the collapsed treeview OK line) so both agree on what "the output" means for a given result.

`hostLabel`'s expanded-row text gets an outcome-specific parenthesized detail, computed from `task.Raw[host]`, in addition to the base "host: OUTCOME": `outputSummary` (OK/Changed/Failed) shows `primaryOutputField`'s text verbatim if it's a single line, or `"N lines of output"` otherwise, or nothing if there's no output text at all (e.g. `copy`/`template`, which only report `changed`) — for Failed specifically, this is usually the failure's own `msg`, since `stdout` is typically empty for a command that never produced output before failing. `skipDetail` (Skipped only) shows `skip_reason`/`false_condition` straight from the recorded result, falling back to just `skip_reason` if `false_condition` isn't a plain string (e.g. a literal `when: false` serializes it as JSON `false`, not a string). Unreachable renders exactly as before — undefined for now, not a gap that was missed.

**Row text (`taskLabel`/`hostLabel`/`playRowText`/`colorTag`).** `colorTag(outcome) string` maps OK/Changed/Skipped/Failed/Unreachable to tag color names — `green`/`yellow`/`teal`/`red`/`maroon`. `teal` is `tcell`'s/W3C's closest named match for ANSI cyan; `maroon` (not `brown`/`darkred`) for Unreachable specifically because it's in the same base-16 ANSI palette family as the other four (index 1, vs `red`'s index 9 — a different terminal-configured slot, not just a different-looking RGB value), whereas `brown`/`darkred` are RGB-approximated extended-W3C names that render less predictably across terminal themes.

The `PLAY:`/`TASK:` label prefixes are gone — `playRowText` renders just the play's name (white, bold); `taskLabel` shows every host in `allHosts` (see `AllHosts` above) right-aligned after the plain task title (silver, regular weight — deliberately not `grayTag`'s plain `"gray"` either, to keep "this is a task's own title" visually distinct from "this host hasn't reported for this task yet"), colored by `task.Hosts[host]`'s outcome if present, `"gray"` otherwise — the "grey until lit up" effect, which falls straight out of that map lookup with no extra bookkeeping. Fitting happens entirely in plain, untagged rune space (raw task name, raw host names) and only wraps the final, already-correctly-sized pieces in color tags and `tview.Escape()` once, at the very end — avoids repeated `tview.TaggedStringWidth` calls inside what can otherwise be a multi-iteration shrink loop. Per `TUI.md`'s algorithm (as adjusted — see below): if title+gap+hosts doesn't fit, the title's own name is shortened first (down to `minTaskTitleName`, with `…`); if that alone isn't enough, whichever hostname is currently longest is shortened next, one rune at a time (no ellipsis — truncation collisions between hostnames are an accepted tradeoff per `TUI.md`), down to a 1-rune floor each; beyond that, overflow is accepted rather than engineered away further. The gap actually rendered is real leftover space once title and hosts are sized (true right-alignment, matching `TUI.md`'s own sketch) — the "3" in `TUI.md`'s spec (`titleHostGapFloor`) is only the threshold used to decide *whether* shrinking is needed, not the rendered gap itself. `minTaskTitleName` is now 30 (was 15) — raised so a title only gives up ground to the host list once the host list has already been squeezed hard. `hostLabel` (the expanded per-host detail view) still colors its whole line uniformly by its single outcome, unaffected by any of the shrink logic above (no width-based truncation applies there).

**The row under the cursor renders with its own look, not a flat `List`-applied highlight (`tui.go`).** The desired appearance — black bold text; light gray background confined to the title; each hostname's outcome color as a *background* instead of a foreground, blended into its neighbor — can't be expressed as one `tcell.Style` applied uniformly to a row's whole text, since different runs within the same row need different foreground/background combinations. So `list.SetSelectedStyle` is set to match `mainTextStyle`'s own colors exactly (a no-op, visually identical to an unselected row), and `playRowText`/`taskLabel`/`hostLabel` each take a `selected bool` that switches their tag construction entirely — `rebuild()` determines which one row is current (see Selection preservation above) and re-renders just that row's text with `selected=true` before `AddItem`.
- **No neutral gap anywhere**: the light gray title background extends through the whole padding gap except the last space before the first hostname; that space, and every hostname's own leading space thereafter, is folded into that hostname's own color block instead of staying a plain, uncolored separator. Deliberately *not* extended to blending the title's own grey into the first hostname's color (see next point) — only the gaps between hostnames get that treatment, per direct request; the title→host0 transition stays a flat handoff.
- **`halfBlock` (U+258C LEFT HALF BLOCK, `▌`)** renders the cell between two adjacent hostnames with the left one's color as foreground and the right one's as background, blending them instead of an abrupt full-cell jump (`hostTransition(leftTag, rightTag)`). Tried on unselected rows too and reverted after visual inspection — looked wrong there, since unselected hostnames are foreground-colored text on a plain background, not background-colored blocks, so there's no matching "two solid colors" context for the blend to sit in. Selected-row-only.
- **`pureBlack = "#1a1a1a"`, not `tcell.ColorBlack` or `"#000000"`**: checked directly against `tcell`'s `FindColor`/`colorfit.go` — on a reduced-palette (256-color, non-truecolor) terminal, a value that exactly matches a base-16 slot's nominal RGB is *always* preferred by `tcell`'s nearest-color search, even when given as a hex value, so `"#000000"` resolves identically to the named `black` — and some terminal themes remap that exact slot to a dark gray rather than true black (the same base-16-vs-fixed-value trap already noted above for `red`/`maroon`). Nudging just off pure black forces selection from the fixed, non-remappable extended-256 grayscale ramp instead (confirmed via the actual escape codes emitted: `38;5;234`, not `30`) — visually indistinguishable from black, immune to that remap.

Two things worth knowing if touching this file:
- `Application.SetInputCapture` maps `Ctrl-C` and `'q'` identically, and their behavior depends on `processDone`: while `ansible-playbook` is still running, both forward `SIGINT` to it (`proc.Signal(os.Interrupt)`) and leave the TUI open so the run's outcome stays visible; once the process has finished, both close the TUI instead. This restores Purpose.md's "Ctrl-C behaves like running ansible-playbook directly" decision, which `tcell`'s raw mode would otherwise silently break — raw mode disables the OS's own Ctrl-C-to-SIGINT delivery, so without this explicit forwarding the child would stop receiving the interrupt it used to get for free.
- `taskLabel`'s width comes from whatever the list's size was at the last rebuild — a bare terminal resize with no new incoming event won't re-flow existing rows until the next event triggers one. Accepted limitation, not a bug.

**Keyboard shortcuts (`tui.go`).** `Keyboard-shortcuts.md` is the source-of-truth reference; this section covers the implementation. Verified directly against `tview@v0.42.0`'s own source (`list.go`/`textview.go`/`application.go`), not assumed: `List` (main tree) natively handles Up/Down/PgUp/PgDn/Home/End/Enter/Space (Space behaves identically to Enter — confirmed from `List`'s own rune-handling code); `TextView` (output view) natively handles all of that plus the vim runes `g`/`G`/`j`/`k`/`h`/`l` and Ctrl-F/Ctrl-B. Neither natively handles j/k, Ctrl-A/Ctrl-E, or (for `List`) Ctrl-F/Ctrl-B/`'G'`.

`SetInputCapture`'s body is three tiers, in order:
1. **Quit** (`q`/Ctrl-C) — unchanged from before.
2. **Universal key aliases**, applied regardless of which page is frontmost: `j`/`k` → synthesize `KeyDown`/`KeyUp`; Ctrl-F/Ctrl-B → `KeyPgDn`/`KeyPgUp`; Ctrl-A/Ctrl-E → `KeyHome`/`KeyEnd`; `'G'` → `KeyEnd`. Returning a *different* `*tcell.EventKey` than the one received makes `Application` forward the synthesized event to whichever primitive is currently focused, exactly as if the user had typed that key (confirmed from `application.go`) — so these ride the exact same code path plain Home/End/PgUp/PgDn already use, on both `List` and `TextView`, with no duplicated logic. This is also what makes `'G'`/Ctrl-E deliberately plain navigation rather than resuming autoscroll: they're indistinguishable, once translated, from the user having pressed the real End key.
3. **Page-specific bindings**, `if viewingOutput { ... } else { ... }`: output view gets Left/Right → `navigateOutputHost` (steps through `outputTask.HostOrder`, no wraparound) and `n`/`p` → `navigateOutputTask` (steps through `tasksForHost(state, outputHost)`, no wraparound); main tree gets `'F'` (the sole surviving "jump to bottom + resume follow" binding — see Autoscroll above), `E`/`C` → `expandAll`/`collapseAll`, Right/Left → `handleRight`/`handleLeft`, `n`/`p` → `navigateMainTask`.

`expandAll`/`collapseAll` set every task's `expanded` entry at once. `collapseAll` has a cursor-fallback: if `currentID` is currently a `hostRowID` (about to disappear), it's reassigned to that row's own task first, so the cursor lands on the now-collapsed task row rather than `rebuild()`'s generic "unknown id → index 0" fallback.

`handleRight`/`handleLeft` act on whichever row is under the cursor right now (`currentRows[list.GetCurrentItem()]`, not `currentID` — the two are normally the same row, but the cursor's on-screen position is what "this element" means here). Right expands a collapsed task; on an already-expanded task, a host row, or a play row, it's a no-op — collapsed→expanded is a one-way trip per keypress, not a "descend into children" gesture. Left collapses an expanded task in place; on a host row it collapses that row's *parent* task and moves `currentID` there (Left always means "close/go up," never a no-op on a leaf); on a play row it's a no-op (plays aren't collapsible — there's no `playNode` expand state to speak of).

`navigateMainTask(delta)` hops the cursor to the previous/next task, via `allTasks(state)` (the host-agnostic sibling of `tasksForHost`, flattening every task across every play in run order) — bounds-checked, no wraparound. If the cursor started on a specific host of the current task, that same host is carried to the destination task, but only if the destination has actually recorded a result for it (`target.Hosts[host]` present) — otherwise the cursor falls back to the destination task's own row, since there's no host row to land on yet. Starting from a play row is a special case with no `allTasks` index to step from: "next" targets that play's own first task, "prev" targets the *previous* play's last task (a no-op from the very first play). Either way, the destination task is force-expanded (`expanded[target] = true`) so the landing row is actually visible.

Closing the output view (`outputView.SetDoneFunc`) now does more than flip `viewingOutput` and switch pages: it sets `expanded[outputTask] = true`, points `currentID` at `hostRowID{outputTask, outputHost}`, and calls `rebuild()` *before* switching back to the main page — so the tree's cursor always reflects whatever the output view was last showing, even if that moved via `navigateOutputHost`/`navigateOutputTask` since the view was first opened, per `Keyboard-shortcuts.md`'s explicit requirement.

**Mouse (`tui.go`).** `app.EnableMouse(true)` (on `NewLiveTUI`'s `app` construction) turns events on; most of the rest falls out of `tview`'s own built-in mouse handling, confirmed against `List`'s/`TextView`'s source rather than assumed: `List`'s click handling already fires a row's `Selected()` callback on the first click (identical to Enter) — so a single click on a host row already opens its output; no separate double-click wiring was needed on top of that. Scrolling in the output view (a plain `TextView`) is likewise free — its wheel handling just pans, and there's no "selected line" concept to fight.

The main tree needed real work, though: `List`'s own wheel handling only pans an internal `itemOffset`, but `List.Draw()` *unconditionally* re-clamps that offset on every redraw to keep `currentItem` visible (checked directly against `list.go` — there's no flag to disable this). Panning the viewport directly therefore only ever gets you as far as the current item's own distance from the edge before every next redraw snaps it back — worse, while `following` is on, the heartbeat ticker pins `currentItem` to the last row every 200ms, undoing any wheel-pan almost immediately. Rather than fight the clamp, `app.SetMouseCapture` drives it: `MouseScrollUp`/`MouseScrollDown` are consumed (List's own `itemOffset`-only handling never runs) and instead move `currentItem` by one row via `list.SetCurrentItem`, which is the one thing `Draw()`'s clamp actually watches — so the clamp itself becomes the panning mechanism, with no cap on range. This also means autoscroll disengages for free: `SetCurrentItem` fires the same `changed` callback arrow keys already trigger, so wheel scrolling is "genuine navigation" exactly like a keypress, no separate `following = false` needed. The visible tradeoff is that the highlighted row now moves along with the scroll rather than staying fixed while the view pans around it — accepted deliberately, since there's no way to decouple panning from selection in this widget without dropping `List` for a hand-rolled scroll (out of scope here).

**Test fixtures (`testdata/`).** Playbooks (and inventory files) used to manually exercise the aggregation logic: `basic.yml` (simple sequential tasks including a sleep, demonstrates live streaming), `outcomes.yml` (single host, all four original outcome buckets including an ignored failure), `multihost.yml` + `multihost-inventory.ini` (two hosts diverging on the same task, to exercise per-host aggregation within one task), `hostnames.yml` + `hostnames-inventory.ini` (varied-length hostnames to exercise `taskLabel`'s shrink algorithm, plus a host pointed at an unreachable address with a short SSH connect timeout, to trigger `v2_runner_on_unreachable` for real — run with `--forks 1` to serialize per-host completion for an observable grey-to-lit transition).

## Current scope constraints (from Purpose.md)

These aren't accidental omissions — they're explicit v1 decisions and should inform what "done" means for near-term work:

- No run history — single-session only, revisit later.
- No interactive prompt handling (`--ask-become-pass`, vault password prompts, `pause` tasks) — not supported yet.
- Ctrl-C should behave the same as it does when running `ansible-playbook` directly — implemented, see `tui.go`'s `SetInputCapture` note above.
- Target scale is ~10 hosts, not hundreds/thousands — this is an interactive dev tool, not a fleet-management tool.
- Only a limited subset of `ansible-playbook`'s CLI surface should be exposed initially; expand only as needed.
