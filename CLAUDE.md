# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Tangsible is a TUI wrapper for `ansible-playbook`, aimed at interactive use (e.g. during development). `Purpose.md` documents the "why" — read that before making design choices; this file covers the "how".

The TUI (`tview`) comes up immediately and updates incrementally as jsonl events arrive while `ansible-playbook` runs. Navigation: arrow/j-k (no wraparound), Space/`b` page down/up, Enter expands/collapses a task's host rows, Right/Left expand/collapse a task directly, `E`/`C` expand/collapse everything, `n`/`N` hop to next/prev task (preserving selected host where possible), Home/End/`G`/Ctrl-A/Ctrl-E jump to first/last row, `q`/Ctrl-C quit (or interrupt the running process — see Exit codes below). The view auto-follows the newest row until the user scrolls (including via End/`G`/Ctrl-E, deliberately plain navigation); only `F` re-engages follow. Full shortcut reference: `Keyboard-shortcuts.md`.

Play rows: white/bold. Task rows: plain gray, with every host discovered so far shown on the collapsed row, each colored by its outcome for *that* task (green/yellow/teal/red/maroon for OK/Changed/Skipped/Failed/Unreachable) or grey if not yet reported — not aggregate counts. The selected row renders distinctly (black bold text, light gray title background, per-host outcome colors as backgrounds with blended transitions) rather than a flat highlight. Expanding a host row shows outcome + a short detail (OK: single output line or line count; Skipped: `skip_reason`/`false_condition`). Enter on a host row opens a full-screen drill-down (MSG/STDOUT + STDERR + full JSON); Left/Right there switch host, `n`/`N` switch task. Top/bottom bars are white-on-navy; the top bar ticks a spinner + elapsed time, freezing once the run finishes. Requires a real TTY.

## Commands

```
go build ./...                                          # build
go vet ./...                                             # lint
go run . run [<playbook.yml>] [ansible-playbook args...] # run
```

The leading verb is mandatory (`resolve.go`'s `parseVerb`): `run` or `rerun` (see Rerun below).

Try it against the bundled fixtures:
```
go run . run testdata/outcomes.yml -i localhost,
go run . run testdata/multihost.yml -i testdata/multihost-inventory.ini
```

`go test ./...` runs the unit suite (`go test -run <Name> ./...` for one test) — see `TESTING.md`. `go test -tags e2e ./...` adds tmux-driven e2e smoke tests (`e2e_rerun_test.go`), needing `tmux`/`ansible-playbook`, excluded by default.

The playbook argument is optional (`resolve.go`): if omitted, resolved in order from `$TANGSIBLE_PLAYBOOK`, `./.tangsible/config.toml`, `$XDG_CONFIG_HOME/tangsible/config.toml` (or `~/.config/...`), then `./site.yml`; usage error otherwise. Both config files share:
```toml
[general]
default_playbook = "myplaybook.yml"
```

Requires `ansible-playbook` and the `ansible.posix` collection (`ansible-galaxy collection install ansible.posix`).

## Architecture

**Verb dispatch / playbook resolution (`resolve.go`, `main.go`).** `os.Args[1]` must be a verb (`run`/`rerun`); `main()` funnels both into the same TUI/generation machinery (see Rerun). `splitPlaybookArgs` decides by *shape* whether a playbook was given positionally: empty or starting with `-` means no playbook (whole slice becomes passthrough), anything else is the playbook — this is `run`'s own resolution; `rerun` has a separate, history-aware one. `resolvePlaybook()` tries env var → project config → XDG config → `./site.yml`. A missing config file is silent; an existing-but-unparseable one warns to stderr and falls through. The resolved playbook string is passed through with no path-joining of Tangsible's own — `ansible-playbook`/`buildTaskSourceIndex` resolve relative paths against the cwd themselves.

**Data source.** Shells out to `ansible-playbook` with `ANSIBLE_STDOUT_CALLBACK=ansible.posix.jsonl` and `ANSIBLE_JSON_INDENT=0` — one JSON object per line as each event happens, enabling live consumption (the built-in `json` callback buffers everything until the end). Pinning `ANSIBLE_JSON_INDENT=0` guards against a user's `ansible.cfg` breaking the one-event-per-line scanner. Never uses Ansible's Python API or a custom callback plugin (see Purpose.md's Platform section).

**Concurrency (`main.go`).** TUI and event stream run concurrently, coordinated by two `atomic.Bool`s: `processDone` (set on `cmd.Wait()`; per-*generation*, reset by `requestRerun` before each new spawn) and `quitting` (set once the user quits; checked before every event so a closed UI is never queued into — tview's update queue is a fixed 100-slot buffer nothing drains once stopped). `streamStderr` collects the child's stderr into a slice printed only after `app.Run()` returns (printing to the terminal while the alternate screen is active would corrupt it); `cmd.Wait()`'s error is likewise deferred.

**Pre-flight gate (`main.go`).** A bad playbook path/parse error/missing inventory is caught by `ansible-playbook`'s own CLI layer before any callback event fires, writing zero bytes to stdout — so showing the TUI unconditionally used to open a blank, ticking screen. `scanEvents` sends one `streamItem` per stdout line on its own goroutine, closing the channel at EOF; `main` peeks one item before constructing `state`/`NewLiveTUI`. If the channel closes with nothing (`!ok`), the TUI is never built — stderr + exit error print directly. `v2_playbook_on_play_start` fires unconditionally as the first event of any real run (even a zero-task play), so "at least one line arrived" is a reliable gate. Not handled by this gate: `--list-tasks`/`--list-hosts`/`--syntax-check` bypass Ansible's callback system and print listing text straight to stdout, so they still open the same empty ticking TUI.

**Exit codes (`main.go`, `tui.go`).** `ansible-playbook`'s exit codes are overloaded:
- **99** = "user interrupted execution." Unambiguous here because `tcell`'s raw mode disables OS Ctrl-C→SIGINT delivery, so the child only ever receives SIGINT via Tangsible's own forwarding.
- **4** = both `HOST_UNREACHABLE` and `PARSER_ERROR` (ansible-core has its own `FIXME: conflicts` comment about this). Disambiguated via `state.HadUnreachable` (set only by a real `v2_runner_on_unreachable` event, structurally impossible for a parse-time failure): `benignHostUnreachable := exitCode == 4 && state.HadUnreachable`. Exit 6 (failure + unreachable) still reports as an error.

Both benign cases return normally (exit 0) instead of `os.Exit(1)`; only 99 additionally suppresses stderr noise. `statusRowText` renders the closing status line: green for genuine success, yellow for benign-unreachable, red for user-stopped or genuine failure — every terminal case gets an explicit line so a real failure never reads as "did this even finish?". `genuineFailure(code, hadUnreachable)` is the shared predicate behind that and behind auto-jumping the cursor to the last failed task/host on the running→frozen transition (skipped if that task doesn't match the active filter — see Filtering).

`state.HadUnreachable` is read with no atomic, deliberately: every write happens inside `state.Apply`, which always runs on the single `app.Run()` event-loop goroutine.

**Event shape (`events.go`).** `rawEvent` decodes the subset of the jsonl schema needed. Empirically confirmed, not formally documented upstream — re-verify against real output before depending on new fields: `v2_playbook_on_play_start`/`v2_playbook_on_task_start` carry `play.name`/`task.name` but no host list (no event reveals a task's hosts before its first per-host result); `v2_runner_on_{ok,skipped,failed,unreachable}` share `task` + `hosts: {<hostname>: {...}}`, with `changed` distinguishing OK/Changed within `_on_ok`. `rawEvent.Hosts` is `map[string]json.RawMessage` (module result shapes vary too much to model as one struct) — `decodeHostResult` extracts classification fields; the raw bytes are kept for display (`taskNode.Raw`). `TimestampText` is a plain string with fallible parsing done separately by `Timestamp()`, so a malformed timestamp can't fail `json.Unmarshal` for the whole event.

**Aggregation (`aggregate.go`).** `playbookState.Apply` builds `Plays []*playNode` → `Tasks []*taskNode` → `Hosts map[string]outcome`, lazily (a play only appears once its first task starts). Ansible's linear strategy runs one task across all hosts before the next, so a `currentTask` pointer (updated on task-start) suffices to attribute `runner_on_*` events — no task-ID correlation needed. `v2_playbook_on_task_start` and `v2_playbook_on_handler_task_start` (handlers) are handled identically in the same case — treating them separately used to silently attribute a handler's result onto whichever regular task last started. Counts are computed on demand from `taskNode.Hosts`, not tracked separately. Three nil-checked hooks (`OnPlayAdded`/`OnTaskAdded`/`OnHostRecorded`), UI-agnostic, let `tui.go` grow the tree incrementally instead of rebuilding from scratch. Safe with no mutex only because `Apply` always runs on tview's single event-loop goroutine (via `QueueUpdateDraw`) — not a general concurrent structure.

`AllHosts` is the run-wide sorted set of hosts seen so far (only grows); `tui.go` uses it to grey out hosts that haven't reported for a given task yet. `outcomeUnreachable` is its own outcome, not folded into Failed. `taskNode.Raw` mirrors `Hosts` with each host's full raw JSON, read but never interpreted here. Deliberate simplification: `ignore_errors: true` failures still render as Fail (Ansible itself counts them toward `ok` + a separate `ignored` tally) — this app's rollup won't numerically match Ansible's own recap for such playbooks.

**Plain-text rendering (`render.go`).** `Render` dumps the whole tree in one shot. No longer used by `main`'s normal flow; kept as a dependency-free debug/non-interactive-mode option.

**TUI (`tui.go`).** Built on `tview`/`tcell`. The main tree uses a hand-rolled `treeList` (`treelist.go`), not `tview.List` — see Mouse below for why; row text still goes through `tview.Print`'s same tag-parsing entry point (`[color]text[-]`), so `playRowText`/`taskLabel`/`hostLabel` needed no changes when this migration happened.

`tui.go` owns:
- **Expand state** (`map[*taskNode]bool`) — a new task inherits the *previous* task's current entry (via `allTasks(state)`), except the very first task of a generation, which falls back to `startExpanded` (`.tangsible/config.toml`'s `general.default_tree_state`). This is what makes `E` "sticky" for a still-running playbook.
- **Flattening** — `flattenRows(state, expanded, width)` walks `Plays → Tasks → (if expanded) Hosts` into an ordered row list, rebuilt fresh on every event (cheap at ~10-host scale).
- **Selection preservation** — `rebuild()` tracks the selected row's *identity* (`*playNode`/`*taskNode`/`hostRowID`, not an index, since row order shifts). Computes `selectedIndex` *before* `Clear()`+`AddItem()`, since the cursor row's styling is baked into its own text. A `rebuilding bool` guard is needed because `Clear()`+first-`AddItem()` fires a spurious "changed" event that would otherwise stomp the tracked selection mid-rebuild.
- **Autoscroll** — `following bool` (default true) makes `rebuild()` resolve `selectedIndex` to the newest row. Any genuine navigation disengages it; only `F` re-engages (with its own `jumpingToEnd` guard against immediately un-following itself). End/`G`/Ctrl-E are deliberately plain navigation, not follow-resuming.
- **Navigation triggers a full `rebuild()`** so the cursor's baked-in styling actually moves — otherwise, once frozen (heartbeat ticker stopped), the highlight would never move again.
- **`revealExpandedTask`** — expanding a task via Enter/Right leaves the cursor on the task row itself, so nothing auto-scrolls to reveal newly-added host rows below the fold; this nudges the scroll offset down (never up) just enough to reveal the block's tail.

`NewLiveTUI` returns the `*tview.Application` plus an `applyLive func(rawEvent)` closure; `main.go` never imports `tview` — only `tui.go`/`treelist.go` touch `tview`/`tcell`.

**Heartbeat (`tui.go`).** A 200ms ticker (`spinnerInterval`) calls `app.QueueUpdateDraw(rebuild)`, refreshing the top bar (spinner + elapsed) and the active task's spinner prefix (`state.CurrentTask()`, nil once `processDone`). Stops permanently once `processDone` is observed, after pushing one final frozen frame — elapsed time is latched (`haveFrozenElapsed`/`frozenElapsed`) the first time `rebuild()` sees `frozen == true`, so later rebuilds (from navigation or mouse panning) don't keep recomputing a climbing elapsed time after the run has actually finished. Started only after `app` itself is assigned, for Go memory-model happens-before reasons.

**Resize watcher (`tui.go`).** A second permanent ticker, needed because the heartbeat ticker stops once frozen and nothing else would notice a bare terminal resize then. Skips its body while the run is live (heartbeat already covers resize). Once frozen, compares `list.GetInnerRect()`'s width against `lastRebuildWidth` each tick and calls `rebuild()` + `app.ForceDraw()` only on an actual change. Must use `ForceDraw()`, not `Draw()`/`QueueUpdate` — calling `Draw()` from inside a `QueueUpdate` closure (already on the event-loop goroutine) is a self-deadlock.

**Task source lookup (`source.go`).** `buildTaskSourceIndex(playbookPath)` backs the drill-down's `TASK:` section. Every event's `task.path` is an absolute `file:line`, resolved by Ansible itself even for a Jinja-built `include_tasks:` path — so no include/role resolution needs reimplementing; `buildTaskSourceIndex` just walks every `.yml`/`.yaml` under the playbook's directory tree and indexes each task by `(path, start line)`. A miss (unusual layout, a runtime-generated task) just means no `TASK:` section, never an error. Uses `gopkg.in/yaml.v3`'s line-tracked `*yaml.Node` tree (not a typed struct) to compute each task's end line as the start of the next sibling at whichever ancestor level has one — this is what correctly stops a `block:`'s last task right before a sibling `rescue:` key with no special-casing of `block`/`rescue`/`always`, and handles multi-line scalars for free (the boundary comes from the next task's line, not from measuring the scalar). Source text is sliced verbatim, never reformatted; `{{ ... }}` expressions render as literal text (no Jinja evaluation).

**Output drill-down (`tui.go`).** Root is a `tview.Pages` with `"main"` and `"output"` (a single reused `TextView`). Host rows' `selected` callback calls `showOutput(task, host)` → `formatHostOutput` → switch pages; `SetDoneFunc` (Escape/Enter/Tab/Backtab) switches back. Two gotchas: `TextView.SetText` doesn't reset scroll position, so `showOutput` must call `ScrollToBeginning()` every time; Left/Right and `n`/`N` mean different things per page, so `SetInputCapture` needs a `viewingOutput bool` to dispatch correctly.

`formatHostOutput` decodes `task.Raw[host]` into a generic map (module shapes vary too much for a fixed struct), leads with a colored status line, a `TASK:` section from `sourceIndex[task.Path]`, `primaryOutputField`'s text, then `stderr` if present, then the full result as pretty JSON as a universal fallback. `primaryOutputField` picks `stdout` if non-empty else `msg` — shared with the collapsed-row OK-line summary so both agree on what "the output" means.

**Color in the output view.** `SetDynamicColors(true)` means every piece of dynamic content must be `tview.Escape()`'d first (a literal `[` from YAML/JSON would otherwise be misread as a color tag). Section headings use colors deliberately outside the outcome palette (orange/aqua/red/gray for Task/Output/Errors/Details) so they're never mistaken for an outcome color. `colorizeYAML` gives the Task section light `key:` highlighting via a regexp, not a real YAML parser — good enough, not chased to 100%.

**Diff output (`main.go`, `tui.go`).** `--diff` is unconditionally appended to every generation's invocation. The drill-down gains a **Diff** tab (`buildDiffTab`), a direct port of ansible-core's own `CallbackBase._get_diff` display logic, using `github.com/pmezard/go-difflib`'s `UnifiedDiff` (the same algorithm real `--diff` output uses) — so hunk headers/context grouping match real `ansible-playbook --diff` output. Handles the `diff` field being a single dict or list of dicts, binary/oversize skip notices, and non-string before/after (serialized as JSON, matching Ansible's own default).

**Docs tab (`ansibledoc.go`, `tui.go`).** Shows a task's module documentation by shelling out to `ansible-doc <action>` (the task's own `action` field — `ansible-doc` resolves both bare and FQCN names itself). Strips the ANSI SGR codes `ansible-doc` always emits (rather than translating them to tview tags, which would need re-escaping literal `[` in the docs text without also escaping the tags just inserted). Cached by module name (`docsCache`), not cleared on rerun since module docs don't depend on the run. Tab order in the drill-down: Resolved, Task definition, Docs, Details. A "Play definition" tab existed briefly and was removed outright after live use showed it was never consulted — its whole plumbing (`taskNode.Play`, `playNode.Path`, etc.) came out with it.

**Two-paned drill-down (`tui.go`, `design-docs/TwoPanedLayout.md`).** On a wide enough terminal, the drill-down opens beside the tree instead of taking over the screen. Governed by `general.two_pane_layout` (`*bool`, absent = enabled). A third `Pages` entry, `"split"`, reuses the exact same `flex`/`outputFlex` primitives the other two pages use (not parallel copies) plus a `splitDivider` box. `rebuild()` re-decides `splitMode` live on every call (`totalWidth >= splitMinTotalWidth`, 110 cols) — not decided once at open — using `pages.GetInnerRect()`'s width, since `list`'s own width isn't a reliable proxy once split-mode has pinned it independently of the terminal.

Live-sync: `showOutput` unconditionally sets `expanded[task]=true; currentID = hostRowID{task,host}; following=false` and calls `rebuild()` on every call (not just first open), so `Left`/`Right`/`n`/`N` inside the drill-down keep the tree pane's cursor in sync in real time. Hostnames are omitted from collapsed tree rows while split (the currently-relevant host is already shown via live-sync) — implemented via the same `allHosts == nil` fallback path `computeHostColumnLayout`/`taskLabel` already had for "no hosts reported yet." The tree pane stays fully inert while split (no focus-switching); its bottom-bar hint text swaps to reflect that.

**Row text / host column layout (`taskLabel`/`hostLabel`/`colorTag`, `computeHostColumnLayout`).** `colorTag` maps outcomes to `green`/`yellow`/`teal`/`red`/`maroon` — `teal` for ANSI cyan, `maroon` (not `brown`/`darkred`) because it's in the same base-16 ANSI palette family as the others rather than an RGB-approximated extended name. Hosts are left-aligned starting at a shared column across all task rows (computed once per `rebuild()` via `computeHostColumnLayout`, not per-row) — the widest *natural* task title across the whole run, monotonically non-decreasing since `state.Plays` only grows within a generation. If the widest title + full host list + a breathing-room floor don't fit, the column shrinks first (down to `minTaskTitleName`=30), then hostnames shrink one rune at a time (no ellipsis, floor of 1 rune, overflow accepted beyond that) — run once against the shared column, not per row, so truncated host text lines up column-by-column.

**Collapsed-row summary mode (`design-docs/Morehosts.md`).** When color isn't usable (`NO_COLOR`, non-color terminal, or `general.color = false`) or hosts don't fit even after full shrinking, a task's host list is replaced by a fixed `OK:x/Chgd:x/Skip:x/Fail:x/Unrch:x` count summary instead, colored per-field if color is usable, plain text otherwise. `useColor` is computed once via a throwaway `tcell.NewScreen()` (since `Application.Screen()` isn't available before `Run()` starts) — `SetScreen` must run before `EnableMouse(true)`, since `EnableMouse` only touches a non-nil screen. Live-reevaluated every rebuild, same as `splitMode`.

**Selected-row rendering.** Can't be one uniform `tcell.Style` since different runs within a row need different fg/bg — `playRowText`/`taskLabel`/`hostLabel` each take a `selected bool` that switches their tag construction. `halfBlock` (▌) blends adjacent hostnames' colors at their boundary (selected rows only — tried unselected too, reverted, looked wrong without the "two solid color blocks" context). Uses `pureBlack = "#1a1a1a"`, not `tcell.ColorBlack`/`"#000000"` — a value that exactly matches a base-16 slot's nominal RGB always gets mapped back to that (potentially theme-remapped) slot on reduced-palette terminals; nudging off pure black forces the fixed extended-256 grayscale ramp instead.

**Ctrl-C/`q` (`tui.go`'s `SetInputCapture`).** Behavior depends on `processDone`: while running, both forward SIGINT to the child and leave the TUI open; once finished, both close the TUI. This restores "Ctrl-C behaves like running ansible-playbook directly" (Purpose.md), which `tcell` raw mode would otherwise silently break.

**Keyboard shortcuts (`tui.go`).** `Keyboard-shortcuts.md` is the source-of-truth reference. `SetInputCapture` is three tiers: (1) Quit — `q`/Ctrl-C; (2) universal key aliases applied regardless of frontmost page — `j`/`k`→Down/Up, Ctrl-F/Ctrl-B and Space/`b`→PgDn/PgUp, Ctrl-A/Ctrl-E→Home/End, `G`→End — implemented by returning a *different* synthesized `*tcell.EventKey`, which `Application` forwards to the focused primitive exactly as if typed, so no logic is duplicated per-widget; (3) page-specific bindings, gated on `viewingOutput`: output view gets Left/Right (`navigateOutputHost`) and `n`/`N` (`navigateOutputTask`, both no wraparound); main tree gets `F` (jump-to-bottom + resume follow), `E`/`C` (expand/collapse all), Right/Left (`handleRight`/`handleLeft`), `n`/`N` (`navigateMainTask`). Dialog-open guards (`searchDialogOpen`/`rerunDialogOpen`/`filterDialogOpen`) are checked before tier 2, so a literal typed space/letter still lands normally in a text field.

`handleRight`/`handleLeft` act on whichever row is under the cursor (not `currentID`) — Right is a one-way collapsed→expanded trip (no-op otherwise); Left always means "close/go up" (collapses an expanded task, or on a host row collapses its parent task and moves the cursor there; no-op on a play row). `navigateMainTask(delta)` hops via `allTasks(state)`, bounds-checked, no wraparound, carrying the selected host to the destination task only if that task actually recorded a result for it. Closing the output view syncs the tree's cursor to whatever (task, host) was last shown there, even if that moved via in-view navigation since it was opened.

**Mouse (`tui.go`, `treelist.go`).** `tview.List`'s wheel handling only pans an internal `itemOffset`, but `List.Draw()` unconditionally re-clamps that offset to keep `currentItem` visible on every redraw — so panning could never move the viewport further than the cursor's own distance from the edge. `treeList` (a minimal purpose-built `tview.Primitive`, single-line rows only, no shortcuts/horizontal-scroll/wraparound) fully decouples `itemOffset` from `currentItem`: `Draw()` has no clamp at all; keeping the cursor visible after genuine navigation is handled instead by `ensureVisible()`, called only from `SetCurrentItem` on an actual index change (guarded by the same `rebuilding` flag so `rebuild()`'s own housekeeping calls don't trigger it) — this is what makes unbounded wheel panning possible. Click handling ports `list.go`'s ordering: a row's `selected` callback fires before `SetCurrentItem` moves the cursor there.

**Filtering (`tui.go`, `Filters.md`).** `filterQuery{mode, search}` bundles the filter kind (All/Interesting/Changed/Failed/Search) with a search term. `taskVisible(t, q, sourceIndex, isActive)` is the single predicate: a task matches Changed/Failed if *any* host has that specific outcome (Unreachable counts toward Failed, not Changed); Interesting matches Changed, Failed, Unreachable, a non-empty stderr, or a warning, on any host — the broader "worth a second look" filter, backed by `TaskNode.Warnings`/`HasStderr` (`aggregate.go`), precomputed per host at ingestion time rather than decoded from raw JSON on every redraw (a measured cost — profiling a frozen recap once showed most of its CPU time was exactly that). `isActive` (the run's current in-progress task) always matches regardless of filter, so an in-progress task can't flicker in and out before it has any recorded outcome. The search filter (`taskMatchesSearch`) does case-insensitive substring matching against the task's title, its source text, or any host's output — an empty term matches everything. `flattenRows` skips non-matching tasks entirely, but shows *all* hosts of a task that does match. `visibleTasks`/`visibleTasksForHost` mirror `allTasks`/`tasksForHost` for `n`/`N` navigation so filtered-out tasks are never a navigation target. On a filter switch, if the cursor's task disappears, `nearestVisibleTask` walks forward then backward from its old position to land on the nearest surviving task (only relevant when `following == false`).

Two dialogs, not one (split after live use showed a combined menu+search-box was too easy to fumble): `f` opens a discrete-key `a`/`i`/`c`/`f` menu (`filterDialogOpen`) where every other key is swallowed and `q` closes without quitting (a menu reflex, unlike everywhere else in the app); `/` opens a real `tview.InputField` (`searchDialogOpen`) where every key except Ctrl-C passes through untouched to the field's own native editing, since a real search term can legitimately contain any shortcut letter. Ctrl-C always closes whichever dialog is open *and* still performs its normal abort — the one key that's never ambiguous.

## Rerun (`Rerun.md`)

Re-run a finished playbook (whole thing or `--start-at-task`, with editable tags/hosts) without leaving Tangsible, or via a `rerun` CLI verb.

**Invocation history (`rerunargs.go`, `history.go`, `resolve.go`).** Settings and history are deliberately two separate files/types — combining them meant every invocation's history append rewrote (and could corrupt/strip comments from) the user-authored settings file too:
- `.tangsible/config.toml` — `settingsConfig`, user-authored, read-only from Tangsible's point of view.
- `.tangsible/state.toml` — `stateConfig` (`General.Last`, `History []playbookHistory`), fully app-owned, read+written via full-rewrite each time.

`appendInvocation` is the single funnel every verb invocation goes through: caps history at 20 entries per playbook (oldest dropped), and sets `General.Last` to the target just run — a separate field from `History` because `History` preserves first-seen order, not recency. `lastTarget` falls back to a lone `History` entry if `Last` is unset (covers a state file from a build predating that field); two-or-more entries with no `Last` can't be disambiguated. Only `.tangsible/state.toml` is gitignored, not the whole directory — `config.toml` is meant to be shared/tracked.

Each history entry is one generation's passthrough-arg list as a single string (`argsToHistoryString`/`historyStringToArgs`, a minimal POSIX-ish tokenizer — quoting/escaping only, no expansion). `parsePassthroughArgs` pulls `--tags`/`-t` and `--limit`/`-l` out of a tokenized arg list (both `--flag value` and `--flag=value`, multiple occurrences comma-joined), leaving the rest in `Rest` untouched. An attached short form like `-tfoo` isn't recognized (falls through to `Rest`) — a documented gap.

**Process-restart mechanics (`main.go`).** `tview.Application.Run()` is still called exactly once for the whole process; a rerun spawns a new child and streams into the *same* running `app`. `procHandle` (an `atomic.Pointer[os.Process]`) is what Ctrl-C/`q` forwarding always reads fresh, so it targets whichever generation is current. `spawnGeneration` is the shared "start one invocation" step; `runGeneration` drains one generation's stdout, waits, and records a `generationOutcome`. `main` accumulates one outcome *per generation* (a rerun's tree/screen state is gone by the time Tangsible exits, so its stderr would otherwise be lost) and prints all of them in order after `app.Run()` returns; only the last one decides Tangsible's own process exit code. `requestRerun(startAtTask, tags, hosts)` resets `state` (`playbookState.Reset()`, keeping the `On*Added` hooks wired), reassembles the arg list (new `--start-at-task` if given; tags/hosts from the dialog; everything else carried forward unedited from the *original* invocation's `Rest`), records it, and spawns.

**The re-run dialog (`tui.go`).** A real `tview.Form` — `taskField`/`tagsField`/`hostsField` as plain `InputField`s. A "start at task" checkbox gating `taskField` was tried and dropped: `InputField.SetDisabled()` unconditionally calls its own `finished(-1)`, which `Form`'s shared handler treats as "repeat the last navigation key" once any real Tab/Enter has happened — so toggling the checkbox silently advanced focus, corrupting whatever the user had just typed. `taskField` is always enabled instead, never pre-filled from the cursor.

Modal style matches the search dialog, not the filter menu — every key but Ctrl-C passes through to whichever field has focus. Two exceptions handled centrally: Escape closes the dialog outright (rather than `Form`'s own default of resetting focus to the first field); Enter submits (since `Form` otherwise treats Enter as Tab, never as submit).

**The `rerun` verb (`rerunresolve.go`, `main.go`).** `resolveRerun(args, cfg)` is a pure function implementing precedence: explicit CLI playbook wins over `lastTarget`; CLI `--tags`/`-l` win over that playbook's own history; any other CLI passthrough arg replaces history's `Rest` outright. `ok` is false only when no playbook can be determined at all (no explicit one, no `lastTarget`). A `rerun` invocation records nothing into `state.toml` until the dialog is actually confirmed (via the same `requestRerun`/`submitRerun` path every later rerun uses) — a Ctrl-C before that leaves no trace.

**Test fixtures (`testdata/`).** `basic.yml` (sequential + sleep, live-streaming demo), `outcomes.yml` (all four original outcome buckets incl. ignored failure), `multihost.yml` + inventory (per-host divergence), `hostnames.yml` + inventory (varied-length hostnames for the shrink algorithm, plus one unreachable host for `v2_runner_on_unreachable` — run with `--forks 1` for an observable grey-to-lit transition).

## In-tab search (`Search.md`)

`/` opens a "find text in the currently active tab" prompt in every tab-bearing view (main drill-down, `tangsible diff`, `tangsible hosts`/`host`, `tangsible template`) — scoped to the one tab on screen, never cross-tab or cross-run.

**Core mechanism (`internal/uikit/search.go`)** is built on `TextView`'s own region/highlight API. `TextSearch` reads a tab's plain text via `GetText(true)`, finds every case-insensitive match's byte span, and re-renders the tab wrapping each match in its own colored region tag (black-on-yellow, black-on-orange for the current match). Deliberate simplification: this redraws from *plain* text, so a tab's own supplementary coloring (Diff's line colors, Task's YAML key-highlighting) isn't shown while a search is active — reinserting match tags into already-tagged text would need a hand-rolled tview-tag parser. `Stop()` restores the view's original tagged text and clears highlight state, called whenever a search is cleared.

**Two wiring shapes**, matching how each surface builds its tabs: `tui.go`/`diff.go` rebuild every tab's `TextView` from scratch on each navigation, so search state is wired inline with `clearTabSearch()` at the top of that rebuild; `host.go`/`template.go` build their `TabbedPane` once and populate long-lived `TextView`s later via `SetText`, so they share `internal/uikit/tabsearchbar.go`'s `TabSearchBar` component, with `ClearForView(view)` called right before each individual `SetText` so an async fetch landing on an inactive tab doesn't clear a still-valid search on the active one.

**A real tview dispatch bug**, not just app-level state: focusing a nested `InputField` three `Pages`/`Flex` layers deep doesn't receive forwarded keystrokes via tview's normal path, even though every ancestor correctly reports `HasFocus()`. Worked around by calling `tabSearchInput.InputHandler()` directly from `SetInputCapture` while composing, rather than returning the event for normal dispatch (the same workaround style already used for `treeList`).

**Follow-up fixes worth knowing if touching this again:** switching tabs while a search is active must clear it (`TabbedPane.SetChangedFunc`, covers keyboard *and* mouse tab-switching); `TextView.Highlight()` swaps fg/bg *on top of* whatever color tag a region already carries, so the current-match color must be written pre-swapped into the tag rather than relying on `Highlight()`'s automatic inversion alone; `InputField.SetLabelColor` only sets foreground, so the composing prompt's label needs `SetLabelStyle` with both channels set to avoid black-on-black.

## Current scope constraints (from `Purpose.md`)

These are explicit v1 decisions, not accidental omissions:

- `--ask-become-pass`/`--ask-vault-pass` need no implementation — both prompt during `ansible-playbook`'s bootstrap, strictly before any jsonl event fires, i.e. before the TUI is even constructed, so the prompt reaches the real terminal in its normal (non-raw) state for free.
- **Genuinely unsupported: interactive input requested after the TUI already owns the terminal.** A bare `pause:` (no duration) does *not* hang — Ansible detects non-interactive stdin and skips waiting, completing with a warning visible only in the drill-down's full-JSON fallback. `--step` is worse: it crashes outright (`EOFError`, exit 250) since its confirmation prompt fires from a bare Python `input()` with no non-interactive detection, right at the same event that opens the pre-flight gate. If a mid-run prompt is ever supported, `tcell.Screen.Suspend()`/`Resume()` looks like the right primitive — unexplored beyond that.
- **`strategy: free` shows nothing at all** — confirmed live. Ansible's jsonl callback never emits `v2_playbook_on_task_start` under `free` (only `v2_runner_on_start`/`v2_runner_on_ok` per host, no shared task-start moment), so `aggregate.go`'s `currentTask` stays `nil` all run and every `recordHost` call is silently dropped. The tree stays completely empty while the playbook runs and finishes correctly underneath. Not a small patch: the whole data model assumes one `currentTask` shared by every host, which `free` structurally violates — treated as a distinct, not-yet-planned effort.
- Ctrl-C behaves the same as running `ansible-playbook` directly — implemented (see `tui.go`'s `SetInputCapture`).
- Target scale is ~10 hosts, not hundreds/thousands — an interactive dev tool, not a fleet-management tool.
- Only a limited subset of `ansible-playbook`'s CLI surface is exposed; expand only as needed.
